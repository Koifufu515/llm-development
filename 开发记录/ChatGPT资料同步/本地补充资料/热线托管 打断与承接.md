# 热线托管 V2：承接链路的并发编排与流式响应

> 面向：过一段时间不打开源码也能重新理解承接链路的设计。
> 范围：`AgentChatV2Component.streamWithNonBizIntent` 这一条三分支链路，重点在承接与并发编排。
> 源码定位见文末附录 A。

---

## 一、业务问题

热线客服场景里，用户说完一句话后，系统通常要完成几件事：

- **打断检查**：判断当前请求是否已经被电话系统取消（用户挂断、CTI 转接到其他坐席/队列/IVR 等）。CTI（Computer Telecommunication Integration，计算机电信集成）是呼叫中心的电话侧中间件，负责电话呼叫控制、语音转文本、把本服务返回的话术合成语音播给用户；用户打断时由 CTI 往 Redis 写打断标记（推断，项目中只有检查redis打断标记的代码，没有写入的代码）。
- **业务路由**：理解用户的业务诉求，选择合适的 Skill，准备执行计划。
- **非业务意图识别**：判断用户是否在闲聊、辱骂、要求转人工、表达安全风险等，是否需要由专门流程接管。
- **承接回复**：生成简短的过渡话术，在正式业务回复准备期间减少用户的等待感。

如果串行执行——先意图识别，再业务路由，最后生成回复——多个步骤都涉及模型调用，用户等待时间会累加。在 IVR 场景里，用户长时间听不到声音会以为掉线。

为降低延迟，系统采用 **并发准备、统一仲裁、按序输出** 的设计。

---



## 二、整体架构

四项任务**尽早并发执行**，但它们的执行结果并不都会发送给用户。系统根据打断检查和非业务识别的结果，决定最终采用哪条处理路径。

决策优先级：

> **用户已打断 ＞ 非业务意图接管 ＞ 正常业务处理**

- 打断检查优先级最高。入口检查发现请求已取消，就不继续正常业务回复。
- 没打断，再看非业务识别结果：需要接管则切换到专门流程；无需接管则放行正常业务。
- 转人工和外投升级有计数阈值，未达阈值的那一轮不立即接管，只累计次数。

## 三、一次请求的执行过程

> 以下按"处理阶段"组织，不按固定时间点。并发任务完成顺序不固定——非业务识别可能先于打断检查完成，业务路由也可能早于承接生成结束。



### 阶段 1：并行启动任务

请求进入系统后，四项任务尽早并发启动：


| 任务    | 主要作用                      |
| ----- | ------------------------- |
| 打断检查  | 查询 Redis，确定请求是否已经失效       |
| 业务路由  | 调用路由 Agent，准备 Skill 和执行计划 |
| 非业务识别 | 调用独立的识别 Agent，判断是否需要特殊处理  |
| 承接生成  | 提前生成用户等待期间的过渡话术           |


四个任务都涉及阻塞调用（查 Redis、调 LLM），各自有专用线程池。系统通过 Reactor 组织异步任务、控制订阅关系和数据流转（`Flux.merge`/`flatMap`/`concat`/`takeUntilOther`/`filter`/`map` 等非阻塞操作符）；对于 Redis 查询、同步模型调用等阻塞操作，使用独立线程池隔离，避免长时间占用其他请求需要使用的执行线程。Reactor 操作符默认在信号到达的线程上执行，没有显式 `subscribeOn`/`publishOn` 时不一定运行在固定线程上，关键是把阻塞调用挡在专用线程池里。

需要区分**任务声明与实际执行**：Reactor 中的任务通常在被订阅后才真正执行。系统通过"预热订阅"尽早触发业务路由、非业务识别和承接生成，而不是依次等待前一个任务完成。

### 阶段 2：检查打断与识别意图

系统需要决定本轮请求最终采用哪种处理方式。

- 打断检查通常最快完成（查 Redis）。
  - 命中打断：取消业务路由，最终决策为"打断"。
  - 未命中：等待非业务识别结果。
- 非业务识别完成后，结合打断结果形成**最终决策**，三种互斥结果之一：
  - 打断
  - 非业务接管
  - 正常业务放行

如果非业务识别命中接管（含转人工/外投达阈值），系统取消不再需要的业务路由。

### 阶段 3：承接话术——提前生成，决策后才允许发送

承接话术是缓解等待时间的关键。它和业务路由、非业务识别并发生成，例如：

> "好的，正在为您查询相关信息。"

但**提前生成不代表立即发送**。系统必须先完成打断检查和非业务识别，确认本轮请求允许正常业务处理。

只有正常业务被放行，承接话术才允许进入最终输出。

这把承接拆成两个独立阶段：

- **生成阶段**：提前执行，争取降低等待时间。
- **发送阶段**：等待最终决策放行，避免发送与最终业务决策冲突的话术。

承接发送不需要等待业务路由完成，但仍需等待打断检查与非业务识别的最终决策。决策放行后，承接在业务路由仍在准备的同时先发送给用户。

承接话术是**流式生成与流式发送**的：决策放行后，已经生成的部分立即开始发送，后续内容边生成边发，不需要等承接全部生成完才开始。

### 阶段 4：承接结束后输出主 Agent 回复

正常业务放行后，系统按固定顺序输出：

> **承接回复 → 主 Agent 正式回复**

承接发送期间，业务路由仍在并行执行。承接结束时：

- 如果业务路由已经完成，直接使用准备好的执行计划。
- 如果业务路由还没完成，等待剩余的准备过程。

在正式执行主 Agent 前，系统会**再次检查打断状态**。这是因为入口只检查一次 Redis，无法保证后续执行期间用户没有挂断。二次检查发现打断，就不再进入主 Agent 生成流程；检查通过，主 Agent 才开始调用模型和工具，以流式方式输出结果。

### 阶段 5：统一组织 SSE 输出

虽然系统内部并行执行多个任务，但对外需要保持稳定的响应协议。

整个 SSE 输出分两部分：

1. 先发送固定配置帧，让客户端知道如何处理后续响应（如关闭思考过程展示）。
2. 根据最终决策，选择三条互斥输出路径之一：
  - **打断处理**：发送兼容旧 IVR 协议的占位内容。
  - **非业务接管**：执行专门的话术或工具处理。
  - **正常业务**：先发送承接，再发送主 Agent 回复。

系统使用 `Flux.merge` 并发订阅多个任务和输出路径，使用 `Flux.concat` 保证配置帧先发送，并保证正常业务路径内部承接先于正式回复。

虽然内部存在多条并发流，但最终处理方向由同一个决策结果控制，避免不同路径的回复同时混入用户会话。

## 四、关键技术机制



### 4.1 任务启动与预热

Reactor 的 `Mono` / `Flux` 是声明式的：构造时只定义流，**被订阅时才真正执行**。

如果直接把四项任务串成一条链，每一步都要等前一步完成才订阅下一步，等于串行执行。系统用"预热订阅"打破这个限制：在最终输出流被订阅时，通过 `Flux.merge` 同时订阅多个预热分支，让业务路由、非业务识别、承接生成**尽早开始实际执行**，而不是等最终决策才启动。

业务路由是同步阻塞调用（路由 Agent 选 Skill、装配工具），不能跑在 Reactor 共享线程上。它通过 `CancellableBizIntent` 包装，被订阅时提交到独立线程池 `v2ExpertExecutor` 执行。承接生成同理，用专用线程池 `bridgeReplyExecutor`。

### 4.2 输出仲裁

三条输出路径的互斥由两个机制共同保证：

1. **状态互斥**：最终决策只有一种状态（打断 / 非业务接管 / 正常业务放行），三种状态不会同时成立。
2. **按状态过滤**：三条输出流分别匹配不同的决策状态，同一个决策结果只会通过一条过滤。

三条输出路径互斥靠的是决策本身——决策只会有一种结果，三条路径分别匹配不同结果，同一条决策只会放过一条。`cache()` 不参与互斥判断，它的作用是保证三条路径拿到的是同一个决策结果：没有它，三条路径会各自触发一次决策，既浪费资源，又可能因为决策有非确定性而算出不同结果，互斥就破了。

需要区分**输出互斥**与**执行互斥**：

- 输出互斥：最终只有一条路径的内容发送给用户。
- 执行不互斥：在最终决策产生之前，业务路由、非业务识别、承接生成都在并行执行；决策产生后，不再需要的任务才被请求取消。

也就是说，用户最终只看到一条输出路径，但系统内部一度同时运行多个任务。

### 4.3 承接与主回复时序

承接与主回复的顺序由 `Flux.concat` 保证：`concat` 的语义是"前一个流完成才订阅下一个"，所以承接流没发完，主回复流根本不会被订阅，更不会发送。

这不是靠时序控制，是靠 Reactor 的订阅顺序——承接流 `onComplete` 后，`concat` 才订阅主回复流。

承接发送期间，业务路由在独立线程池上继续跑。承接发完订阅主回复流时，业务路由结果通过 `Mono.cache()` 共享：已完成则直接拿缓存进入主 Agent 调用，未完成则等。

主回复首帧需要携带 `interruptible` 标志（告诉 CTI 这段播报能不能被打断）：

- 如果承接发过，承接首帧已经声明了 `interruptible`，主回复首帧不再补。
- 如果承接没发（生成失败/超时/取消），主回复首帧补 `interruptible=false` 兜底，保证 CTI 拿到确定状态。

承接首帧的 `interruptible` 由承接 Agent 的输出协议决定（`I=0`/`I=1` 控制头），生成侧解析后写入 SSE 帧的 `interruptible` 字段。

### 4.4 取消机制

并发提高了响应速度，但也意味着某些任务可能在已经不需要时继续执行。系统用两种机制取消任务，外加一个状态记录对象。

#### 响应式取消：`Sinks` + `takeUntilOther`

非业务识别和承接生成是响应式流，用 Reactor 的响应式取消：

- 系统通过 `Sinks` 发送停止事件（打断命中、非业务接管命中）。
- 任务流通过 `takeUntilOther` 监听这些事件，事件触发时取消订阅，向上游传播取消。

需要注意：**取消订阅不保证底层模型 HTTP 请求立即终止**，具体取决于 HTTP 客户端是否响应取消。承接生成被取消时，会记录取消状态用于后续异常分类。

#### 业务路由取消：`Future.cancel(true)`

业务路由是同步阻塞的 `Callable`，跑在独立线程池上，`takeUntilOther` 对它无效。系统通过 `CancellableBizIntent` 持有执行任务的 `Future`，不再需要时显式调用取消方法，内部用 `Future.cancel(true)` 尝试中断工作线程。

线程中断是**协作式取消**：如果底层调用不响应中断（比如阻塞在不可中断的 IO 上），任务可能继续执行。这是工程上的真实边界。

#### 取消状态记录：`branchCancelContext`

`branchCancelContext` 内部用 `AtomicBoolean` 记录取消状态，主要用于异常分类和后续处理判断，**不直接停止任何任务**。

三者分工：

- `Sinks`：发送响应式停止事件。
- `Future.cancel(true)`：请求中断业务路由线程。
- `branchCancelContext`：记录取消状态，不直接取消任务。

业务路由的真正取消入口是 `bizIntent.cancel()`，它内部会同时设置 `branchCancelContext` 标志和调用 `Future.cancel(true)`。

## 五、设计价值与工程取舍

这套方案的核心不是简单地把几个 Agent 放到线程池里并行执行，而是解决了三个问题。

### 1. 减少串行等待

业务路由、非业务识别和承接提前执行，把多个耗时步骤的等待时间重叠起来。承接发送期间业务路由继续跑，承接"覆盖"了业务准备时间。

### 2. 保证回复方向一致

系统通过统一的最终决策，控制正常业务和非业务处理之间的互斥关系，避免错误分支向用户发送内容。三条输出流过滤同一个决策结果，只有符合当前决策的路径能够输出。

### 3. 平衡低延迟与取消成本

系统允许提前执行可能用不到的任务（比如最终被打断的承接），以换取更短的响应时间。明确不再需要某个任务时，主动请求取消，减少不必要的计算开销。

### 代价

- 多个模型调用可能同时消耗资源（线程池、LLM 配额）。
- 取消订阅或中断线程不一定能立即终止底层模型请求。
- 整体复杂度上升：并发竞态、取消传播、状态共享都需要额外机制保证正确性。

这套方案实际上是在**响应延迟、计算成本、执行复杂度**之间做权衡。

### 承接解决的是什么、不解决什么

承接解决的是**用户感知的首字节延迟**和**空白等待体验**，不是主回复总耗时：

- 用户听到第一个字的时间大幅缩短（承接首字节远快于主回复首字节）。
- 主回复 LLM 的等待时间本身没有缩短。
- 总耗时（听到主回复完整内容）没有明显缩短，甚至略增（多了承接生成+发送的串行环节）。

面试如果被问"承接是不是让主回复更快了"，要诚实说"没有，承接是让用户更快听到声音，总耗时没缩短"。

## 六、总结

热线托管 V2 的核心是一个并发编排机制：

- 业务路由、非业务识别、承接生成**尽早并发执行**，打断检查同时进行。
- 由打断检查与非业务识别决定**最终处理方向**。
- 正常业务放行后，先输出提前准备的承接话术，再输出主 Agent 正式回复。
- 非业务接管或用户打断时，取消不再需要的任务，切换到专门的处理流程。
- 整个过程通过 Reactor 管理异步订阅与流式输出，通过专用线程池隔离阻塞调用，并结合响应式取消与 Future 中断控制资源消耗。

**最终实现的目标是：尽早开始计算、延后确定输出、保证回复有序，并尽可能减少用户等待时间。**

| ---------------------- | ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `Mono` / `Flux`        | 声明式异步流，订阅时才执行    | 四项任务编排                                                                                                                                                                                     |
| `Mono.cache()`         | 缓存执行结果，多订阅者共享    | `finalOutcome`、`bizIntentPreparation` 共享决策与业务准备结果；承接流 `bridgeChunks.cache()` 让 `warmup` 和 `sequence` 共享同一份生成结果。注意：`cache()` 后上游加载过程不能仅靠后续订阅者取消终止，承接停止必须靠 `takeUntilOther(stopSignal)` 主动触发 |
| `Flux.merge`           | 并发订阅多个流          | 驱动预热分支和三条输出路径并发                                                                                                                                                                            |
| `Flux.concat`          | 顺序订阅，前一个完成才订阅下一个 | 配置帧先发；承接先于主回复                                                                                                                                                                              |
| `Sinks.Empty`          | 手动发送完成信号         | `abortDetected`、`nonBizIntentDetected` 通知停止                                                                                                                                                |

| `subscribeOn`          | 指定流执行的调度器        | 承接生成用 `bridgeReplyExecutor`；业务路由**不经过** `subscribeOn`，由 `CancellableBizIntent` 通过 `executor.submit()` 直接提交到 `v2ExpertExecutor`                                                             |
| `onErrorResume`        | 异常恢复，转成备用流       | 承接异常/超时返回空流，静默降级                                                                                                                                                                           |
| `doOnCancel`           | 被取消时的回调          | 承接被取消时记录状态                                                                                                                                                                                 |
| `Future.cancel(true)`  | 中断线程池工作线程        | 业务路由取消                                                                                                                                                                                     |


> 注意：`onErrorResume` 是异常恢复机制，不是取消机制。取消走 `takeUntilOther` + `doOnCancel`，超时走 `timeout` 触发的 `onError`。两者不要混。



## 附录 C：三种任务的调用形式与取消机制

承接、业务路由、主 Agent 三个任务都调 LLM，但调用形式和取消机制各不相同。**调用形式跟产出形态绑定，取消机制跟任务在链路里的位置绑定**。


| 任务      | 产出形态             | 调用形式                | 取消机制                         | 取消触发方式       |
| ------- | ---------------- | ------------------- | ---------------------------- | ------------ |
| 承接      | 流式话术（边生成边发给用户）   | `Flux`              | `takeUntilOther(stopSignal)` | 主动监听打断/非业务信号 |
| 业务路由    | 一次性决策（选哪个 Skill） | `Callable` 包 `Mono` | `Future.cancel(true)`        | 主动调取消方法中断线程  |
| 主 Agent | 流式回复（边生成边发给用户）   | `Flux`              | 无主动监听，靠下游断开传播                | 被动等 SSE 连接断开 |




### 为什么调用形式不同

- **承接和主 Agent 要流式输出**：用户要尽早听到声音，LLM 每产出一个 chunk 就转成 SSE 帧发给 CTI，不用等全部生成完。用 `Flux`（响应式流）才能边产出边消费。
- **业务路由是一次性决策**：路由结果是"选 Skill A、装配这些工具"这样的完整对象，下游要拿到完整决策才能开始主 Agent。没有"边路由边产出"的需求，用 `Callable` 跑完一次性返回最直接。



### 为什么取消机制不同

取消机制不取决于"跑在哪个线程池"（三个任务都跑在独立线程池），取决于"任务在链路里的位置 + 调用形式"：

- **承接在并行阶段跑**：决策还没出来就开始生成，需要主动监听 `stopSignal`（打断命中或非业务接管命中），信号一响立即停——避免决策出来后承接还在白跑。用 `takeUntilOther` 因为承接是 `Flux`，Reactor 能沿管道传播取消。
- **业务路由是同步阻塞** `Callable`：项目用 `Mono.create` + `executor.submit()` 手动提交任务到 `v2ExpertExecutor`，**不是** `Mono.fromCallable`。取消由 `CancellableBizIntent.cancel()` 显式管理：内部持有 `Future`，调用 `Future.cancel(true)` 中断工作线程，同时设置 `branchCancelContext` 标志。任务生命周期和取消控制完全由 `CancellableBizIntent` 封装，与 Reactor 的取消传播无关。
- **主 Agent 在最终决策放行后才开始**：决策已经出来了，不需要再监听决策信号。主 Agent 流式输出阶段**不主动检查打断标记**（`streamPreparedPlan`/`executeStream` 没有 `abortCheck` 参数）。用户打断靠 CTI 断开 SSE 连接，触发 `doFinally` 里的 `SignalType.CANCEL` 分支，调 `branchCancelContext.cancel()` 和 `bizIntent.cancel()` 清理还在跑的任务。**取消能否传播到** `agent.stream()` **内部并终止底层 LLM HTTP 请求，取决于** `agent.stream()` **的 Reactor 链实现和 HTTP 客户端是否响应取消——这部分未读源码，标记为待验证**。已发出去的话术收不回，能停的靠断开就够了。



### 工程边界

两种取消都不保证底层 LLM HTTP 请求立即终止：

- `takeUntilOther` 取消订阅后，是否终止 HTTP 取决于客户端是否响应取消。
- `Future.cancel(true)` 中断线程，如果底层阻塞在不可中断的 IO 上，任务可能继续执行。

这是协作式取消的固有边界——取消是"请求停止"，不是"强制杀死"。

## 附录 D：承接对延迟的影响（量化分析）

> **重要前提**：以下公式计算的是**服务端 SSE 首帧发出时刻**，不是用户真正听到声音的时刻。真实热线链路还要经过 CTI 接收 → TTS 合成 → 音频起播，"服务端已发送"和"用户听到声音"之间有几十到几百毫秒差。本附录只做服务端侧的理论分析，用户实际首音延迟需用真实监控数据验证。

承接只作用于**业务放行**路径（打断或非业务接管时承接被取消不发）。下面的分析假设本轮走业务放行。

### 时间变量

- `a` = 非业务意图识别耗时
- `b` = 业务路由耗时
- `c` = 主 Agent 回复到第一个字耗时
- `d1` = 承接**生成首字**耗时（LLM 产出第一个 chunk）
- `d` = 承接**生成完成**耗时（LLM 产出完整话术）

四个任务（非业务识别、业务路由、承接生成、打断检查）并行启动。打断检查很快，可忽略。

### 没承接时

用户听到第一个字 = `max(a, b) + c`（主 Agent 要等非业务识别和业务路由都完成才能开始，取较慢者再加主回复首字）。

全程连续空闲 `max(a, b) + c`。

### 有承接时

承接**生成**提前并行跑，但承接**发送**要等 `finalOutcome` 判定 `bizIntentAllowed`——而 `finalOutcome` 依赖非业务识别（a）。所以：

- 承接**生成首字**时刻 = d1
- 承接**发送首字**时刻 = `max(d1, a)`（生成好了但要等决策才能发）
- 承接**生成完成**时刻 = d
- 承接**发送完成**时刻 = `max(d, a)`

通常 d1 < a（承接是短话术，比非业务识别快），所以用户听到承接首字 ≈ **a**——承接首字在 a 时刻立即发（早就生成好缓存着，订阅立即发）。

**主回复首字时刻**：`Flux.concat(bridgeStream, orderedMain)` 要求承接流 `onComplete` 才订阅主回复流，所以主 Agent 启动时刻 = `max(承接发送完成, 业务路由完成) = max(max(d,a), b) = max(d, a, b)`。听到主回复首字 = `max(d, a, b) + c`。

与没承接的 `max(a, b) + c` 相比，差异 = `max(d, a, b) - max(a, b)`：

- 若 `d <= max(a, b)`（承接在业务路由前结束，常见情况）：主回复首字**没变**。
- 若 `d > max(a, b)`（承接结束晚于业务路由）：主回复首字**被推迟** `d - max(a, b)`。



### 时序示意（a=2s, b=3s, c=1s, d1=0.5s, d=1.5s）

```
0s      0.5s     1.5s     2s          2.5s     3s       4s
│       │        │        │           │        │        │
启动    承接首字  承接完   finalOutcome 承接发完  路由完   主回复首字
                          承接首字发出
```

空闲被切成两段：0~2s（等承接首字）+ 2.5~4s（等主回复首字）。

注：本例 d=1.5s < max(a,b)=3s，主回复首字没推迟。若 d > max(a,b)，主回复首字会被推迟。

### 承接改变了什么、没改变什么


| 指标      | 没承接                | 有承接                | 变化                                             |
| ------- | ------------------ | ------------------ | ---------------------------------------------- |
| 听到第一个字  | `max(a, b) + c`    | `max(d1, a)` ≈ a   | 缩短（省掉 b 和 c 的等待）                               |
| 听到主回复首字 | `max(a, b) + c`    | `max(d, a, b) + c` | **条件性**：`d <= max(a,b)` 时没变；`d > max(a,b)` 时推迟 |
| 主回复总耗时  | 不变                 | 不变                 | 没变                                             |
| 整轮总耗时   | —                  | 略增（多了承接生成+发送）      | 略增                                             |
| 连续空闲    | `max(a, b) + c` 一段 | 被切成两段              | 体验改善                                           |




### 关键区分：生成 vs 发送

承接设计的核心是**生成提前、发送等决策**：

- **生成**：在 `start` 时被 `warmup` 订阅启动，并行跑，不等任何决策。d1 时刻首字生成好，d 时刻完整话术生成好，缓存在 `bridgeChunks`（`.cache()`）。
- **发送**：在 `sequence` 里要等 `finalOutcome` 判定 `bizIntentAllowed` 才订阅 `bridgeStream`。决策一出，缓存的首字立即发，不用等承接重新生成。

承接省掉的是"承接生成时间"（生成提前到 d1 完成），**没省掉**"非业务识别时间" a——发送还是要等 a。所以首字从 `max(a,b)+c` 缩短到 a，不是缩短到 d1。

### 面试要点

- 承接不缩短主回复总耗时。听到主回复首字的时间**不一定**不变：承接结束早于业务路由时没变，晚于业务路由时被推迟（因为 `Flux.concat` 要等承接发完才订阅主回复流）。
- 承接缩短的是"听到第一个字"的时间：从 `max(a,b)+c` 缩短到 `max(d1, a)` ≈ a。
- 缩短的来源是省掉 b（业务路由）和 c（主回复首字）的等待，不是省掉 a。
- 连续空闲被切成两段，体验改善但总耗时没缩短，甚至略增。

## 附录 E：非业务意图识别

> 正文第三节阶段 2 只讲了"非业务识别完成后参与最终决策"，这里展开 `NonBizIntentAgent` 的内部机制：关键词短路、小模型识别、命中后走什么链路。源码定位见附录 A。

### 职责与位置

非业务意图识别判断用户本轮是否需要业务 Skill 之外的特殊处理（转人工/外投/安全/辱骂/邀评/超范围等），与业务路由并行跑。由 `NonBizIntentAgent.classify`（`NonBizIntentAgent.java:88`）实现，只在 IVR_HOSTING 链路调用。

### 输入输出

- 输入：最近 2 轮对话 + 当前用户消息（`buildInput`，:266-281，`RECENT_DIALOGUE_LIMIT=2`）。
- 输出：`NonBizIntentDecision`（`HostingIntentDecisionEnum` 枚举 + reply 话术）。

### 两层判定：关键词短路 → 小模型

#### 第一层：关键词短路（不调模型）

两个通道，命中直接定结论：

| 通道 | 触发条件 | 判定 | 代码 |
|---|---|---|---|
| 安全硬通道 | 命中 `SAFETY_KEYWORDS` 且不含 `SAFETY_HEDGE_WORDS` | `SAFETY_EVENT` | `matchSafetyEvent`，:126-139 |
| 辱骂兜底 | 粗口正则命中达阈值（默认 2 次） | `ABUSIVE_LANGUAGE` | `AbuseKeywordDetector` |

安全关键词（:59-61）：车祸、撞车、追尾、翻车、撞到人、撞伤了、受伤、流血、骨折、送医院、住院、昏迷、急救、被困、反锁、失联、被跟踪、被威胁、恐吓、自杀、跳楼、性骚扰、猥亵。

辱骂兜底的原因：露骨辱骂可能被模型内容审核拒绝，拒绝后按放行交主 Agent，所以先拦。

#### 第二层：小模型识别

关键词未命中才调小模型（`invoke`，:159-223）。模型输出 JSON，解析出 `HostingIntentDecisionEnum`。12 种意图：

| 枚举 | 含义 | 是否接管（取消主 Agent）|
|---|---|---|
| BLOCK_META | 数学/写作/翻译/编程/天气/娱乐等非客服能力，提示词注入 | 是 |
| IDENTITY_PROBE | 探测当前客服是人工还是 AI | 是 |
| ABUSIVE_LANGUAGE | 辱骂、人身攻击 | 是 |
| ALLOW_SKILL | 可由候选技能处理 | 否（交回主 Agent）|
| ALLOW_CONTINUATION | 依赖历史会话的业务延续 | 否（交回主 Agent）|
| SOCIAL_ACK | 寒暄、确认、结束语 | 是 |
| HUMAN_TRANSFER | 请求转人工 | 否（只计数，达阈值才接管）|
| SAFETY_EVENT | 人身安全事件 | 是 |
| EXTERNAL_ESCALATION | 外投威胁 | 否（只计数，达阈值才接管）|
| INVITE_SATISFY | 用户感谢/满意，触发邀评 | 是 |
| BLOCK_OUT_OF_SCOPE | 超出客服技能范围 | 是 |
| UNCERTAIN | 信息不足 | 否（交回主 Agent）|

注：代码里是 12 个枚举（`HostingIntentDecisionEnum.java:8-19`），不是 11 个。

### 命中后由什么接管、为什么

命中非业务意图后，**取消主 Agent，由非业务链路接管**。接管者不是某个 LLM Agent，而是工程侧的旁路逻辑——直接调工具或播预设话术，不再调业务模型。原因：这些意图是确定性的，不需要模型再推理（转人工就是转接、邀评就是邀评、辱骂不需要业务回复），而且安全事件必须立即转接，不能等模型再生成一轮。

接管分三种：

| 命中意图 | 接管方式 |
|---|---|
| 邀评（用户感谢/满意）| 调邀评工具记录邀评事件，再播邀评话术；工具失败只播普通感谢 |
| 安全事件 / 转人工达阈 / 外投达阈 | 调转接工具通知电话系统转人工或专员，再播兜底话术 |
| 辱骂 / 身份探测 / 寒暄 / 超范围 / 非客服能力 | 直接播预设话术 + 落库，不调工具 |

不接管（交回主 Agent）的四种：业务可处理、业务延续（主 Agent 正常回复）、不确定（兜底交主 Agent）、转人工/外投未达阈值（只后台计数，本轮仍由主 Agent 回复，达阈值才接管）。

### 关键设计点

- **关键词短路在模型超时窗口外求值**：模型超时会退化成"不确定"交回主链路，安全事件不能只依赖模型这一条通道，所以安全关键词命中直接定结论，不调模型。
- **转人工/外投计数阈值**：未达阈值的那一轮不立即接管，只累计次数，由主 Agent 结合上下文正常回复；达阈值才接管并取消主 Agent。转人工达阈值时同步登记，不像外投那样推迟到本轮结束。
- **接管优先级**：安全事件 > 转人工诉求 > 外投风险。
