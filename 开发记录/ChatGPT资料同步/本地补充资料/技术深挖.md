## 第 1 部 异步、线程、流怎么接

### 1.1 一句话主线

一次热线请求要做三件事：**接住用户的话 → 想出回复 → 把回复一段段流式吐回去**。中间靠 Reactor 的「流」把这三件事串成一条异步管道，线程只在每个步骤被借来用一下、用完就还回池子，没有线程从头陪到尾。

理解这条链路的关键不是记住一堆类名，而是分清三层：**流是什么、流怎么对外变成 SSE、流之间怎么拼接**，以及一个真实生产故障——**模型 SSE 的线程池被工具 RPC 占满**——是怎么治的。

---

### 1.2 流是什么：Flux 是「步骤描述」，不是「线程在跑」

最容易混的起点是把「流」和「线程」绑死，以为流等结果就必须有个线程在那等。

**事实**：`Flux`/`Mono` 是 Reactor 里描述「后续怎么执行」的类型，本身不持有线程。一条流从头跑到尾，可能借过好几个线程执行不同步骤；**等结果期间没有线程在等**——结果没来就没活干，线程早还回池子被借去跑别的请求了。结果回来，由拿到结果的那个线程触发下一步 lambda。


|      | 流（Flux/Mono） | 线程             |
| ---- | ------------ | -------------- |
| 是什么  | 步骤描述（声明）     | 执行者            |
| 数量   | 一个请求一条流      | 池子里有限个，被借来执行步骤 |
| 等结果时 | 流逻辑上「暂停」     | 不占线程，已还回池子     |


这就是 Reactor 用少量线程处理大量并发的核心：**「等结果」不占线程，「执行下一步」才借线程**。

---



### 1.3 一次请求怎么变成 SSE：Flux 数据帧 → SseEmitter → HTTP

热线 V2 链路里，组件层产出一个 `Flux<String>`，每个 String 是一个待发送的 JSON 数据帧（如 `{"type":"content","data":"你好"}`）；Service 层 `subscribe` 这个 Flux，把每个帧经 `SseEmitter` 写进 HTTP/SSE 响应（代码事实：`AgentChatV2Service.executeExpertStream`）。

衔接关系：

```
组件产出数据帧 → Flux<String>（数据流）→ Service subscribe 转发 → SseEmitter.send → HTTP/SSE 响应 → 客户端
```

两个对象分工：

- `Flux<String>`：组件产出的数据帧流，还不是 SSE 事件，只是 JSON 字符串。
- `SseEmitter`：Spring MVC 的异步响应类型，是 Service 往 HTTP 响应里写数据的「管子口」。真正的 HTTP 连接由 Spring MVC/Servlet 容器在 Controller 返回 emitter 后接管。

Service 在中间做的事（骨架）：创建 emitter → 取得本轮处理权（`takeTurn`，对启用队列的渠道串行处理同一会话）→ 起心跳（15s 一次保活）→ 注册超时/断连/出错回调 → `subscribe` Flux 把事件搬到 emitter。

**待确认**：`StreamSessionQueue` 只对 Apollo 配置命中的渠道启用（默认 `ivr_hosting`），通过 Redis 锁协调同一 session；取锁或入队失败时降级为直接处理，因此不是任何情况下都绝对串行——这是代码事实，但具体哪些渠道命中需查 Apollo 配置。

### 1.4 流之间怎么拼接：concat 排顺序，merge 并行

热线一轮里要同时跑四个任务：**打断检查、业务路由、非业务意图识别、即时承接生成**。它们都涉及阻塞调用（查 Redis、调 LLM），用 `Flux.merge`/`flatMap` 并行触发，再用 `Flux.concat`/`takeUntilOther` 按决策顺序拼成最终 SSE 流。

**顺序拼接（**`Flux.concat`**）**：保证前一条流 `onComplete` 后才订阅下一条。热线里用它保证：

- **配置帧在最前**：`{"type":"config","enableThinkingProcess":false}` 先发，客户端先初始化再处理后续事件。
- **承接短句在前、主回复在后**：`IvrHostingBridgeCoordinator` 用 `Flux.concat(bridgeStream, orderedMain)`，承接流先发短句占住用户，主 Agent 正文等承接决策完成再订阅输出。

**并行触发（**`Flux.merge`**/预热订阅）**：四个任务不等前一个完成，尽早订阅触发，谁先有结果谁先走。承接生成失败/超时/不合规都转成 `Flux.empty()`，对下游是正常 `onComplete`，`concat` 立刻订阅主流，**承接失败不阻断主回复**。

**打断时的占位**：用户抢话或挂断被检出时，输出一个 `content("...")` 占位帧（不是真正内容），结束靠后面的 done 帧——IVR 看到 done 才知道本轮结束。

### 1.5 线程在哪：阻塞调用甩专用池，共享线程只跑轻量编排

热线链路里有两类线程活：


| 活的类型          | 谁干            | 例子                                                       |
| ------------- | ------------- | -------------------------------------------------------- |
| 轻量编排（非阻塞，纳秒级） | Reactor 共享线程池 | `merge`/`flatMap`/`concat`/`filter`/`map` 把数据从一个操作符传到下一个 |
| 阻塞 IO（等网络往返）  | 各专用线程池        | 查 Redis、调 LLM、调工具 RPC                                    |


**为什么要分**：阻塞调用若跑到 Reactor 共享线程上，一个线程被占死 1~2 秒，排在它上面的别的请求的 `merge`/`flatMap` 全被堵住，Reactor 高并发前提就破了。所以阻塞调用一律 `subscribeOn(专用池)` 甩出去，共享线程只负责把它们四个的产出拼成最终 SSE 流。

**真实例子——查打断**：`recheckAbort` 返回 `Mono<Boolean>`，用 `subscribeOn(Schedulers.fromExecutor(ivrAbortCheckExecutor))` 把查 Redis 甩到 `ivrAbortCheckExecutor` 专用池（代码事实：`AgentChatV2Component.java:759-769`）。调用链的 Reactor 线程 subscribe 完就还回池子去跑别的请求，查 Redis 那个线程阻塞等 Redis 返回，结果回来由它触发 `flatMapMany` lambda 决定走主回复还是返回 `...`。

热线三道打断检查（入口 `buildAbortDecision`、路由后 `streamPreparedPlanUnlessAborted`、非业务回复前 `executeNonBizIntentOutcome`）每道查 Redis 都在 `ivrAbortCheckExecutor` 上，调用链线程不阻塞。

### 1.6 一个真实故障：模型 SSE 池被工具 RPC 占满



#### 先理清这几个池（否则下面会晕）

这一节会出现好几个"池"，先按「是不是同一个池」归类，关系就清楚了——它们都是线程池，区别只在于**谁建它、给什么活用、是不是独占**。


| 名字                            | 是什么                                                                                      | 给谁用                             |
| ----------------------------- | ---------------------------------------------------------------------------------------- | ------------------------------- |
| `Schedulers.boundedElastic()` | Reactor 库**自带**的全局弹性池，默认 CPU×10 线程 + 10 万队列，谁都能 `subscribeOn` 它                          | 治理前：模型 SSE 读 + 工具 RPC **都挤在这里** |
| Reactor 共享线程池                 | 在本项目语境里主要就指上面这个 `boundedElastic`（被多方共用，所以叫"共享"）                                          | 同上，不是另一个池                       |
| 模型 SSE 池                      | 项目**自建**的专用池（`IsolatedSchedulerHttpTransport` + `VirtualThreadSseExecutor`），虚拟线程 + 信号量有界 | 治理后：**只给模型流式读取**                |
| 工具 RPC 池                      | 项目**自建**的专用池（`TaskConfiguration` 里的 `dynamicToolExecutor` 等）                             | 治理后：**只给工具调用**                  |


关键两点：

1. `boundedElastic` **和"Reactor 共享线程池"在本项目里基本是同一个东西**，不是两个。"Reactor 线程池"也不是特指某一个——Reactor 库自带好几个调度器（`boundedElastic` 给阻塞任务、`parallel` 给 CPU 密集等），本项目出事和治理的都是 `boundedElastic` 这一个。
2. **"共享"和"专用"是相对的**：`boundedElastic` 叫"共享"是因为全局共用、没隔离；模型 SSE 池和工具池叫"专用"是因为项目自建、只给一类活用。本质都是线程池，区别在隔离边界。

所以下面"模型 SSE 池被工具 RPC 占满"这句话的主语是**治理前**那个共用的 `boundedElastic`，不是治理后的模型 SSE 池——治理后的池就是为了不再被占满才建的。

```
治理前：boundedElastic（Reactor 自带，全局共享）
  ├─ 模型 SSE 阻塞读  ← 慢工具把线程占满后，这里排队
  └─ 工具 RPC          ← 一批慢工具把线程占满
  问题：挤一起，工具拖垮模型，静默排队不报错

治理后：拆成两个独立池，互不抢线程
  模型 SSE 池（自建，虚拟线程有界）  ── 只给模型读
  工具 RPC 池（自建）                ── 只给工具调
```



#### 故障与治理

这是上面「阻塞调用甩专用池」原则没做好时的真实后果，也是本项目线程治理的核心案例。

**问题**：AgentScope 框架自带的 `OkHttpTransport.stream(HttpRequest)` 内部写死了 `.subscribeOn(Schedulers.boundedElastic())`，而 `boundedElastic` 这个全局池被本服务所有阻塞型操作共用——模型 SSE 读取 + 各工具 `callAsync` 的 RPC。`boundedElastic` 默认上限是 `CPU*10` 个线程、队列 10 万。一旦一批慢工具 RPC 把线程占满，新的模型 SSE 任务只能在池里**静默排队**（队列不拒绝也不报错），表现为「请求没发出、静默等到外层超时」（代码事实：`IsolatedSchedulerHttpTransport` 类注释，`IsolatedSchedulerHttpTransport.java:32-48`）。

**为什么不能简单包一层**：Reactor 中「最靠近源头的 `subscribeOn` 生效」，外层再包一层 `subscribeOn` 无法把阻塞读取挪走——底层 `client.newCall().execute()` 和 `reader.readLine()` 仍在 `boundedElastic` 上。

**解法**：三层隔离。

1. **复刻并替换传输层** `IsolatedSchedulerHttpTransport`：复刻 `OkHttpTransport.stream` 的 SSE 解析逻辑（复用已配置好的 `OkHttpClient`，超时/SSL/代理不变），只把 `subscribeOn` 换成传入的专用 `Scheduler`。`execute`/`close` 直接委托给原 `OkHttpTransport`。
2. **按 channel 分池** `ModelSseSchedulerRegistry`：`Pool` 枚举绑定渠道与并发上限（如 QN 180、DEFAULT 160），每池建独立 Scheduler + Transport，共享底层 OkHttp 连接池。
3. **Java 21 虚拟线程有界并发** `VirtualThreadSseExecutor`：用 `Executors.newThreadPerTaskExecutor(Thread.ofVirtual().name(poolName + "-virtual-", 0).factory())` 创建，有界语义靠 `Semaphore(concurrencyCap, true)` + 超时（Apollo `model.sse.acquire.timeout.ms` 默认 1000ms）实现，满则 `RejectedExecutionException` 快速失败（代码事实：`VirtualThreadSseExecutor.java:40-49`）。

**工具池另开**：`TaskConfiguration` 进线分发 qn/zz/default 三池 + `dynamicToolExecutor`（35×35 + 队列 1000 + AbortPolicy），同样为了离开 `boundedElastic`，让模型往返与工具 RPC 不再抢同一批线程。

**监控**：`GET /boundedElasticStats` 汇总各池 `activeTasks`/`queuedTasks`/`acquireTimeoutCount`，可观测是否还在排队。

**演进**：`41ddc55f`（`SwitchableSseExecutor` Apollo 灰度切换）→ `3a6b4c39`（删除切换器，全量虚拟有界池）。

**诚实边界**：

- 虚拟线程**只用于 AgentScope 模型 SSE 阻塞读**，不是 Spring `SseEmitter` 出口线程。`SseEmitter` 的写入由 Spring MVC/Servlet 容器线程接管，跟这个池无关。
- 无线上 QPS/延迟前后对比数据，汇报只能讲「治理手段 + 监控口径」，数值需运维补。

### 1.7 容易讲混的两个点

**① Spring** `SseEmitter` **出口线程 ≠ 模型 SSE 阻塞读线程**

这是两条不同的链路：

- **模型 SSE 阻塞读**：AgentScope 调模型时，OkHttp 流式读取模型返回的 SSE，阻塞在 `reader.readLine()`。这是被工具池占满的那个池，用虚拟线程有界池治理。
- `SseEmitter` **出口**：Service 把数据帧写给客户端那条 SSE，由 Spring MVC 容器线程管理。两者不要混成一个。

**②** `ivrAbortCheckExecutor`**（查打断）和模型 SSE 池是两个不同的专用池**

都是「阻塞调用甩专用池」的同一思想，但不是同一个池：

- `ivrAbortCheckExecutor`：热线链路里查 Redis 打断检查的专用池。
- 模型 SSE 池（`ModelSseSchedulerRegistry` 管的虚拟线程池）：模型 OkHttp 流式读取的专用池。

讲「流不是线程」时用查打断举例没问题；讲「SSE 池被工具池占用」时要切到 `IsolatedSchedulerHttpTransport`/`VirtualThreadSseExecutor`，不要把两个池混成一个。

### 1.8 Netty/NIO 与本项目的关系（旁支澄清）

**结论先行**：那个「ThreadLocal 跨 Netty 线程失效 → 写兜底类」的故事是**租车模块（`css-zuche-agent`）**的；V2/IVR（`css-agent-server`）的业务上下文存 Redis 不存 ThreadLocal，**没有这个问题**。V2/IVR 运行时底层会经过 Netty/NIO，但都是框架自带、且不丢上下文；V2/IVR 真正的线程治理点是 1.6 的 OkHttp 阻塞读隔离，**不是 Netty**。

#### NIO、Netty 是什么（通用知识，非本项目特有）

- **NIO** = Non-blocking IO，Java 1.4 的 IO API（`Channel`/`Buffer`/`Selector`）。核心机制：一个线程靠 `Selector` 同时盯多个连接，谁有数据才处理，不用一个连接绑一个线程傻等。这是「少量线程处理大量连接」的基础。
- **Netty** = 基于 NIO 封装的网络框架。核心是 **EventLoop**——一组固定线程，每个负责一批连接的所有事件。网络事件（连接来了、数据到了、连接断了）触发回调，EventLoop 线程被借来执行回调。**EventLoop 线程不能阻塞**，一阻塞它负责的所有连接都卡住。



#### 本项目 HTTP 入口是 Tomcat，不是 Netty（核实事实）

容易误解成「本项目用 Netty 做服务端」，实际不是：


| 项            | 事实                                                                                                                        |
| ------------ | ------------------------------------------------------------------------------------------------------------------------- |
| HTTP 入口      | Spring MVC + **Tomcat**（`spring-boot-starter-web`），热线请求由 Tomcat 线程接                                                       |
| Reactive 栈   | 同时引了 `spring-boot-starter-webflux`（默认 reactor-netty），但 HTTP 入口走 Servlet/Tomcat，webflux 主要作 **reactive 客户端**（`WebClient`）用 |
| 模型 SSE 读     | **OkHttp**（同步阻塞 IO），不是 Netty——这正是 1.6 故障的主角                                                                               |
| pom 里的 netty | 没有直接声明 `io.netty`，是 reactor-netty 的**传递依赖**                                                                               |




#### 两个模块对「上下文存哪」的不同选择

这是理解「为什么租车有 Netty 副作用、V2/IVR 没有」的关键：


|                           | 租车（`css-zuche-agent`）                                     | V2/IVR（`css-agent-server`）           |
| ------------------------- | --------------------------------------------------------- | ------------------------------------ |
| 业务上下文存哪                   | ThreadLocal（`AgentContextHolder`）                         | **Redis**（`ExpertConversationState`） |
| 跨线程怎么处理                   | `Schedulers.onScheduleHook` 传播 + 询价场景 sessionId 静态 Map 兜底 | 天然跨线程，不用处理                           |
| 有没有 Netty ThreadLocal 副作用 | 有（询价场景）                                                   | **没有**（业务上下文不在 ThreadLocal）          |


V2/IVR 的 `ExpertConversationState`（`expert/ExpertConversationState.java`，存 Redis）装的是：当前技能、订单、阶段（ReferenceState）、状态摘要、已执行工具结果、查单白名单、待确认订单、切单前原诉求、版本号等。这些跨多轮、跨线程都要稳定在，所以放 Redis 不放 ThreadLocal。ThreadLocal 在 V2/IVR 只放 `UserContextHolder`（登录用户，同步 Servlet 链路用）和 `TraceIdHolder`（traceId，日志用）这类轻量东西。

#### V2/IVR 运行时经过 Netty 的地方（但不丢上下文）

V2/IVR 链路里 `WebClient`（reactor-netty）做外部调用——知识召回、记忆、语雀文档、沙箱等——响应回调会落到 **Netty event loop 线程**上，和租车一样会经过 Netty 线程切换。区别只在于：V2/IVR 业务上下文在 Redis，不在 ThreadLocal，所以即使经过 Netty 线程也**不会丢上下文，不需要兜底**。

#### 一句话收口

记 V2/IVR 时，把 Netty/NIO 那段当**租车的旁支**：V2/IVR 的业务上下文在 Redis，ThreadLocal 只放登录用户和 traceId，没有 ThreadLocal 跨 Netty 丢失的问题；V2/IVR 真正要操心的线程治理点是 1.6 的 OkHttp 阻塞读 + `boundedElastic` 隔离，跟 Netty/NIO 无关（OkHttp 是阻塞 IO）。

### 1.9 面试可能的追问

**Q：为什么不直接给** `boundedElastic` **调大？**
调大只延缓不解决：慢工具 RPC 数量不固定，池再大也可能被打满，且 `boundedElastic` 队列 10 万不拒绝，问题仍是静默排队而非快速失败。隔离 + 有界 + 快速失败才能让故障可见、可治。

**Q：虚拟线程为什么适合这个场景？**
模型 SSE 阻塞读是典型「大量阻塞、少 CPU」的 IO 密集任务，虚拟线程轻量、按需创建，阻塞时不占平台线程，适合承载大量并发阻塞读；配 `Semaphore` 做有界，满时快速失败而不是无限排队。

**Q：承接超时为什么不会拖垮主回复？**
承接流所有失败路径（超时/异常/不合规/取消）都被 `onErrorResume` 转成 `Flux.empty()`，对下游是正常 `onComplete`；`Flux.concat(bridgeStream, orderedMain)` 在承接流 `onComplete` 后立刻订阅主流，所以承接空流完成 → 主流立即开始，主 LLM 不会因承接超时断掉。

**Q：**`subscribe` **之后线程去跑别的流，跑的是什么的流？**
跑别的请求的流。Reactor 线程池服务多个请求，A 请求等结果时线程还回池子，能被借去跑 B 请求的 `merge`/`flatMap`。一个池服务很多请求，靠「等结果时线程还回去」实现高并发。

## 第 2 部 V2 编排：上下文怎么裁、工具怎么预取



### 2.1 这部要讲清什么

V2 编排模式（`css-agent-server` 的 `expert/` 包）的核心约束是：业务 Agent 每轮拿到的不是全量信息，而是工程按当前办理阶段裁好的有限切片。这部讲两件事——**上下文是怎么装配出来的**，以及**为什么它不会随对话无限长起来**。

两个核心结论：

1. **上下文装配**：模型每轮看到的是「当前阶段对应的一段说明 + 当前阶段能调的一批工具 + 仅在记忆重置时补入的最近对话」。当前处于哪个阶段由工程侧确定性状态机决定（存在会话缓存里），模型不自己判断阶段。工具预取发生在模型推理之前，把入参已确定的查询提前跑掉，结果既喂给模型也写进状态机台账。
2. **上下文不膨胀**：V2 没有用「调模型把长对话总结成短摘要再塞回去」这种压缩。它靠分作用域隔离（记忆按技能+订单隔开，换就清）+ 每个作用域内设硬上限（对话 6 轮、工具 20 个、单条 4000 字符、摘要 160 字），从源头不让上下文长起来。这些都是常数时间裁剪，不调模型，不引入摘要本身的幻觉风险。

下面先看一轮里上下文怎么装配（2.2），再看让它不膨胀的具体裁剪点（2.3），最后看工具预取这条数据面准备链（2.4）。

---



### 2.2 一轮上下文是怎么装配出来的

先说清几个容易混的术语，再走流程。

- **state（阶段）**：一个技能的办理流程被切成若干阶段，比如退款技能是 `CONFIRM → SOLUTION → EXECUTE`。每个阶段绑定一段说明和一组允许调用的工具。当前停在哪个阶段叫「当前 state」。
- **reference 文档**：**技能**的办理说明，按 state 切段存。不是一整篇，是每 state 一段。
- **Memory**：业务 Agent 的多轮对话记忆，用独立 namespace 隔离。换技能或换订单时会清空重来。
- **会话状态缓存**：存在 Redis 里的跨轮状态（`ExpertConversationState`），装当前技能、订单、阶段、已执行工具结果、最近对话等。Memory 清空不影响它。

一轮的装配流程（谁触发 → 输入什么 → 决定什么 → 产出什么 → 喂给模型）：

```
用户消息进来
  │
  ▼
读会话状态缓存 ── 取出上一轮已提交的阶段、订单、工具结果
  │
  ▼
路由 Agent 提议 ── 选哪个技能 + 进/停/重来（不带多轮上下文，只看工程注入的决策上下文）
  │
  ▼
工程状态机落定 ── 以缓存里的阶段为起点，结合订单和工具历史结果，决定本轮 state
  │
  ├─▶ 按 state 切段取 reference 正文（只取当前那段）
  ├─▶ 按 state 叠加工具集（通用 + 当前 state 专属）
  ├─▶ 决定 Memory namespace（换技能/订单/重来则换 namespace）
  │     └─ 换了 namespace → 补注入 carryOver（最近对话 + 工具历史）
  └─▶ 同步预取工具（入参已确定的查询，见 2.4）
  │
  ▼
把以上切片注入业务 Agent 输入 ── 模型按当前阶段说明和工具组织回复
  │
  ▼
本轮成功后回写缓存（乐观锁校验版本号）
```

模型每轮实际拿到的是这条流程末端的切片，不是全量。下面逐项说明每样东西的取法和边界。

**① reference 正文：当前 state 对应的那一段**

reference 文档在配置里按 state 切段存，取法是两步查表：

- `references`：`state → path` 的映射，由 `SkillReferenceRegistry.resolve` 按 stateFlow 顺序建好（`SkillReferenceRegistry.java:20-45`）
- `resources`：`path → 内容` 的映射，存每一段正文

运行时先用当前 state 查 `references` 拿 path，再用 path 查 `resources` 拿内容，放进 `ExpertExecutionPlan.referenceContent`（`ConversationOrchestrator.java:300-310`）。path 找到了但内容为空时直接抛 `IllegalStateException`，不静默给模型一段空话。

举例：退款技能 stateFlow 是 `CONFIRM → SOLUTION → EXECUTE`，每个 state 绑一段说明。停在 `SOLUTION` 时模型只看到「给方案阶段」那一段，推进到 `EXECUTE` 才换看到「执行阶段」那段。

**② 工具集：通用工具 + 当前 state 专属工具**

`SkillToolConfigResolver.resolve(source, referenceState)`（`SkillToolConfigResolver.java:25-50`）：先放通用工具（所有阶段都能用），再叠当前 state 专属工具，state 级配置按 toolCode 覆盖通用配置。模型这轮只能看到这批工具。

这是「间接限制」——决定模型能看见什么，不是拦它调什么。真正拦执行的是另一个 Hook（一轮最多一个操作类工具），那是硬限制，不在上下文这条线上。

**③ carryOver：只在 Memory 重置时才补**

业务 Agent 的 Memory 用独立 namespace（`AgentCreateOptions` 注释「Expert 模式使用独立共享 namespace」）。state action 是 `RESET`/`RESTART` 时 Memory 清空、换 namespace，模型这轮看不到任何历史消息，这时工程补注入 `ExpertCarryOverContext`（`ConversationOrchestrator.java:340-348`）：

- 最近几轮对话（从会话状态缓存取，不从 Memory 取，因为 Memory 已清）
- 当前订单已执行的工具历史

判断条件：`memoryReset = !memorySessionId.equals(fallbackMemorySessionId)`。沿用同一 namespace 时**不注入**，因为历史已在 Memory 消息链里，再注入会让同一段话出现两次。

**④ 会话参数**

`buildOrderSessionParam` 把订单相关参数放进 `sessionParam`，供工具预取和模型用。

### 2.3 上下文为什么不无限长：6 个确定性裁剪

结论：V2 不用模型做对话摘要压缩，靠工程侧确定性裁剪从源头控制上下文体量。6 个裁剪点散在状态机和台账里，下表按「作用域隔离」和「作用域内硬上限」两类归纳。

**作用域隔离——换就清，不累积**


| 裁剪点                | 机制                 | 触发条件                                           | 代码定位                                               |
| ------------------ | ------------------ | ---------------------------------------------- | -------------------------------------------------- |
| Memory 换 namespace | 清空记忆，模型这轮看不到任何历史消息 | state action 为 `RESET`/`RESTART`（换技能、换订单、推倒重来） | `AgentCreateOptions` 注释「Expert 模式使用独立共享 namespace」 |
| stateSummary 清空    | 上一轮摘要清成 null，不跨流程带 | 换技能或换订单（非「同技能同订单」）                             | `ConversationOrchestrator.java:322-325`            |


**作用域内硬上限——沿用同一 Memory 时兜住体量**


| 裁剪点          | 上限      | 怎么裁                                  | 代码定位                                                     |
| ------------ | ------- | ------------------------------------ | -------------------------------------------------------- |
| 最近对话         | 6 轮     | 每轮 `appendDialogue` 后 `trimHead` 从头删 | `ConversationOrchestrator.java:49, 1411-1417, 1514-1517` |
| 工具台账条数       | 20 个工具  | 按 `toolCode` 去重只留最新一次                | `ExecutedToolHistory.java:36-40`                         |
| 工具单条输出       | 4000 字符 | 超过 `substring(0, 4000) + "...(截断)"`  | `ExecutedToolHistory.java:296-303`                       |
| stateSummary | 160 字   | 上一轮回复截到 160 字，前缀加 state 名            | `ConversationOrchestrator.java:1520-1531`                |


**两个额外的污染防护**

- **预取结果脱敏**：预取调用会在 Memory 消息链留等位，入参含手机号、Token。`PrefetchHistoryInvalidator.isPrefetchCallId` 把这些从 `fromMemory` 路径排除，只走 `fromPrefetch` 那条已脱敏来源（`getModelIdentityInput()` 只保留身份字段），避免敏感信息长期占上下文位（`ExecutedToolHistory.java:181-188`）。
- **max token 兜底**：模型因达到最大输出 Token 终止时，`MaxTokensFallbackHook` 把半截回复替换成固定短话术再写进 Memory，不让被截断的半句话污染后续轮次（`MaxTokensFallbackHook.java:31-60`）。

**和「LLM 摘要压缩」的区别**

「对话太长，调一次模型把前面 N 轮总结成一段短摘要再塞回去」这种机制，V2 里没有。V2 的思路是**从源头不让上下文长起来**：分作用域隔离 + 每个作用域内设硬上限。这些都是常数时间裁剪，不调模型，不丢精度，也不引入摘要本身的幻觉风险。真正的「从零开始」靠 Memory 换 namespace——换技能、换订单、推倒重来都走这条。

---



### 2.4 工具预取：模型推理前的数据面准备

**为什么预取**

有些查询工具的入参在模型推理前就已确定（比如订单号已在会话上下文里）。如果等模型推理时自己调，要多一轮模型-工具往返，首 token 延迟高，模型也可能漏调、错调。预取把这些「入参已确定、迟早要查」的查询提前跑掉，模型推理时直接拿结果。

预取不替代模型调用：模型推理时还能调没预取过的工具；被预取过的工具，模型再调同一个，结果以预取的为准（进台账后同名取新），不重复查接口。

**预取哪些工具**

判定依据是工具配置里的 `requirePrefetchFields`（必填字段，`DynamicApiTool.java:125, 170`）。预取时用 `findMissingRequiredFields` 检查这些字段，会话上下文已经能填齐必填字段的工具才被预取；缺了就跳过这个工具并记日志（`DynamicApiTool.java:334-340`）。

**待确认**：哪些工具实际被配了 `requirePrefetchFields` 取决于各技能的配置数据，本文未逐个核实配置；面试被追问具体工具名时需补查技能配置。

**怎么执行**

预取发生在 Agent 构建期，是同步的——注释明确「工具预取在 Agent 构建期同步执行，这段耗时直接计入首 token」（`AgentChatV2Component.java:928`）。预取「没有 LLM 动态传参，只依赖会话上下文参数 + 工具配置中的固定参数」（`DynamicApiTool.java:329-331`），入参合并规则是 context → configured → preset（`DynamicApiTool.java:352-357`）。

`DynamicApiTool.prefetch(sessionContext)` 逐个工具执行（`DynamicApiTool.java:332-347`）：合并入参 → 检查必填字段 → 调接口 → `buildPrefetchResult` 把原始返回转成模型可见快照并算 status。

预取结果的 status 分档：


| status             | 含义   |
| ------------------ | ---- |
| `RESULT_AVAILABLE` | 有数据  |
| `EMPTY`            | 空返回  |
| `BUSINESS_FAILED`  | 业务失败 |
| `TOOL_ERROR`       | 工具异常 |


**结果去哪**

预取结果（`PrefetchResult` 列表）有两条去路：

1. **进工具台账，和模型发起的调用合并**。`ExecutedToolHistory.collect` 从两个来源取（`ExecutedToolHistory.java:52-65`）：Memory 消息链里模型发起的调用（`fromMemory`）和工程侧预取结果（`fromPrefetch`）。合并时同名工具以本轮工程侧预取的新鲜结果为准（`ExecutedToolHistory.java:54-55`）。这个台账给状态机用——下一轮状态机判断能不能推进阶段，看的就是台账里工具执行成功还是失败。预取调用在 Memory 留的等位（入参含手机号、Token）被 `PrefetchHistoryInvalidator.isPrefetchCallId` 从 `fromMemory` 排除，只走已脱敏的 `fromPrefetch`（`ExecutedToolHistory.java:181-188`）。
2. **作为耗时观测**。`buildAgentBuildStep` 把预取工具数量和构建耗时打成思考步骤暴露给前端，标题「Agent 构建与工具预取」（`AgentChatV2Component.java:1607-1620`）。因为预取是同步的、计入首 token，单独拆出来才能判断是预取拖慢了还是模型推理拖慢了。

---



### 2.5 边界与待确认

- **预取工具配置未逐个核实**：哪些工具配了 `requirePrefetchFields` 取决于技能配置数据，本文只核实了判定机制，未核实具体工具清单。
- **无线上定量数据**：预取对首 token 延迟的实际改善、上下文裁剪的实际节省量，均无线上数据，面试只能讲机制和观测口径。
- **适用范围**：本部只描述 V2 编排模式（`expert/` 包），不涉及其他模块的 Skill 运行时。



### 2.6 面试可能的追问

**Q：为什么不直接让模型自己决定调什么工具，要工程预取？**
模型自己调要一轮模型-工具往返，首 token 延迟高，且模型可能漏调、错调。预取把入参已确定的查询提前跑掉，模型推理时直接拿结果，既省一轮往返又压低首 token。但预取只挑入参已确定的，模型动态生成的入参还得模型自己调。

**Q：预取结果和模型实时调用结果冲突时听谁的？**
同名工具以本轮工程侧预取的新鲜结果为准（`ExecutedToolHistory.java:54-55`），旧结果被覆盖，不重复占位。模型再调同一个被预取过的工具，结果以预取的为准，不会重复查接口。

**Q：reference 为什么按 state 切段而不是整篇给模型？**
整篇给模型会出现跳阶段、复述错误当前阶段（状态幻觉），话术和工具与实际进度错位。按 state 切段，模型每轮只看到当前阶段那一段说明 + 当前阶段能调的工具，配合工程状态机确定当前在哪个 state，从源头限制模型的活动范围。

**Q：换技能/换订单时旧上下文怎么办？**
Memory 换 namespace 直接清空（不是压缩），模型从零开始；但原诉求进切单前暂存为独立字段（`pendingResumeMessage`），切单成功后下一轮自动接回，用户不用重说。历史对话存在会话状态缓存里，Memory 清空不影响它，下一轮从缓存取出来注入业务 Agent 输入。

**Q：你说没有 LLM 摘要压缩，那对话特别长怎么办？**
V2 靠硬上限兜：最近对话只留 6 轮、工具台账 20 个上限且按 toolCode 去重、单条工具输出 4000 字符截断、stateSummary 160 字。这些是常数时间裁剪，不调模型。真正的「从零开始」靠 Memory 换 namespace——换技能、换订单、推倒重来都走这条，不累积。

## 第 5 部 V2 Hook：模型过程怎么采集、怎么送到前端

### 5.1 一句话主线

V2 采用「**外层编排手工记录 + Agent 内部 Hook 采集**」的混合方案：路由、状态机、Agent 构建等外层阶段由编排代码记录；模型的多轮推理和工具执行发生在 `ReActAgent` 内部，外层看不到，因此通过 `ThinkingProcessHook` 监听 Agent 生命周期事件。

最容易混淆的三个对象，先记住它们的关系：

```
ThinkingProcessHook = 观察 Agent 内部事件的组件
sink                = Hook 写入 ThinkingStep 的入口
thinkingFlux        = 外界读取这些 ThinkingStep 的出口
```

`thinkingFlux` 不是业务代码凭空创建的第二套思考过程，它就是 `ThinkingProcessHook` 内部通道的读端。

---

### 5.2 为什么不全写在 V2 编排代码里

V2 外层编排能直接看到：

```
路由开始/结束
状态机计算完成
业务 Agent 开始/结束
Agent 构建与工具预取耗时
```

但是，外层只是调用 `agent.call(...)` 或 `agent.stream(...)`，看不到 `ReActAgent` 内部发生的：

```
第 1 次调模型
  → 模型决定调查单工具
  → 工具执行
第 2 次调模型
  → 模型根据工具结果继续推理
  → 生成回复
```

如果不用 Hook，就必须修改或包装 `ReActAgent` 内部的每次模型调用和工具调用。Hook 是框架预留的统一扩展点：Agent 运行到某个节点时发出 `HookEvent`，Hook 把事件转换成可观测步骤。

因此项目里不是「全用 Hook」，而是按事件所处层次分工：

- Agent 内部事件：`ThinkingProcessHook` 采集。
- Agent 外部阶段：编排代码手工记录。例如工具预取在 Agent 构建期完成，不在 Agent 推理生命周期里，所以 `AgentChatV2Component.buildAgentBuildStep` 手工生成「Agent 构建与工具预取」步骤。

---

### 5.3 Hook 怎么变成 `thinkingFlux`

#### 第一步：Hook 内部创建一条通道

`ThinkingProcessHook` 的构造方法创建 `sink`，再用 `sink.asFlux()` 取得同一条通道的读端（`ThinkingProcessHook.java:89-96`）：

```java
this.sink = Sinks.many().unicast().onBackpressureBuffer();
this.flux = sink.asFlux();
```

Agent 运行时，框架把 `PreReasoningEvent`、`PostActingEvent` 等事件交给 `hook.onEvent(event)`。Hook 把事件转成 `ThinkingStep`，最后通过 `sink.tryEmitNext(step)` 写入通道（`ThinkingProcessHook.emit`）。

#### 第二步：将 Hook 挂到 Agent，并暴露读端

`HookComponentResolver.resolve` 中（`HookComponentResolver.java:200-204`）：

```java
ThinkingProcessHook hook = new ThinkingProcessHook(context.getSkillNames());
context.getBuilder().hook(hook);
context.getBuilder().hook(new FinalModelInputHook(hook));
context.setThinkingFlux(hook.flux());
context.setThinkingProcessHook(hook);
```

这四行分别是：创建 Hook → 挂载到 Agent → 将 Hook 的读端放进构建上下文 → 保留 Hook 引用供结束时关闭。

#### 第三步：跟 Agent 一起返回

`RealtimeAgentFactory.create()` 构建的 `AgentCreateResult` 同时携带（`RealtimeAgentFactory.java:289-300`）：

```
created
├── agent                 ReActAgent 实例
├── thinkingProcessHook   挂在该 Agent 上的 Hook
└── thinkingFlux          该 Hook 内部通道的读端
```

所以 `created.getThinkingFlux()` 的准确含义是：**从 Agent 创建结果中取出已挂载 Hook 的输出通道**。

完整生产链是：

```
Agent 内部产生 HookEvent
  → ThinkingProcessHook.onEvent()
  → 转换成 ThinkingStep
  → sink.tryEmitNext(step)
  → thinkingFlux 向订阅者输出 ThinkingStep
```

---

### 5.4 Hook 实际采集什么

`ThinkingProcessHook` 主要将 AgentScope 生命周期事件映射成以下步骤（`ThinkingProcessHook.onEvent`）：

- `PreReasoningEvent` → `reasoning_start`：一轮模型推理开始。
- `ReasoningChunkEvent` → `reflection`：提取显式 `ThinkingBlock` 增量，按 100 字符或 250ms 微批发送。
- `PostReasoningEvent` → `model_usage`：采集 token 用量，并识别本轮是否产生工具调用。
- `PreActingEvent` → 记录工具开始时间，当前实现不单独发 `tool_call` 步骤。
- `PostActingEvent` → `tool_result` / `tool_error`：记录工具参数、结果、耗时及并行组。
- `PreSummaryEvent` / `PostSummaryEvent` → 记录 ReAct 达到迭代上限后的额外收尾模型调用。这里的 Summary 是生成最终回复，不是压缩会话历史。
- `ErrorEvent` → `error`：记录 Agent 错误。

`FinalModelInputHook` 和 `ThinkingProcessHook` 共用同一条输出通道，在 `PreReasoningEvent` 时补充「最终送模消息、工具 schema、生成参数」。它的 priority 是 210，故意晚于 `ThinkingProcessHook` 的 200 执行；代码注释明确说目的是「尽量采到最终版本」（`FinalModelInputHook.java:52-55`）。两个 Hook 各有自己的迭代计数器，排序依赖是为了同一次事件的采集时机，不是共享计数器。从实现上看，将最终送模快照拆成独立 Hook，让它可以单独设置这个执行顺序。

**边界**：这采集的是框架事件和模型显式返回的 `ThinkingBlock`，不是读取模型不可见的隐藏思维。

### 5.5 路由 Hook：实时采集，结束后回放

V2 每轮会先调路由 Agent，用它选 Skill 并给出状态流转建议。`ConversationOrchestrator.prepareForStream()` 先创建：

```java
List<ThinkingStep> routerThinkingSteps = new ArrayList<>();
```

调用 `ExpertRoutingAgent.route(...)` 时，明确把 `routerThinkingSteps::add` 作为 `thinkingConsumer` 传入（`ConversationOrchestrator.java:179-186`，方法调用始于 `:179`，方法引用在 `:186`）。路由 Agent 创建后订阅自己的 `thinkingFlux`：

```java
created.getThinkingFlux().subscribe(thinkingConsumer, errorConsumer);
```

因此路由侧的实际数据方向是：

```
路由 Agent 内部事件
  → 路由 ThinkingProcessHook
  → 路由 thinkingFlux
  → thinkingConsumer
  → routerThinkingSteps.add(...)
```

路由调用使用 `created.getAgent().call(input)...block()`，要等完整的 `RouterIntentDecision` 返回后，工程状态机才能选定 Skill、阶段和工具集。路由结束后，`StreamPreparation` 将执行计划和 `routerThinkingSteps` 一起带回。

`AgentChatV2Component.executeStream()` 才按顺序输出：

```
config 帧
  → 已缓存的路由思考步骤
  → Agent 构建/预取耗时步骤
  → 业务 Agent 思考流与正文流
```

所以路由是「**Hook 产生时就被采集，但采集结果先进 List，没有直接接到 SSE**」。`buildRouterThinkingStream` 只在路由完成后把 List 重新转成 Flux 并回放（`AgentChatV2Component.java:1626-1634`）。

这种实现的实际价值是**事后调试**：可以查看路由模型收到什么、为什么选中某个 Skill、token 和耗时如何，同时保证前端先看到路由过程、再看业务过程。它不是实时进度条。

**设计推断**：代码注释称这是「简单方案」，说明并非技术上必须缓存。完全可以把路由 Hook 的输出通道直接合并进最外层 SSE，同时让最终路由决策继续交给状态机。当前方案换取了接线简单、展示顺序稳定，代价是失去路由阶段的实时可见性。`call(...).block()` 只能证明业务 Agent 必须等路由结果，不能证明路由思考无法实时发送。

### 5.6 业务 Hook：与正文流实时汇合

业务 Agent 也有自己独立的 `ThinkingProcessHook`，不与路由 Agent 共用 Hook 实例。`executeStream()` 创建业务 Agent 后，从 `AgentCreateResult` 取出 Hook 的读端，将 `ThinkingStep` 转成 SSE 使用的 JSON 字符串（`AgentChatV2Component.java:1052-1054`）：

```java
Flux<String> thinkingStream = created.getThinkingFlux() != null
        ? created.getThinkingFlux().map(this::toThinkingJson)
        : Flux.empty();
```

`thinkingFlux == null` 不是异常，而是完整可视化 `ThinkingProcessHook` 没有创建时的正常结果：例如非 TEST 渠道，或 TEST 渠道显式关闭 `enableThinkingProcess`。此时使用 `Flux.empty()` 作为「不产生任何思考事件、直接正常完成」的占位流，后面的 `merge` 实际上只转发正文 `contentStream`。这就是 5.7 中「Hook 未创建」在业务输出侧的直接表现。

`map(this::toThinkingJson)` 不生成新的思考，只是转换元素格式：

```
ThinkingStep Java 对象
  → {"type":"thinking", ...} JSON 字符串
```

同时，`agent.stream(...)` 产生给用户的正文 `contentStream`。两条流的分工是：

```
thinkingStream = Hook 采集的调试/可观测事件
contentStream  = 业务 Agent 生成的正式回复
```

`Flux.merge(thinkingStream, contentStream)` 不是把两段文字拼起来，而是同时订阅两条流，哪条先产生事件就先向下游发那个事件。例如：

```
10ms thinkingStream → {"type":"thinking","step":"reasoning_start"}
30ms thinkingStream → {"type":"thinking","step":"tool_result"}
50ms contentStream  → {"type":"content","data":"已经为您查到订单"}
```

前端根据 `type` 将 `thinking` 放进调试面板，将 `content` 放进正式回复区。业务正文流结束时，`contentStream.doFinally` 调用 `thinkingHook.complete()` 关闭 Hook 的 sink，否则 `merge` 会继续等待尚未结束的思考流，整条 SSE 不能正常完成。

### 5.7 真实 IVR 为什么没有可视化思考流

先分清两类用途：

- `ThinkingLogHook`：轻量内部埋点，受 Agent 级 `enableThinkingProcess` 开关控制（未配置时默认为 `true`）。它在非 TEST 渠道的提前 `return` 之前注册，因此开关开启时，非 TEST 渠道也会挂载（`HookComponentResolver.java:131-138`）。
- `ThinkingProcessHook`：本部讲的完整可视化 Hook，会产生 `thinkingFlux` 供前端展示。

挂载完整 `ThinkingProcessHook` 必须同时满足：

```
channel == TEST
&& agentConfig.enableThinkingProcess == true
```

`HookComponentResolver` 先在非 TEST 渠道直接 `return`（`HookComponentResolver.java:167-169`）；进入 TEST 后还要通过 `enableThinkingProcess` 二级开关（`:193-204`），才创建 `ThinkingProcessHook` 和 `thinkingFlux`。

因此真实 `IVR_HOSTING` 的因果链是：

```
非 TEST 渠道
  → ThinkingProcessHook 根本不创建
  → AgentCreateResult.thinkingFlux = null
  → 不存在可合并到 SSE 的完整思考流
```

`AgentChatV2Component.streamWithNonBizIntent()` 固定先发 `{"type":"config","enableThinkingProcess":false}`，只是保持 SSE 首帧协议一致、告诉消费端本轮没有可视化思考。**它是协议表现，不是关闭思考流的根因；根因是 `ThinkingProcessHook` 没有创建。**

---

### 5.8 面试表达

> V2 对模型过程的采集是外层手工埋点与 Agent 内部 Hook 的混合方案。`ThinkingProcessHook` 监听 `ReActAgent` 的推理、工具执行和收尾事件，将 `ThinkingStep` 写入 sink，`thinkingFlux` 是同一条通道的读端。路由 Agent 的读端被接到 List，因此在路由完成后回放；业务 Agent 的读端则直接与正文 Flux 合并，所以可以实时交错输出。路由缓存回放是当前的简化接线，不是技术限制。完整可视化 Hook 只在 TEST 且 `enableThinkingProcess=true` 时创建；真实 IVR 没有这条 `thinkingFlux`，固定的 `enableThinkingProcess=false` 配置帧只是协议声明。
