# 面试稿：会话编排 + 状态机 + 订单切换

一句话主线：模型提议进、停或重来，工程对照缓存、订单和工具结果，决定本轮打开哪个阶段。

枚举名（`HOLD`/`NEXT`/`RESTART`、`RESET`/`CONTINUE`/`ADVANCE`/`RESTART`/`NONE`）只在第 5 节出现，前几节用「进、停、重来」和「阶段」。

---

## 1. 业务为什么需要这个系统

客服办理一笔订单要分阶段：先确认订单和诉求，再给方案、说明代价，最后才真正执行动作。每个阶段绑定一段办理说明和一组允许调用的工具，只有走完当前阶段才能进入下一阶段。

系统有两种模式。

**普通模式**：模型一次拿到全部技能、全部阶段的办理说明和全部工具，自行选择技能、自行判断当前处于哪个阶段、自行选择工具。问题在于模型无法稳定保证只走当前阶段、只调用当前阶段允许的工具，会出现跳阶段、调用错误工具的情况，并且会复述错误的当前阶段（状态幻觉），导致话术和工具与实际进度错位。

**编排模式**：路由模型负责提供技能选择和状态流转建议，工程侧负责验证、约束并确定最终生效的阶段和工具配置。其中"当前处于哪个阶段"由一个工程侧确定性状态机管理：当前阶段存储在会话缓存中（上一轮成功后写回），路由模型每轮仅提议对当前状态的操作：推进、保持或重来，状态机以缓存中的当前阶段为起点，结合当前订单和已执行工具的历史结果，决定本轮处于哪个阶段。确定性体现在：对于给定的路由结果、缓存状态、订单和工具结果，状态转换规则是确定的，而不是整个过程完全不依赖模型。模型仅保留一项自由度：按当前阶段的办理说明和工具，组织给用户的回复。

编排模式解决的核心问题是普通模式中模型自行管理状态、自行选择工具的不可控性，用工程侧确定性状态机替代模型自管状态，防止状态幻觉。

## 2. 系统实际怎么工作

### 一轮的流程

1. 用户话进来，读会话缓存。缓存里只有上一轮已成功提交的阶段和订单，没有就空。
2. 路由模型在候选技能里选一个，并提议推进、保持或重来。它不使用框架自动累积的会话历史，但工程将历史对话、当前意图、当前技能、当前阶段和上一轮状态摘要显式注入它的输入，作为决策上下文。路由模型不输出当前阶段，只输出技能选择和状态流转建议。
3. 工程以缓存中的已提交阶段为起点，结合当前订单和已执行工具的历史结果，决定本轮处于哪个阶段。这里的历史结果是上一轮成功结束时写回缓存的，不是本轮的——本轮还没开始调工具。如果当前已提交阶段绑定的工具在上一轮执行失败或业务校验失败，模型的推进建议降级为保持，留在当前阶段让模型重新处理。
4. 工具随当前阶段给定：先放通用工具，再叠当前阶段专属工具。
5. 业务模型按当前阶段的办理说明和工具回复用户。
6. 这轮成功结束后回写缓存（包括本轮工具执行结果，供下一轮状态机检查），回写前先校验版本号：比对这轮开始时的版本和当前缓存版本，一致才回写，不一致说明中间已有别的轮写过，放弃这次回写。计划生成时不提前写，避免中途失败造成进度超前。

### 订单切换

换技能或换订单，从新流程的第一阶段重新开始。状态按技能和订单隔开，每个技能 + 订单组合独立存。

模型可以提议换成另一笔订单，但订单号必须来自查单工具刚返回的结果。工程从工具输出里抽出订单号维护一个白名单，模型提议的目标必须精确命中白名单才切，对不上就拦掉，请用户再补充信息。

切成后清掉旧订单的技能进度、工具结果和白名单；业务 Agent 的 Memory 也清空。历史对话存在会话状态缓存里，Memory 清空不影响它，下一轮从缓存取出来注入业务 Agent 输入，让上下文不断得太干净；原诉求下一轮自动接回，用户不用从头说。工具结果不注入，因为属于旧订单作用域，带入新订单会污染。

## 3. 关键技术为什么这样选

**为什么不让模型管状态。** 状态机的当前阶段只读会话缓存里已提交的值，模型每轮只提建议，由工程落定。原因是模型会复述错误的当前阶段（状态幻觉），说错后话术和工具跟着错位，用户会以为事情已经办完。

**为什么用乐观锁而不是悲观锁。** 回写缓存时用版本号做乐观校验，版本不一致就放弃回写。原因是同一会话两轮重叠是少见情况，不是常态。悲观锁会让正常路径为少见情况常驻代价；乐观锁在正常路径不需要持锁等待，只在真重叠时丢掉慢的那轮。

**为什么用查单白名单而不是放开切单。** 切单时模型提议的目标订单必须精确命中工程从查单工具结果里维护的白名单，对不上就拦截。原因是模型会编造订单号，放开切单会把流程带到一笔不存在的订单上。白名单只收工具结果里真实出现过的订单，把编造的订单号挡在外面。

**为什么暂存原诉求再接回。** 进入切单前把用户原诉求另存为独立字段，切单成功后下一轮自动接回。原因是切单会清掉旧订单的技能进度，原诉求会一起丢失，不暂存用户切完单得再说一遍。

## 4. 工程难点

- **状态幻觉**：模型复述错当前阶段。后果：话术和工具全错位，用户误以为已办妥。解法在上一节。
- **并发覆盖**：同一会话两轮重叠，慢的那轮回写会盖掉快的那轮的新进度。后果：进度回退、订单记错。解法：乐观锁，版本过期放弃回写。
- **模型乱切单**：模型输出切到一笔没查过的订单。后果：流程带到不存在的订单。解法：查单白名单精确校验，对不上拦截。
- **切单丢原诉求**：切单清进度时原诉求一起没。后果：用户要重说。解法：进切单前暂存为独立字段，切成后接回。用独立字段（模型输出）而不是对话历史，因为对话历史是多轮列表不明确哪句是原诉求，且需要标志控制续接时机。
- **中途失败**：路由失败、技能装配失败、Memory 没存上，都发生在这一轮办到一半时。后果：进度被一次失败推前，下一轮从错的地方开始。解法：三类失败各有降级回到主模型，且都不拿失败轮去推进阶段。

## 5. 追问回答

这一节才出现枚举名，前面用不到。

**第一轮为什么从第一阶段开始。** 缓存为空时没有已提交的技能和订单，状态机直接返回 `RESET`，落到这个技能流程的第一阶段。模型这一轮的进/停/重来不参与翻阶段，因为没有已提交的阶段可翻。

**什么情况下模型的「进」不生效。** 两种：已经是流程最后一个阶段，再进也停在原地，结果记成 `CONTINUE` 而不是 `ADVANCE`；或者当前阶段绑定的工具在上一轮已执行的结果是工具执行失败 / 业务校验失败，编排器先把建议改成保持，阶段停住。注意这里看的是上一轮写回缓存的历史工具结果，不是本轮的——本轮还没开始调工具。

**查单白名单怎么拦。** 从本轮列表查单工具输出里抽出订单号进白名单，上限 40 条。模型的目标订单必须精确命中白名单；漏传目标且本轮只有唯一一笔查单时，用那笔补上。对不上就丢掉这次切单，回固定话术。

**工具可见性和执行拦截是两件事。** 可见性是按当前阶段叠加工具集，决定模型能看见哪些工具，是间接限制。执行拦截是在执行前保证一轮最多一个操作类工具，多余的工具调用删掉，是硬限制。状态机本身只管翻到哪个阶段，不直接拦执行。

**版本回写。** 计划生成时记下当时的缓存版本。回写前再读一次缓存，版本对不上就整轮放弃回写，并清掉这次还没提交的 Memory。

**Memory 什么时候清空。** `RESET` 和 `RESTART` 时 Memory 清空，下一轮新建；`CONTINUE` 和 `ADVANCE` 沿用原来的。所以换技能、换订单、推倒重来都让业务模型从新 Memory 开始，历史对话存在会话状态缓存里，下一轮从缓存取出来注入业务 Agent 输入，不是完全空白。
