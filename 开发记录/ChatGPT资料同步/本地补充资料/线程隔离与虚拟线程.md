# 前置基础：Servlet、OkHttp、Reactor 通俗讲解 + 对比

## 一、Servlet

### 是什么

**Servlet 是 Java EE 里，运行在服务端（Tomcat/Jetty）用来接收、处理 Web 请求的后端技术。**

> 属于**服务端（Server）** 技术

### 核心作用

浏览器/客户端发 HTTP 请求 → Tomcat 把请求交给 Servlet → Servlet 执行业务代码、返回响应给客户端。

- 协议：基于 **HTTP**
- 运行位置：**服务器（Tomcat）**
- 典型流程：
  1. 客户端浏览器发起 GET/POST 请求
  2. Tomcat 接收请求，转发到对应 Servlet
  3. Servlet 获取参数、查询数据库、处理业务
  4. Servlet 通过 `response` 返回结果（html/json）

### 简单代码示例

```java
public class HelloServlet extends HttpServlet {
    @Override
    protected void doGet(HttpServletRequest request, HttpServletResponse response) {
        response.getWriter().write("hello world");
    }
}
```

> 现在 SpringMVC/SpringBoot 的 `@Controller` 底层本质还是 Servlet。



### 异步 Servlet（SseEmitter）—— 本项目的关键

本项目 SSE 接口用的不是普通 Servlet，而是**异步 Servlet**。普通 Servlet 处理时一直占着 Tomcat 的工作线程，直到响应写完；异步 Servlet（`AsyncContext` / `SseEmitter`）允许 Servlet 线程把活儿交出去、立刻归还，后续由别的线程往客户端推数据，写完再收尾。**这是后面「往客户端写不占线程」的关键。**

## 二、OkHttp



### 是什么

**OkHttp 是 Square 开源的 Java / Android HTTP 客户端工具库。**

> 属于**客户端（Client）** 工具



### 核心作用

让你的 Java 程序**主动去调用别人的 HTTP 接口**，发送 http 请求，拿到返回数据。相当于用代码实现一个"浏览器"，去请求别的后端服务。

- 运行位置：你的应用（客户端）
- 能力：发送 GET、POST、上传文件、设置请求头、超时控制、连接池、https、异步请求
- 常见场景：后端服务 A 调用另一个后端服务 B 的接口（服务间调用）；Android 访问后台接口



### 简单示例

```java
OkHttpClient client = new OkHttpClient();
Request request = new Request.Builder()
        .url("https://xxx.com/api")
        .build();
try (Response response = client.newCall(request).execute()) {
    System.out.println(response.body().string());
}
```



### 阻塞读 —— 本项目的痛点

OkHttp 的 `execute()` 和读 body 都是**阻塞调用**——线程会卡在 `read()` 上，直到对方把数据吐完。本项目用 OkHttp 读模型 SSE 流，线程要**死等模型一个字一个字吐完**（30~60 秒）。**这是后面「从模型读占线程的大头」的根源。**

## 三、Reactor



### 是什么

**Reactor（reactor-core）是 Java 生态的响应式编程库，提供** `Flux` **/** `Mono` **两个核心抽象，以及** `Scheduler` **决定操作在哪个线程上执行。**

> 属于**编排者**库，跑在你的应用里



### 核心作用

让你用**声明式**的方式编排异步数据流，由库负责在合适的线程上调度每个操作，而不是你手动管理线程。

- **Flux**：表示 0..N 个元素的异步序列（比如 SSE 一个字一个字吐，就是 `Flux<String>`）
- **Mono**：表示 0..1 个异步结果
- **Scheduler**：决定 Flux/Mono 的操作在哪个线程/线程池上跑

### 先弄清两个概念：响应式 与 声明式

Reactor 的描述里反复出现「响应式」「声明式」，先讲清这两个词，否则后面看不懂。

#### 响应式（Reactive）

传统写法是「你主动去拉数据」：调一个方法，线程卡住等它返回，拿到结果再调下一个。每一步都是「拉」。

**响应式反过来：数据「推」给你，你「响应」它的到来。** 你不再说「给我这个用户」，而是说「**当用户数据到了的时候，做这些事**」。数据什么时候来、要不要异步，都由库在背后处理，你只描述「数据到了之后怎么变换、怎么处理」。

核心思想：**把一切看作随时间流动的数据流，你描述这条流上的变换，数据自己流过来触发。** 这就是「响应式」名字的由来——你响应数据的到来。

#### 声明式（Declarative）

声明式是和**命令式**对立的概念，区别不在「要不要说每一步做什么」，而在**你说的「每一步」是变换还是机制**：

- **命令式**：你写**机制**——循环、中间变量、判断、控制时机、处理空和错误。你既说「做什么」，又说「怎么做」。
- **声明式**：你只写**变换**——过滤、映射、保存。循环、变量、时机、错误处理这些「怎么做」的部分，框架替你做了。

同一个任务（查用户 → 过滤年龄>18 → 名字转大写 → 保存），对比：

```java
// 命令式：你写循环、中间变量、判断
List<User> users = userDao.findAll();
List<User> filtered = new ArrayList<>();
for (User u : users) {                       // 你写循环
    if (u.getAge() > 18) {                    // 你写判断
        filtered.add(u);                      // 你写收集
    }
}
List<String> names = new ArrayList<>();
for (User u : filtered) {                    // 又一个循环 + 中间变量
    names.add(u.getName().toUpperCase());
}
for (String n : names) {                     // 第三个循环
    save(n);
}

// 声明式：你只写变换，循环/变量/判断全交给框架
userDao.findAllFlux()
    .filter(u -> u.getAge() > 18)
    .map(u -> u.getName().toUpperCase())
    .doOnNext(this::save)
    .subscribe();
```

声明式替你省掉了：3 个 for 循环、2 个中间 List 变量、1 个 if 判断、时机控制、空/错误处理。你留下的全是变换（过滤、转大写、保存）。

> 一句话：命令式你写**怎么做**（循环 + 变量 + 判断 + 时机），声明式你只写**做什么**（变换），怎么做交给框架。SQL 是最熟的声明式例子——你写 `SELECT name FROM users WHERE age>18`，扫表、过滤、收集全是数据库引擎干的。

### Flux / Mono 细讲

`Flux` 和 `Mono` 是 Reactor 里「数据流」的两个具体表示。它们是**异步数据流的抽象**——不是已经装好的数据，而是「将来会发出数据」的流。

> 注意：「异步」指的是数据**随时间一个一个到达**（不是一次性返回）、操作**可以调度到不同线程**。**不是说 Flux 自己做非阻塞 I/O**。读和写是流的源头和出口干的，Flux 只是中间的管子（见下文「和本项目的关系」）。

#### Mono：0 或 1 个元素的异步流

`Mono<T>` 表示异步地发出 0 个或 1 个 T 类型元素，然后完成（或出错）。可以理解成**升级版的 Future/Promise**：现在没数据，将来某个时刻发出一个值（或发出完成信号表示没有、或发出错误）。

```java
Mono<User> userMono = userDao.findByIdMono(1);  // 现在没数据
userMono.subscribe(user -> System.out.println(user));  // 订阅后，将来数据到了才执行
```

典型场景：查一个用户、调一次接口拿一个结果——单值异步操作。

#### Flux：0..N 个元素的异步流

`Flux<T>` 表示异步地发出 0 个、1 个或多个 T 类型元素，然后完成（或出错）。它是一条**随时间流动的序列**，元素可以一个一个地、在不同时刻发出。SSE 一个字一个字吐，就是典型的 `Flux<String>`——模型吐一个、Flux 发一个，吐 30 秒就发 30 秒。

```java
Flux<String> sseStream = modelClient.streamChat(prompt);
sseStream
    .map(String::toUpperCase)
    .doOnNext(word -> sendToClient(word))
    .subscribe();
```

#### 三个关键特性（Flux/Mono 共有）

1. **惰性——不订阅就不执行**。`Flux`/`Mono` 只是描述，调用 `subscribe()` 之前什么都不会发生。
2. **三种信号驱动**：`onNext(item)` 发出一个元素；`onComplete()` 流正常结束；`onError(e)` 流出错终止。你「响应」的就是这些信号。
3. **操作符串成管道**：`map`/`filter`/`flatMap`/`doOnNext` 等每个接收一个流、返回一个新流，链起来就声明出一条变换管道。数据流过来时，每个元素依次穿过这些操作符——这就是声明式 + 响应式的结合。

#### Mono vs Flux 一句话区分

| | Mono | Flux |
|---|---|---|
| 元素个数 | 0 或 1 | 0..N |
| 类比 | Future/Promise（单值异步） | 事件流/序列（多值异步） |
| 典型场景 | 查一个用户、调一次接口 | SSE 吐字、消息队列、定时事件 |

### 简单示例

```java
Flux<String> stream = Flux.fromIterable(List.of("a", "b", "c"))
        .map(String::toUpperCase)
        .publishOn(Schedulers.boundedElastic());
stream.subscribe(System.out::println);
```

### 和本项目的关系 —— Flux 是管子，不是读写的人

本项目 SSE 链路里有三个角色，**Flux 既不读也不写，它是中间的管子**：

| 角色 | 干什么 | 阻塞吗 |
|---|---|---|
| **OkHttp** | **读**——从模型的 HTTP 响应里把字读出来 | 阻塞（钉线程） |
| **Flux** | **传**——把读到的字往后传，中间可声明变换、可指定线程池 | 不读不写，只是管子 |
| **SseEmitter** | **写**——把字推给客户端 | 非阻塞（NIO） |

数据实际怎么走：

```
[某个线程上的阻塞读循环]
  while 模型还在吐:
      chunk = okhttp.read()        // 阻塞，等模型吐一个字   ← OkHttp 在读
      fluxSink.next(chunk)         // 把这个字塞进 Flux       ← 喂给管子
  ↓ Flux 管子里
  chunk → map(...) → doOnNext(...)   // 你声明的变换在这里跑
  ↓ 订阅端
  subscriber.onNext(chunk) {
      sseEmitter.send(chunk)       // 推给客户端             ← SseEmitter 在写
  }
  // 模型吐完
  fluxSink.complete() → onComplete → sseEmitter.complete()
```

阻塞的 `okhttp.read()` 在管子**入口**，非阻塞的 `sseEmitter.send()` 在管子**出口**，Flux 在中间。读阻塞不阻塞取决于入口接的是谁（这里接阻塞的 OkHttp），写阻塞不阻塞取决于出口接的是谁（这里接非阻塞的 SseEmitter），**Flux 本身和读写是否阻塞无关**。

那 Flux 到底有什么用？三个原因：
1. **声明式变换**：在「读到字」和「写字给客户端」之间要过滤、拼装、加心跳、转格式，用操作符链声明比手写循环清晰。
2. **线程调度控制（关键）**：Flux 的每个阶段可由 `Scheduler` 指定跑在哪个线程池。**这正是后面整套线程池隔离故事的载体**——「OkHttp 阻塞读跑在哪个池」就是通过 Flux 的 `publishOn`/`subscribeOn` 指定的。
3. **背压、错误、完成信号统一处理**：模型吐太快客户端收不过来（背压）、读出错、流结束，Flux 用 `onError`/`onComplete`/背压机制统一管。

### 重要：链路是多层 Flux 嵌套，处理在内层

前面的「一条管子」是简化说法。实际上 OkHttp 和 SseEmitter 之间**不是空的**，中间隔着 agent 的 ReAct 处理（推理 + 工具调用），而且这条链路是**多层 Flux 嵌套**的：处理发生在内层，Controller 订阅的是最外层（处理后的输出）。

> 关键认知：Controller 订阅的不是模型的原始流，是 agent 处理完之后的流。工具调用那些处理在更内层的 Flux 里已经做完了，到 Controller 的回调时，出来的已经是最终回复文本。

**三层 Flux，处理在内层，订阅在最外层：**

```
[模型] 吐原始 SSE 行
   ↓ 喂进
[第1层 Flux] OkHttp 原始流（IsolatedSchedulerHttpTransport.stream）
   ↓ 被消费
[第2层 Flux] agent.stream —— ReAct 在这里：推理、调工具、多轮循环
   ↓ 产出 agent 事件（含 AGENT_RESULT）
[第3层 Flux] .filter(AGENT_RESULT).map(文本) —— 只留最终文本
   ↓
[Controller 订阅第3层] 拿到的已是最终文本
   ↓ emitter.send(文本)  ← 直接推，不用再处理
[客户端]
```

对应代码：

- **第 1 层**：`IsolatedSchedulerHttpTransport.stream` 用 `Flux.<String>create(...)` 产出模型吐的**原始 SSE 行**（推理片段、工具调用请求、最终结果混在一起）。
- **第 2 层**：`context.agent().stream(...)` 是 agent 的流，**ReAct 循环就在这一层**——消费第 1 层的原始字，做推理、调工具（工具结果再喂回模型）、多轮循环，最后产出 agent 事件。`StreamOptions` 还显式排除了推理片段（`includeReasoningChunk(false)`，只要 `AGENT_RESULT`）。
- **第 3 层**：`.filter(AGENT_RESULT).map(textContent)` 把 agent 事件过滤成**纯最终文本**。到这一步，推理、工具调用早就在第 2 层消化完了。
- **Controller 订阅第 3 层的输出**：`agentChatService.queryStream(request)` 返回的就是第 3 层这个纯文本 Flux，Controller 的回调拿到的 `content` 已经是处理完的最终文本，直接 `emitter.send` 推客户端——不需要再处理，因为处理在内层已做完。

所以「Controller 的回调直接推给客户端」**不是因为跳过了处理**，而是因为它订阅的位置在处理**之后**。处理（含工具调用）发生在内层的 `agent.stream` 里，Controller 订阅的是最外层、处理后的输出。

> 准确说法：本项目 SSE 链路是**多层 Flux 嵌套**——最内层 OkHttp 读原始字 → 中间层 `agent.stream` 做 ReAct（含工具调用）→ 最外层过滤出最终文本 → Controller 订阅最外层、直接推客户端。OkHttp 在入口阻塞读，SseEmitter 在出口非阻塞写，中间的 ReAct 处理由内层 Flux 承载。**问题就出在：默认情况下，最内层的阻塞读被调度到全局共享的** `boundedElastic`**。**

## 最关键区别


| 项目  | Servlet         | OkHttp         | Reactor            |
| --- | --------------- | -------------- | ------------------ |
| 角色  | **服务端，接收别人的请求** | **客户端，主动发起请求** | **编排者，把异步操作串成流水线** |
| 位置  | 跑在 Tomcat 服务器上  | 跑在你的应用里        | 跑在你的应用里            |
| 方向  | 等着别人来访问我        | 我去访问别人         | 不接也不发，只负责调度        |




### 把三者串起来的场景

1. 客户端发 SSE 请求 → 本服务的 **Servlet（异步）** 收到，线程立刻归还
2. 本服务用 **Reactor 的 Flux** 编排：调 **OkHttp** 去读模型的 SSE 流
3. OkHttp 阻塞读模型吐的字 → 这个读跑在 Reactor 调度的线程池上
4. 读到的字通过 Flux 推给异步 Servlet，由 Tomcat 的 NIO 写回客户端

> Servlet = 接请求的一方（异步，不占线程）
> OkHttp = 发请求的一方（阻塞读，占线程）
> Reactor = 把两者串起来、决定阻塞读跑在哪个池的编排者

# 主线：从「为什么读占线程、写不占」到「隔离 + 虚拟线程」



## 第 0 层：起点问题

**为什么从模型读才是占线程的大头，而往客户端写不是？**

同样是 SSE，同样是流式吐字，读和写的线程代价却完全不同。这是整篇文档要回答的第一个问题，也是后面所有讨论的入口。

## 第 1 层：读和写的线程代价为什么不同

回答第 0 层，分两条线对比。

### 往客户端写：异步 Servlet + NIO，几乎不占线程

本项目的 SSE 接口返回 `SseEmitter`，走的是 Spring MVC 的**异步 Servlet**。流程是：

1. Tomcat 收到请求，分配一个工作线程进入 Controller。
2. Controller 创建 `SseEmitter` 并立刻返回——**这个工作线程当场归还给 Tomcat**，不占着。
3. 后续往客户端推数据时，由别的线程调用 `emitter.send(...)`，数据交给 Tomcat 的 **NIO 非阻塞 I/O** 写出去——写线程把数据丢给内核就返回，不等客户端收完。
4. 流结束调用 `emitter.complete()` 收尾。

关键：**写这一步用的是 NIO，写线程不阻塞、不等待**。所以「往客户端写」几乎不占线程，吐多少字都不需要钉一个线程。

### 从模型读：OkHttp 阻塞 read()，钉死一个线程

本服务调模型用的是 OkHttp，`read()` 是**阻塞调用**。模型用 SSE 一个字一个字吐，本服务要派一个线程死等在 `read()` 上，等模型吐完才返回。一次对话 30~60 秒，这个线程就被钉死 30~60 秒。所以「从模型读」才是占线程的大头。

### 一句话对比

- 写客户端：异步 Servlet + NIO，写线程丢下数据就走 → **不占线程**。
- 读模型：OkHttp 阻塞 `read()`，线程死等吐完 → **占线程，且占很久**。

**这一层留下一个新问题**：那这个「死等在 read() 上的线程」具体是哪个线程？谁派它来的？跑在哪个池子上？

## 第 2 层：这个阻塞读默认跑在哪个池上

回答第 1 层的疑问。OkHttp 的阻塞读是被 Reactor 的 `Flux` 操作符调度的，而 Reactor 对「阻塞操作」的默认去处是 `Schedulers.boundedElastic()`。

### boundedElastic 是什么

`boundedElastic` 是 Reactor 给**阻塞 I/O** 准备的默认线程池。容量默认是「CPU 核数 × 10」上限，排队任务有上限。它的设计意图就是：当你明确知道某个操作会阻塞、又没指定专用池时，扔到这里跑，免得阻塞跑在并行计算的 `parallel` 池上把 CPU 任务拖死。

### 关键属性：进程级全局共享

`boundedElastic` 是**进程级单例**——整个 JVM 里所有 Reactor 流的阻塞操作，只要没显式指定别的池，全都落到这一个 `boundedElastic` 上。所有渠道、所有阻塞操作都往这一个池里塞。

> 小注：`boundedElastic` 是 Reactor 的 **Scheduler**（抽象的「调度器」接口，决定操作在哪个线程跑）；它内部包着一个 **ExecutorService**（具体的线程池）。文档后面说的「分池」，分的是 ExecutorService，再由 Reactor 包成 Scheduler 供 Flux 使用。两者关系就是「Scheduler 包着 ExecutorService」。

**这一层留下一个新问题**：全局共享为什么是个问题？大家共用一个池不是挺好吗？

## 第 3 层：全局共享池为什么会出事

回答第 2 层的疑问。讲清「共享池」在多渠道、多负载下的失败模式。

### 争抢

160 个 SSE 读 + 工具调用 + 其他阻塞操作，全挤一个池。池容量有限，超过就排队。

### 互相污染

某个渠道慢（模型卡 30 秒），它占着池里的线程不放，别的渠道的请求只能排队等。一个渠道的尾延迟拖垮其他渠道的响应时间——这就是**跨渠道污染**。

### 级联

上游慢 → 池线程被占满 → 新请求排队 → 排队超时 → 调用方重试 → 雪崩。一个渠道的故障会沿共享池**级联**到所有渠道。

### 假阳性积压

池满了，新请求被拒或排队，监控看起来像「服务过载」，其实是被某个慢渠道拖累。告警指向过载，根因却是隔离缺失。

### 一个具体场景走查

- 旧方案（共享 `boundedElastic`）：渠道 A 的模型卡 30 秒，A 的 160 个读占满池里大部分线程；渠道 B 的新请求进来，只能排在后面等，B 的 P99 从 2 秒飙到 30 秒，甚至超时。B 的用户根本没招惹 A，却被 A 拖死。
- 新方案（按渠道分池）：A 的读跑在 A 自己的池里，B 的读跑在 B 自己的池里。A 卡死只影响 A，B 的 P99 不受影响。

**这一层留下一个新问题**：怎么解决？显然不能让大家挤一个池。

## 第 4 层：隔离方案 —— 按职责 / 渠道分池

回答第 3 层的疑问。讲清「分而治之」的思路。

### 按职责分池

- **模型 SSE 读**：按渠道再细分，`modelSseQnExecutor`、`modelSseZzExecutor` 等。一个渠道卡了不拖累别的渠道。
- **工具调用**：单独 `dynamicToolExecutor`。工具慢不拖累模型读。
- **其他**：各自独立的池（`memoryRecordExecutor`、`priorityExecutor` 等）。



### 两个隔离方向

- **工具侧**：`AgentBuildContext` 把 `dynamicToolExecutor` 注入框架的 `ToolkitConfig.executorService`，注释明说「传入后框架 ToolExecutor 不再使用全局 boundedElastic」。框架默认行为（工具跑全局 `boundedElastic`）被显式覆盖。
- **模型 SSE 侧**：`IsolatedSchedulerHttpTransport` 把 SSE 读取的 Scheduler 替换成按 channel 分的 `modelSse*Executor`，不落全局 `boundedElastic`，也不落工具池。



### 隔离的附带收益：可观测性

分池之后每个池有独立指标（`/boundedElasticStats`、各 executor 的 `stats()`）。出问题能定位到是哪个渠道、哪类操作在拖累，而不是面对一个混在一起的「池满了」告警无从下手。

**这一层留下一个新问题**：分了池之后，每个池要扛 160 个并发阻塞读。如果用平台线程，160 个 OS 线程被钉死 30~60 秒，太贵了。怎么办？

## 第 5 层：阻塞 + 大量线程的传统痛点

回答第 4 层留下的疑问。先把「为什么 160 并发阻塞读用平台线程贵」讲透，为后面的方案做铺垫。

### 平台线程 = OS 线程，一对一

Java 传统的线程（平台线程）和操作系统的线程是**一对一**的。`new Thread()` 在 JVM 里建一个，内核里就真的建一个 OS 线程陪它。

### 阻塞时 OS 线程干等

平台线程最痛的一点：**一旦阻塞在 I/O 上（比如** `read()`**），这个 OS 线程就干等，什么也干不了，但它的内存和调度资源还占着。**

### 160 并发的代价

- 每个 OS 线程默认栈约 1MB，160 个 ≈ 160MB 栈内存。
- 内核调度 160 个线程的上下文切换开销。
- 这 160 个线程大部分时间都在 `read()` 上干等，纯浪费。

所以传统上「阻塞 + 大量线程」是个昂贵组合，逼着人要么限制并发、要么换非阻塞 I/O。

**这一层留下一个新问题**：能不能既保留「阻塞写法」（简单、成熟），又不要付出「大量 OS 线程」的代价？

## 第 5.5 层：设计取舍 —— 两条路，为什么选后者

回答第 5 层的疑问。读者到这里会自然想：既然阻塞 + 大量线程贵，那直接换成**非阻塞 I/O** 不就好了？这是个合理的质疑，必须正面回答。

### 两条路

- **路线 A：换非阻塞 I/O**。把 OkHttp 换成非阻塞的 HTTP 客户端（如 WebClient / 基于 Netty）。读模型不再钉线程，一个事件循环线程能扛成千上万的并发连接。
- **路线 B：保留阻塞 OkHttp + 用虚拟线程扛并发**。阻塞写法不变，但把跑阻塞读的线程从平台线程换成虚拟线程，让「阻塞 + 大量线程」变便宜。



### 为什么本项目选 B

1. **改造成本**：模型调用、SSE 解析、工具调用整条链路都建立在阻塞 OkHttp 之上，换非阻塞客户端意味着整条链路重写（回调/响应式风格、错误处理、超时语义全变）。虚拟线程方案只换底层线程模型，上层业务代码几乎不动。
2. **成熟度与可控性**：OkHttp 阻塞调用栈简单、调试直观、超时和重试语义清晰；非阻塞客户端的调试栈深、错误难追。对一个已有大量业务逻辑的服务，保留阻塞写法风险更低。
3. **虚拟线程让 B 的代价消失**：B 路线唯一的缺点就是「阻塞 + 大量线程贵」，而虚拟线程正好把这个缺点抹掉。既然缺点没了，B 就成了「低成本改造 + 低风险」的优选。

> 一句话：非阻塞不是「更好」，而是「另一种取舍」。当虚拟线程让阻塞写法不再贵时，「保留阻塞 + 隔离 + 虚拟线程」在改造成本和可控性上反而更优。这正是本项目选 B 的原因。



## 第 6 层：虚拟线程 —— 让「阻塞 + 大量线程」变便宜

回答第 5 / 5.5 层的疑问。这是文档的技术高潮。

### 虚拟线程是什么

虚拟线程（Java 21 正式特性）是 **JVM 管理的轻量线程**，运行在少数几个 OS 线程（叫**载体线程 carrier**）之上。关系从平台线程的「1:1」变成虚拟线程的「N 个虚拟线程 : M 个载体线程」（M 很小，通常等于 CPU 核数）。

### 关键特性

1. **创建几乎免费**：虚拟线程不对应 OS 线程，JVM 在堆上分配，创建成本接近创建一个对象。可以建几万、几十万个。
2. **栈很小、按需分配**：平台线程栈固定 1MB，虚拟线程栈初始只有几百字节，用到才长。
3. **阻塞时「卸载」**：这是最关键的——虚拟线程阻塞在 I/O 时，JVM 把它从载体线程上「摘下来」，载体线程立刻可以去跑别的虚拟线程。等 I/O 好了，虚拟线程再「装回」某个空闲载体线程继续跑。
