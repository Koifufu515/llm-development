# 会话编排：状态机、订单切换与并发回写

> 面向：过一段时间不打开源码也能重新理解 Expert 会话编排这条链路的设计，并能应对面试。
> 范围：会话编排链路——意图识别、工程算态、Skill/reference 选择、订单切换、状态回写。
> 源码定位见文末附录 A。

---

## 一、业务问题

客服办理一笔订单要分阶段：先确认订单和诉求，再给方案、说明代价，最后才真正执行动作。每个阶段绑定一段办理说明（reference）和一组允许调用的工具，只有走完当前阶段才能进入下一阶段。

如果让模型自己管状态，会出现两类问题：

- **状态幻觉**：模型复述错误的当前阶段，说"已经为您办理完成"但实际还没执行；话术和工具跟着错位，用户以为事情已经办妥。
- **跳阶段、调错工具**：模型一次拿到全部阶段、全部工具，会自行判断当前阶段并直接调用末态工具（比如还没协商就先改判）。

为解决这个不可控性，系统把"当前处于哪个阶段"从模型手里拿走，交给工程侧一个**确定性状态机**：当前阶段只读会话缓存里上一轮已成功提交的值，模型每轮只提建议（推进 / 保持 / 重来），工程结合缓存、订单和已执行工具的历史结果决定本轮真正处于哪个阶段。模型仅保留一项自由度：按当前阶段的办理说明和工具组织给用户的回复。

另一个绕不开的问题是**订单切换**。一笔电话里用户可能改问另一笔订单，模型也会"编造"订单号。系统必须保证切单目标真实存在、切单后旧订单的工具结果不污染新订单、且用户原来的诉求不会因为切单而丢失。

还有一类工程问题：同一会话两轮可能并发重叠，慢的一轮回写会盖掉快的一轮的新进度。系统必须能识别并丢弃过期回写。

整条链路要解决的核心问题是：**用工程侧确定性状态机替代模型自管状态，并在并发、切单、失败降级等边界上保持状态一致。**

## 二、整体架构

整条链路围绕一个会话状态对象展开，存在 Redis 里，按会话 ID 隔离。每一轮分两个阶段：

1. **准备阶段**：读缓存 → 调路由模型 → 工程算态 → 装配 Skill 和工具 → 产出本轮执行计划。这一阶段只读缓存，不写。
2. **完成阶段**：业务 Agent 流式回复结束后，比对版本号回写缓存（推进状态、合并工具台账、记录对话、处理切单）。

关键角色：

| 角色 | 职责 |
| --- | --- |
| 路由模型 | 输出技能选择 + 当前意图 + 状态流转建议（HOLD/NEXT/RESTART）。不输出当前状态。 |
| 状态机 | 工程侧确定性。以缓存中的已提交状态为起点，结合路由建议、reference 表、是否同技能同订单，给出本轮状态和动作。 |
| 编排器 | 主控。准备阶段算态、装配执行计划；完成阶段版本校验、状态推进、订单切换、工具台账合并、对话落库。 |
| 状态存储 | 会话状态存取，每次保存版本号自增。 |
| 工具装配器 | 按 reference 状态叠加工具：通用工具 + 当前状态专属工具。 |
| 执行拦截钩子 | 一轮最多一个操作类工具调用。 |
| 切单识别 | 按技能编码识别是否切单技能。 |

决策主线：

> **路由模型提议（HOLD/NEXT/RESTART） → 工程算态（结合缓存状态、是否同技能同订单、上一轮工具结果） → 状态机给出本轮状态和动作 → 装配 Skill/reference/工具 → 业务 Agent 执行 → 完成时版本校验回写**

模型只提建议，不落定状态。这是整条链路最核心的约束。

## 三、一次请求的执行过程

> 以下按"处理阶段"组织，不按固定时间点。准备阶段是同步阻塞的（路由模型调用、状态装配都在主流程上），完成阶段在业务 Agent 流式结束后异步触发。

### 阶段 1：读缓存与候选技能解析

请求进入编排器后：

1. 读会话状态。缓存为空时返回一个空对象（不是 null），后续逻辑统一处理。
2. 解析配置里的技能组，把每个技能的定义（编码、名称、描述、状态流、reference 路径、资源）解析成候选集合。配置损坏（缺编码、缺内容、状态流里有非法状态、reference 缺内容）会抛异常，被外层捕获后降级到主 Agent。

会话状态的关键内容：

- 上一轮已提交的技能和订单。
- 上一轮已提交的 reference 状态（取证 / 判责 / 协商 / 处置）。
- 会话级工具台账：按工具编码去重，只留最新一次结果。
- 查单白名单：查单工具命中过的订单号，上限 40。
- 待确认候选订单：上一轮列表查单唯一命中的订单。
- 切单前暂存的原诉求及续接标志。
- 当前业务 Agent 的 Memory 命名空间。
- 乐观锁版本号，每次保存自增。

### 阶段 2：路由模型提议

调路由 Agent：

- 路由 Agent 必须配置禁用框架自动累积的会话历史。工程显式注入它的输入：候选技能列表、缓存状态摘要（当前意图、当前技能、当前阶段、订单是否锁定、状态摘要）、最近 6 轮对话、当前用户消息、可选的 IVR 阶段短期记忆。
- 路由模型输出：技能编码、当前意图（最多 12 字）、状态流转建议（HOLD/NEXT/RESTART）。**不输出当前状态**——这是关键约束，当前状态只由工程缓存提供。
- 路由不用框架的结构化输出工具，而是文本里解析 JSON。原因是框架结构化输出会在模型没调函数时强制补一轮，多付一次全量调用（约 10K token、1 秒以上），且补的那轮会把上一轮文本读进历史继续推理，可能给出与第一次不同的结果。解析失败抛异常，上层降级到主 Agent。

路由失败、未命中候选技能、技能配置损坏，都会降级到主 Agent，不推进状态。

### 阶段 3：工程算态

这是整条链路最核心的一步。输入是路由建议 + 缓存状态 + 当前订单 + 已执行工具台账，输出是本轮的 reference 状态和动作。

#### 3.1 计算订单作用域

决定本轮按哪笔订单走：

- 不需要订单的技能用全局作用域。
- 缓存里有真实订单 → 用缓存订单（Agent Redis 是唯一事实来源，IVR 重复携带的旧订单不能覆盖）。
- 缓存为空且未标记会话已初始化 → 用请求里的订单作首轮种子。
- 缓存为空但已标记初始化 → 返回"缺失"，拒绝回退到 IVR 进线旧订单。

订单作用域决定后续工具台账、白名单、状态缓存键的隔离范围。

#### 3.2 判断"同技能同订单"

当前候选技能等于缓存里的已提交技能，且订单作用域也相同。这是状态机能否沿当前流程推进的前提。换技能或换订单，状态机直接 `RESET` 回到新流程的首态。

#### 3.3 计算有效状态流转建议

路由建议 `NEXT` 时，检查当前 reference 状态绑定的工具在上一轮已执行的结果是否失败（工具执行错误 / 业务校验失败）。失败则降级为 `HOLD`，留在当前阶段让模型重新处理。

注意这里看的是**上一轮写回缓存的历史工具结果**，不是本轮的——本轮还没开始调工具。这是"中途失败不推进"的关键。

#### 3.4 状态机决策

状态机是纯函数，输入（是否同技能同订单、已提交状态、路由建议、reference 表），输出（本轮状态、动作）：

- reference 表为空（技能没绑 reference）→ 返回（null，`NONE`），不参与状态机。
- 不是同技能同订单 → 返回（首态，`RESET`）。
- 路由建议 `RESTART` 且当前已是末态 → 返回（首态，`RESTART`）；不是末态 → 返回（当前，`CONTINUE`），不允许中途跳回首态。
- 路由建议 `NEXT`：已是末态 →（当前，`CONTINUE`）；有下一态 →（下一态，`ADVANCE`）。
- 路由建议 `HOLD` 或为空 →（当前，`CONTINUE`）。

动作五种：`RESET`（换流程回首态）、`RESTART`（同流程末态回首态）、`CONTINUE`（保持当前）、`ADVANCE`（推进到下一态）、`NONE`（技能无状态机）。

#### 3.5 装配 reference 内容和工具

- 按状态流顺序构建"状态 → reference 路径"的有序映射，再从资源里取出 reference 正文。状态没绑 reference 时返回空映射，状态机直接走 `NONE` 分支。
- 工具装配：先放通用工具，再叠加当前 reference 状态的专属工具，状态级配置按工具编码覆盖通用配置。操作类和敏感操作标记只允许收紧，不能被状态配置降级。

工具可见性是**间接限制**：模型只看见当前阶段允许的工具。执行拦截是另一件事，见阶段 5。

#### 3.6 计算 Memory 命名空间

`RESET` 和 `RESTART` 时换新的命名空间（带 UUID），其他动作沿用原来的。Memory 按 flow 隔离，跨技能或状态机重启时旧 Memory 会被清理，已经执行成功的写操作（如改判）会从模型视野里消失——这是工具台账存在的理由。

#### 3.7 计算 carryOver 上下文

Memory 换了命名空间，模型本轮看不到任何历史消息。carryOver 把最近对话和当前订单作用域下的已执行工具台账注入业务 Agent 输入，让上下文不断得太干净。沿用同一命名空间时历史已在消息链里，再注入会让同一段话出现两次，所以只有 Memory 重置时才注入。

#### 3.8 产出执行计划

把上述所有结果打包成本轮执行计划，带上当时的缓存版本号（完成时用于乐观锁校验）。这一步**不写缓存**——避免中途失败造成进度超前。

### 阶段 4：业务 Agent 流式执行

业务 Agent 按当前阶段的 reference 内容、可见工具、carryOver 上下文组织回复，流式输出。这一阶段的状态机不介入，工具执行拦截在这里发生。

### 阶段 5：执行拦截——一轮最多一个操作类工具

执行拦截钩子在模型推理后、工具真正执行前触发：

- 用一个原子布尔标志，第一个操作类工具调用 `compareAndSet(false, true)` 成功放行。
- 后续操作类工具调用一律丢弃，如果丢弃后消息里没有别的块，补一条"本轮已经选择过一个操作类工具"的文本。
- 查询类工具不受此限。

这是**硬限制**，区别于阶段 3 的工具可见性（间接限制）。状态机本身只管翻到哪个阶段，不直接拦执行；执行拦截由这个钩子兜底。

### 阶段 6：完成阶段——版本校验回写

业务 Agent 流式结束后，调用编排器的完成方法（或降级路径）。

正常完成的关键步骤：

1. 重新读缓存，比对执行计划里记的版本号和当前缓存版本号。不一致说明中间已有别的轮写过，**整轮放弃回写**，并清理这次还没提交的 Memory。
2. 解析切单决策：只接受切单技能显式返回的 `SWITCH`，目标必须精确命中白名单；漏传目标时用待确认候选订单补；对不上就降级为 `UNKNOWN`，并拦截模型回复（替换成"抱歉，这笔订单暂时还没有确认成功"）。
3. 切单成功时：清掉旧订单的技能进度、工具台账、白名单；标记原诉求可续接；清掉旧 Memory 命名空间。
4. 推进状态：当前状态 = 执行计划里的 reference 状态；写一条状态摘要。
5. 合并工具台账：按工具编码去重只留最新一次，上限 20 条。兜底的"已执行"状态不能盖掉真实的"成功"状态。
6. 追加对话，上限 6 条。
7. 保存：版本号自增、更新时间戳，写回 Redis。

降级路径的区别：

- **主 Agent 降级回写**：路由或装配失败降级主 Agent 时，只保存对话和 Memory，不推进技能/reference 状态。
- **持久化降级回写**：业务 Agent 回复已流式送达但 Memory 没存上时，仍记录对话、工具事实、首轮订单种子；显式切单技能还会提交有效换单。并发版本过期时整轮放弃回写。

### 阶段 7：切单后的原诉求续接

切单成功后，下一轮用户不一定再重说原诉求。系统在进入切单技能时把原诉求（优先用当前意图，否则取最近一条用户消息）暂存为独立字段，并标记"尚未可续接"。

切单成功提交时把续接标志置为"可续接"。下一轮如果是静默（用户没说话），编排器检测到续接标志，就用暂存的原诉求构造一个续接请求重新走准备流程，并把当前用户消息置空避免把原诉求重复记成新发言。

非静默的正常轮如果用户已经主动说话，清掉暂存，不再自动续接。

## 四、关键技术机制

### 4.1 模型提议、工程落定

状态机的当前状态只来自会话缓存，模型每轮只提流转建议，由状态机落定。这是为了防状态幻觉：模型复述错当前阶段后，话术和工具会跟着错位，用户会以为事情已经办妥。

需要区分**路由输出**和**工程算态**：

- 路由输出：技能编码 + 当前意图 + 状态流转建议（HOLD/NEXT/RESTART），不含当前状态。
- 工程算态：以缓存当前状态为起点，结合是否同技能同订单、reference 表、上一轮工具结果，得出本轮状态和动作。

"确定性"体现在：给定相同的路由结果、缓存状态、订单和工具结果，状态转换是确定的；不是整个过程完全不依赖模型。模型保留的自由度是按当前阶段的 reference 和工具组织回复。

### 4.2 乐观锁回写

完成时比对执行计划记的版本号和当前缓存版本号，不一致整轮放弃回写。每次保存版本号自增。

用乐观锁而不是悲观锁的原因：同一会话两轮重叠是少见情况，不是常态。悲观锁会让正常路径为少见情况常驻代价；乐观锁在正常路径不需要持锁等待，只在真重叠时丢掉慢的那轮。

放弃回写时还要清掉这次还没提交的 Memory 命名空间，避免 Memory 残留污染下一轮。

### 4.3 查单白名单与切单校验

切单时模型提议的目标订单必须精确命中工程从查单工具结果里维护的白名单。原因是模型会编造订单号，放开切单会把流程带到一笔不存在的订单上。

白名单维护链路：

- 本轮列表查单工具（带订单列表查询能力，或工具编码属于列表查单工具集合）的输出里抽取订单号，并入白名单，上限 40 条，超出按先进先出丢弃。
- 抽取时先按 JSON 解析递归找订单号字段；解析失败时按原文定位标准字段，兼容截断 JSON。
- 模型提交 `SWITCH` 时，目标必须在白名单里；漏传目标且本轮只有唯一一笔查单时，用待确认候选订单补；对不上就降级为 `UNKNOWN` 并拦截回复。

流式下发前还会做一次校验，避免把未通过白名单的切单话术播给用户。

### 4.4 工具可见性 vs 执行拦截

这两件事经常被混淆，必须分清：

| 机制 | 作用层 | 性质 | 实现 |
| --- | --- | --- | --- |
| 工具可见性 | 模型输入 | 间接限制（模型看不见就不会调） | 按当前 reference 状态叠加工具集 |
| 执行拦截 | 工具执行前 | 硬限制（调了也删） | 一轮最多一个操作类工具 |

状态机本身只管翻到哪个阶段，不直接拦执行。可见性按阶段叠加工具集，决定模型能看见哪些工具；执行拦截在工具真正执行前保证一轮最多一个操作类工具，多余的工具调用删掉。两者互补，不能互相替代——模型可能在一轮里并行生成多个操作类工具调用，光靠可见性挡不住。

### 4.5 切单原诉求暂存与续接

切单会清掉旧订单的技能进度，原诉求会一起丢失。系统在进入切单技能时把原诉求另存为独立字段，切单成功后下一轮自动接回。

为什么用独立字段而不是对话历史：对话历史是多轮列表，不明确哪句是原诉求，且需要标志控制续接时机。切单确认前的静默不得消费原诉求，必须等显式 `SWITCH` 提交成功后才置可续接。

切单成功后清掉旧订单的技能进度、工具台账、白名单、Memory，但保留最近对话和原诉求——下一轮从缓存取出来注入业务 Agent 输入，让上下文不断得太干净；工具结果不注入，因为属于旧订单作用域，带入新订单会污染。

### 4.6 Memory 按 flow 隔离与工具台账

业务 Agent 的 Memory 按 flow 隔离：`RESET` 和 `RESTART` 换新命名空间（带 UUID），旧 Memory 被清掉。已经执行成功的写操作（如改判）会从模型视野里消失，导致模型重复提出同一个动作。

工具台账就是为了补这个缺口：跨 flow 保留，按工具编码去重只留最新一次，上限 20 条。台账从两个来源取：Memory 消息链里模型发起的调用、工程侧预执行的只读工具；预取结果排在后面，同名工具以本轮工程侧的新鲜结果为准。

台账还有两个细节：

- 兜底状态不能盖已知状态：跨实例回写时执行现场状态经常读不到，采集会把真实"成功"写成兜底的"已执行"。台账按工具编码只留一条，若用兜底盖掉"成功"，下一轮复述"已经为您申请"会被护栏当成没执行过。
- 本轮已注入的工具要从历史台账里剔除：本轮工具结果区已经带了最新结果，历史台账里的同名旧快照必须去掉，否则同一个工具会以两个不同结果同时出现在模型上下文里。

### 4.7 降级路径

整条链路有三类失败，各有降级路径，且都不拿失败轮去推进阶段：

| 失败点 | 触发 | 降级动作 |
| --- | --- | --- |
| 路由失败/未命中技能/配置损坏 | 准备阶段内捕获 | 降级主 Agent，不装配技能/工具 |
| 技能装配阶段失败 | 装配失败时 | 原执行计划转主 Agent 降级计划，沿用降级 Memory 命名空间 |
| 回复已送达但 Memory 没存上 | 流式结束后 | 仍记录对话、工具事实、首轮订单种子；切单技能仍提交有效换单 |

所有降级路径在回写时都走版本校验，过期一律放弃回写，避免失败轮覆盖成功轮的状态。

## 五、设计价值与工程取舍

这套方案的核心不是简单地把状态机写在工程侧，而是解决了三个问题。

### 1. 防状态幻觉

模型不再输出当前状态，只提推进/保持/重来建议。当前状态由工程缓存提供，状态机以缓存为起点算态。即使模型说错，话术和工具也跟着不错位。

### 2. 保证状态一致

并发回写靠乐观锁丢弃过期轮；切单靠白名单拦截编造订单；中途失败靠"不推进 + 降级主 Agent"避免进度被一次失败推前。三个机制共同保证缓存里的状态始终是已成功提交的真实进度。

### 3. 平衡模型自由度与工程约束

模型保留按当前阶段 reference 和工具组织回复的自由度，工程约束状态流转、工具可见性、操作类工具执行次数。模型在该自由度内发挥，越界由工程兜底。

### 代价

- 路由模型每轮都要调一次，增加一次模型调用延迟（约 1 秒以上）。
- 状态机决策依赖缓存和工具台账的正确性，缓存损坏或工具状态采集不准会影响下一轮判断。
- 整体复杂度上升：状态机、乐观锁、白名单、Memory 隔离、工具台账、降级路径，每一项都有自己的边界条件。
- 切单续接依赖续接标志和静默轮触发，非静默轮用户主动说话会清掉暂存，原诉求不会自动接回。

这套方案实际上是在**状态可控性、调用延迟、实现复杂度**之间做权衡。

### 状态机解决的是什么、不解决什么

状态机解决的是**当前阶段的确定性**和**阶段流转的工程约束**，不解决模型在当前阶段内的回复质量：

- 当前阶段不会因为模型说错而错位，这是状态机保证的。
- 模型在当前阶段内怎么组织话术、怎么用工具，仍由模型自身决定，状态机不介入。
- 工具执行结果是否成功，由工具自身决定，状态机只在下一轮算态时读这个结果决定是否降级推进。

面试如果被问"状态机是不是让模型回复更准了"，要诚实说"不直接改善回复质量，它保证的是阶段和工具不错位；回复质量仍取决于模型在当前阶段约束下的表现"。

---

## 六、总结

Expert 会话编排的核心是一个"模型提议 + 工程落定"的状态机机制：

- 路由模型每轮提议技能 + 状态流转建议，**不输出当前状态**。
- 工程以缓存中的已提交状态为起点，结合是否同技能同订单、上一轮工具结果，由状态机落定本轮状态和动作。
- 按 reference 状态装配技能内容和工具集，业务 Agent 在约束内组织回复。
- 完成时比对版本号回写缓存：推进状态、合并工具台账、记录对话、处理切单。
- 切单靠查单白名单拦截编造订单，原诉求暂存后续接，旧订单作用域整体清理。
- 并发回写靠乐观锁丢弃过期轮，失败轮走降级路径不推进状态。

**最终实现的目标是：模型只提建议、工程落定状态，保证阶段和工具不错位，并在并发、切单、失败降级等边界上保持状态一致。**

## 附录 B：状态机决策表

`ReferenceStateMachine.resolve(是否同技能同订单, 已提交状态, 路由建议, reference 表)` 的全部输出：

| 前提 | 路由建议 | 输出状态 | 输出动作 | 含义 |
| --- | --- | --- | --- | --- |
| reference 表为空 | 任意 | null | NONE | 技能无状态机，不参与 |
| 不是同技能同订单 | 任意 | 首态 | RESET | 换技能或换订单，回到新流程首态 |
| 任意 | RESTART 且当前已是末态 | 首态 | RESTART | 同流程末态用户明确不接受，回到首态 |
| 任意 | RESTART 且当前不是末态 | 当前 | CONTINUE | 不允许中途跳回首态，保持当前 |
| 任意 | NEXT 且当前已是末态 | 当前 | CONTINUE | 再推进也停在原地 |

## 附录 C：面试追问要点

**第一轮为什么从第一阶段开始。** 缓存为空时没有已提交的技能和订单，"同技能同订单"判断为否，状态机直接返回 `RESET`，落到这个技能流程的首态。模型这一轮的进/停/重来不参与翻阶段，因为没有已提交的状态可翻。

**什么情况下模型的"进"不生效。** 两种：已经是流程最后一个阶段，下一态就是当前，结果记成 `CONTINUE` 而不是 `ADVANCE`；或者当前阶段绑定的工具在上一轮已执行结果是失败，工程先把 `NEXT` 改成 `HOLD`，阶段停住。注意这里看的是上一轮写回缓存的历史工具结果，不是本轮的——本轮还没开始调工具。

**查单白名单怎么拦。** 从本轮列表查单工具输出里抽订单号进白名单，上限 40 条。模型的目标订单必须精确命中白名单；漏传目标且本轮只有唯一一笔查单时，用待确认候选订单补上。对不上就丢掉这次切单，回固定话术"抱歉，这笔订单暂时还没有确认成功"。

**工具可见性和执行拦截是两件事。** 可见性是按当前阶段叠加工具集，决定模型能看见哪些工具，是间接限制。执行拦截是在执行前保证一轮最多一个操作类工具，多余的工具调用删掉，是硬限制。状态机本身只管翻到哪个阶段，不直接拦执行。

**版本回写。** 计划生成时记下当时的缓存版本号。回写前再读一次缓存，版本对不上就整轮放弃回写，并清掉这次还没提交的 Memory。每次保存版本号自增。

**Memory 什么时候清空。** `RESET` 和 `RESTART` 时 Memory 换新命名空间，旧 Memory 被清掉；`CONTINUE` 和 `ADVANCE` 沿用原来的。所以换技能、换订单、推倒重来都让业务模型从新 Memory 开始，历史对话存在会话状态缓存里，下一轮从缓存取出来注入业务 Agent 输入，不是完全空白。

**为什么路由不用框架结构化输出。** 框架的结构化输出是先让模型自由生成，没调函数再强制补一轮。路由每轮因此要多付一次全量模型调用（约 10K token、1 秒以上），而且补的那轮会把上一轮文本读进历史继续推理，可能给出与第一次不同的结果。路由输出格式由提示词保证，工程从文本里解析 JSON；解析失败抛异常，上层降级到主 Agent。

**中途失败为什么不推进。** 路由失败、技能装配失败、Memory 没存上，都发生在这一轮办到一半时。如果还推进阶段，下一轮会从错的地方开始。三类失败各有降级回到主模型，且都不拿失败轮去推进阶段。主 Agent 降级回写只保存对话和 Memory，不推进技能/reference；持久化降级回写仍记录对话、工具事实、首轮订单种子，但不推进技能/reference。

**切单后原诉求怎么不丢。** 进入切单技能时把原诉求（优先当前意图，否则最近一条用户消息）暂存为独立字段，标记"尚未可续接"。切单成功提交时置"可续接"。下一轮静默时检测到可续接，就用暂存消息重新走准备流程，并把当前用户消息置空避免重复记成新发言。非静默轮用户主动说话会清掉暂存，不再自动续接。

**为什么用独立字段暂存原诉求而不是对话历史。** 对话历史是多轮列表，不明确哪句是原诉求，且需要标志控制续接时机。切单确认前的静默不得消费原诉求，必须等显式 `SWITCH` 提交成功后才置可续接。

## 附录 D：Memory 与 State

整条链路里有两个容易混淆的"记忆"：**State**（工程侧的会话状态）和 **Memory**（模型侧的短期记忆）。它们存的地方不同、存的内容不同、隔离方式不同、作用也不同。面试时被问"你们状态怎么管的"，必须先把这两个分清。

### D.1 一句话区分

- **State** 是工程侧的**确定性会话状态**：当前阶段、当前订单、工具台账、白名单、原诉求。按会话 ID 隔离，跨 flow 保留，是状态机的输入。
- **Memory** 是模型侧的**短期对话记忆**：System prompt、用户消息、assistant 回复、工具调用与结果。按 Memory 命名空间隔离，按 flow 切换，是业务 Agent 推理的上下文。

State 告诉工程"现在到哪一步了"，Memory 告诉模型"刚才聊了什么"。

### D.2 State 保存什么

State 是一个对象，存在 AgentScope 的 Session 里（底层 Redis），按会话 ID 隔离。每一轮准备阶段读、完成阶段写（带版本号自增）。

| 字段 | 内容 | 作用 |
| --- | --- | --- |
| 已提交技能 | 上一轮成功提交的技能组、技能 GUID、技能编码 | 判断本轮是否"同技能同订单"；状态机据此决定 `RESET` 还是沿当前流程推进 |
| 当前订单 | Agent Redis 单方维护的订单 GUID | 订单作用域隔离的基准；IVR 重复携带的旧订单不能覆盖它 |
| 当前意图 | 路由模型产出的当前核心诉求（最多 12 字） | 注入下一轮路由输入；切单时作为原诉求的首选来源 |
| 当前 reference 状态 | 上一轮已提交的阶段（取证 / 判责 / 协商 / 处置） | **状态机的当前状态唯一来源**——模型不输出这个值，只由工程缓存提供 |
| 状态摘要 | 状态名 + 上一轮回复前 160 字 | 注入路由输入，让路由模型知道上一阶段谈到了什么 |
| Memory 命名空间 | 当前业务 Agent Memory 的 namespace | 跨轮沿用同一 Memory；`RESET`/`RESTART`/切单成功时换新或置空 |
| 最近对话 | 最近 6 轮用户 + assistant 消息对 | 注入路由输入；Memory 重置时通过 carryOver 注入业务 Agent，让上下文不断得太干净 |
| 工具台账 | 本会话已执行过的工具，按工具编码去重只留最新一次，上限 20 | 跨 flow 保留，补 Memory 隔离的缺口——见 D.4 |
| 查单白名单 | 查单工具命中过的订单号，上限 40 | 切单目标必须精确命中白名单，拦截模型编造的订单号 |
| 待确认候选订单 | 上一轮列表查单唯一命中的订单 | 模型提交 `SWITCH` 但漏传目标时用它补齐 |
| 原诉求 + 续接标志 | 切单前暂存的原始诉求 + 是否可续接 | 切单成功后下一轮静默时自动续接，用户不用重说 |
| IVR STM 注入轮数 | 已注入过智子阶段短期记忆的轮数，上限 3 | 只在托管前三个正常用户轮次注入 STM，避免长期注入 |
| 版本号 + 更新时间 | 乐观锁版本，每次保存自增 | 完成时比对版本号，不一致整轮放弃回写 |

State 的核心特征：**跨 flow 保留**。换技能、换订单、状态机重启时，State 里的大部分字段会被主动清理（旧订单的技能进度、工具台账、白名单），但最近对话和原诉求保留——下一轮从 State 取出来注入业务 Agent，让上下文不断得太干净。

### D.3 Memory 保存什么

Memory 是 AgentScope 框架的 `AutoContextMemory`，存在 AgentScope 的 Session 里（底层 Redis），按 **Memory 命名空间**隔离（不是会话 ID）。业务 Agent 每轮加载历史、推理、保存。

| 内容 | 说明 |
| --- | --- |
| System prompt | 当前技能的 reference 正文、可见工具说明、规则约束 |
| 用户消息 | 本轮用户输入（可能合并了澄清上下文） |
| Assistant 回复 | 模型流式产出的文本 |
| 工具调用 | 模型发起的 `tool_use`（工具名 + 入参） |
| 工具结果 | 工具执行后回写的 `tool_result`（输出文本） |

`AutoContextMemory` 有两份存储：

- **working**：发给模型的那份，会清洗（媒体占位、旧订单预取失效）和压缩。
- **original**：完整原始消息列表，压缩后仍保留，用于审计和 `context_reload` 恢复。

上下文压缩：当 token ≥ `maxToken × tokenRatio` 或消息条数 ≥ `msgThreshold` 时触发，按 6 种策略依次尝试（连续工具调用压缩、大消息卸载、历史轮次摘要等）。压缩配置在 `MemoryConfig` 里，默认窗口 131072 token、比例 0.6、消息条数 200。

Memory 的核心特征：**按 flow 隔离**。`RESET` 和 `RESTART` 时换新命名空间（带 UUID），旧 Memory 被 `clearExecutionMemory` 清掉；切单成功后旧订单的 Memory 也清掉。这样换流程时模型不会带着上一流程的工具调用历史继续推理。

### D.4 为什么要分两份

光有 Memory 不够，光有 State 也不够，必须两份配合。

**只有 Memory 会出什么问题**：Memory 按 flow 隔离，跨技能或状态机重启时旧 Memory 被清掉，已经执行成功的写操作（如改判）会从模型视野里消失。模型看不到"已经改过判了"，会重复提出同一个动作。状态机也读不到"上一轮工具失败"，无法在下一轮把 `NEXT` 降级为 `HOLD`。

**只有 State 会出什么问题**：State 只存"已提交的结论"，不存模型推理过的完整消息链。业务 Agent 每轮要带着历史对话和工具结果继续推理，没有 Memory 就等于每轮从零开始，模型连上一句用户说什么都不知道。

**两份配合的分工**：

- State 存"确定性结论"：当前阶段、当前订单、工具台账、白名单、原诉求。是状态机的输入，是工程判断的依据。
- Memory 存"推理过程"：System prompt、对话、工具调用与结果。是业务 Agent 的上下文，是模型推理的依据。

State 的工具台账就是为了补 Memory 隔离的缺口：Memory 被清掉后，台账把上一轮执行过的工具结果重新注入业务 Agent 输入（通过 carryOver），让模型知道"改判已经做过了，别再提"。

### D.5 一轮里两者怎么协作

以一次"协商后用户同意，模型要执行改判"的轮次为例：

1. **准备阶段读 State**：读出当前阶段 = 协商、当前订单、上一轮工具台账（空）、Memory 命名空间。
2. **路由模型提议**：路由模型看到注入的 cached_state（当前阶段 = 协商）和最近对话，提议 `NEXT`。
3. **工程算态**：状态机从协商推进到处置（`ADVANCE`）；同技能同订单，Memory 命名空间沿用。
4. **业务 Agent 执行**：加载 Memory（含协商阶段的对话历史），模型看到用户同意，调用改判工具。改判工具执行成功，结果写入 Memory 的 `tool_result`。
5. **完成阶段回写 State**：
   - 推进当前阶段 = 处置。
   - 把改判工具结果并入工具台账（`toolCode = 改判`，`status = SUCCESS`）。
   - 追加对话。
   - 版本号自增，写回 Redis。
   - 保存 Memory（`agent.saveTo`，把本轮消息链持久化）。

下一轮如果用户问"刚才改判了吗"：

- State 的工具台账里有改判成功记录，工程知道"已经改过"。
- Memory 里有完整的改判对话和工具结果，模型也能看到"已经改过"。

但如果下一轮换了技能（State 走 `RESET`、Memory 换新命名空间）：

- Memory 被清掉，模型看不到改判记录。
- State 的工具台账**跨 flow 保留**，通过 carryOver 注入业务 Agent，模型还是能看到"上一笔订单改判已经做过"。

### D.6 隔离与清理对照

| 场景 | State | Memory |
| --- | --- | --- |
| 同技能同订单，`CONTINUE`/`ADVANCE` | 沿用，推进当前阶段 | 沿用同一命名空间，追加本轮消息 |
| 同技能同订单，`RESTART`（末态回首态） | 当前阶段回到首态 | 换新命名空间，旧 Memory 清掉 |
| 换技能或换订单（`RESET`） | 当前阶段回到新流程首态 | 换新命名空间，旧 Memory 清掉 |
| 切单成功提交 | 清掉旧订单的技能进度、工具台账、白名单；保留最近对话和原诉求 | 旧订单 Memory 清掉，新订单从空 Memory 开始 |
| 并发版本过期 | 整轮放弃回写 | 清掉这次还没提交的新 Memory |
| 路由/装配失败降级主 Agent | 不推进技能/reference，只保存对话 | 沿用降级 Memory 命名空间 |

注意：State 的"清掉"是字段级清理（只清旧订单作用域的内容），不是整个对象删掉；Memory 的"清掉"是整个命名空间删除，下一轮从空 Memory 开始。

### D.7 面试追问要点

**State 和 Memory 有什么区别。** State 是工程侧的确定性会话状态，按会话 ID 隔离，跨 flow 保留，存当前阶段、订单、工具台账、白名单、原诉求；Memory 是模型侧的短期对话记忆，按 Memory 命名空间隔离，按 flow 切换，存 System prompt、对话、工具调用与结果。State 是状态机的输入，Memory 是业务 Agent 推理的上下文。

**为什么 Memory 要按 flow 隔离。** 换技能或状态机重启时，模型不应该带着上一流程的工具调用历史继续推理。比如改判流程结束进入下一个技能，模型不该还看得到改判工具的调用记录，否则会混淆当前阶段的可用工具。按 flow 隔离让每个流程从干净的上下文开始。

**为什么 State 要跨 flow 保留工具台账。** Memory 按 flow 隔离后，已经执行成功的写操作会从模型视野里消失，模型会重复提出同一个动作。工具台账按工具编码去重只留最新一次，跨 flow 保留，下一轮通过 carryOver 注入业务 Agent，让模型知道"这个写操作已经做过了"。

**Memory 命名空间什么时候换。** `RESET` 和 `RESTART` 时换新的（带 UUID），其他动作沿用原来的；切单成功后旧订单的 Memory 也清掉。换新命名空间时旧的会被 `clearExecutionMemory` 删除，不是留着等过期。

**State 的版本号干什么用。** 乐观锁。准备阶段生成执行计划时记下当时的版本号，完成阶段回写前再读一次缓存比对版本号，不一致说明中间已有别的轮写过，整轮放弃回写，并清掉这次还没提交的 Memory。每次保存版本号自增。

**State 里的最近对话和 Memory 里的对话有什么关系。** State 里的最近对话是给路由模型看的（最近 6 轮），路由 Agent 禁用框架自动累积的会话历史，工程显式注入这段对话作为决策上下文。Memory 里的对话是给业务 Agent 看的（完整消息链），业务 Agent 跨轮累积推理。Memory 重置时，State 的最近对话通过 carryOver 注入业务 Agent，让上下文不断得太干净。

**切单成功后哪些清掉哪些保留。** 清掉旧订单的技能进度、工具台账、白名单、Memory；保留最近对话和原诉求。保留是为了下一轮重新路由时模型还能看到用户原来想干什么；清掉是因为这些属于旧订单作用域，带入新订单会污染。

## 附录 E：壳 Agent、技能组与 Skill 落表流程

> 这部分回答"Skill 从哪来、Agent 怎么知道用哪些 Skill"。正文阶段 1「读缓存与候选技能解析」说"解析配置里的技能组"，但没说技能组从哪来、Skill 怎么进 DB。本附录补这个前置。
>
> 适用范围：V2 热线托管（`css-agent-server` expert 包）。zuche 模块是本地 `SKILL.md` 随 jar 打包、启动时扫描编译注册，不走这套 DB 流程，见 E.7 对照。

### E.1 壳 Agent 是什么

壳 Agent（shell agent）是 DB 里 `t_css_agent` 表的一条 Agent 记录（`AgentPO`），是某个业务线/渠道的"外壳配置"。代码里 `MainAgentTurnExecutor`、`MainAgentNode` 都有 `AgentPO shellAgent` 参数，`AgentChatV3Component:79` 注释写"解析主 Agent 壳及其多 Agent 配置"。

"壳"的意思：它本身不直接做推理，是个**容器**，装着"用哪个路由模型、用哪个承接模型、用哪个非业务意图模型、能用哪些 Skill"这些配置（即 `AgentConfig.expertConfig`）。真正的推理由路由模型 + 业务 Agent + 工具完成，壳 Agent 只声明"这个入口用哪一套配置"。

运行时用户消息进来，先按 `agentCode` 找到壳 Agent（`AgentBuildCacheService.getPublishedAgentByCode`），再用壳 Agent 的 `expertConfig` 驱动整个编排。

### E.2 为什么是"技能组"而不是一个 Agent 一个 Skill

一个业务线（如"租车客服"）对应一个壳 Agent，但一个业务线里有多个业务场景（取消订单、提前还车、车辆询价、车辆故障...），每个场景一个 Skill。所以一个壳 Agent 要处理这一业务线下的所有场景，就得装配**一组 Skill**（技能组），路由模型每轮从这组里选一个最匹配当前用户消息的 Skill。

如果一个壳 Agent 只装一个 Skill，路由模型就没必要存在——每轮都是同一个 Skill。路由模型的意义就是"从多个候选里选"。

`ExpertConfig.skillGroup` 是 `List<SkillGroupDTO>`（一个壳 Agent 可以有多个技能组），每个 `SkillGroupDTO` 里有 `skillGuids`（一组 Skill guid）和 `needOrder`（这组 Skill 是否需要订单信息）等属性（`SkillGroupDTO.java:11-20`）。分组是为了给一组 Skill 挂公共属性（比如"这组都需要订单"），不是简单的扁平 guid 列表。

### E.3 Skill 在 DB 里的三张表

| 表名 | PO | 存什么 |
|------|-----|--------|
| `t_css_agent_skill` | `AgentSkillPO` | Skill 定义本身：guid/code/name/content/stateFlow/toolGuids/status/versionNo |
| `t_css_skill_config` | `SkillConfigPO` | Skill 的知识库绑定：code/kbGuid/knowledgeGuid/channel |
| `t_css_skill_resource` | `SkillResourcePO` | Skill 的资源文件（发布时克隆用） |

`AgentSkillPO` 关键字段（`AgentSkillPO.java`）：

- `code`：全局唯一编码，必须以 `_skill` 结尾。
- `content`：Skill 定义正文（Markdown）。
- `stateFlow`：Skill 启用的 reference 状态列表（JSONB），顺序即执行顺序。
- `toolGuids`：关联的工具 GUID 列表（JSONB）。
- `status`：1=草稿 / 2=已发布 / 3=已下线。
- `versionNo`：版本号。

### E.4 H5 后台建 Skill 落表流程

运营在 H5 后台点按钮，前端调 `/skill/v2/*` 接口（`SkillV2Controller`），服务端 `SkillV2ServiceImpl` 落表。四步：

**第 1 步：建技能（`/skill/v2/create` → `createSkill`，:99）**

校验 code 必须以 `_skill` 结尾、code 全局唯一 → new `AgentSkillPO`，填 guid/code/shortCode/name/description/appType/businessType/stateFlow，**status = DRAFT** → `agentSkillMapper.insert` → 落 `t_css_agent_skill`。草稿状态，运行时不会用。

**第 2 步：绑知识库（`/skill/v2/configKb` → `configKb`，:80）**

new `SkillConfigPO`，填 code/knowledgeGuid/kbGuid/channel → `selectByCode` 查不到就 `insert`，查到就 `updateByCode` → 落 `t_css_skill_config`。

**第 3 步：改全局配置（`/skill/v2/updateGlobal` → `updateGlobal`，:127）**

更新 `AgentSkillPO` 的 name/description/appType/businessType/stateFlow → `agentSkillMapper.updateByCode` → **发 MQ 通知缓存刷新**（`MqHelper.sendMq(NOTIFY_TOPIC, cacheUpdateMsg)`，type="skill"）。

**第 4 步：发布（`/skill/v2/publish` → `publishSkill`，:283）**

校验必须是草稿状态 → 把原记录 `status` 改成 `PUBLISHED` + 写 `versionNo` + `releaseNote` → **克隆一份新的草稿**（新 guid，同 code，status=DRAFT）→ `cloneSkillResources` 把资源也克隆到新草稿。

发布的设计：发布后原版本变"已发布"（运行时用这个），同时产生一个新草稿供下次修改。运行时读"已发布"版本，运营改"草稿"版本，互不影响。

### E.5 运行时怎么从 DB 装配候选表

`ConversationOrchestrator.prepareForStream`（正文阶段 1）里：

1. `AgentBuildCacheService.getPublishedAgentByCode(agentCode)` → 查 `t_css_agent`（带 Caffeine 缓存）→ 拿到壳 `AgentPO`。
2. 取 `agentPO.getAgentConfig().getExpertConfig().getSkillGroup()` → 拿到 `List<SkillGroupDTO>`。
3. `buildCandidates(expertConfig)`（`ConversationOrchestrator.java:648`）遍历每个 group 的 `skillGuids` → `agentBuildCacheService.getResolvedSkills(guids)` → 查 `t_css_agent_skill`（按 guid 取已发布版本）→ 拿到 `ResolvedSkillDefinition`（含 code/content/stateFlow）。
4. 组装成候选表 `Map<skillCode, SkillCandidate>`。
5. 路由模型从候选表里选一个 Skill（正文阶段 2）。

整条链路：

```
运营在 H5 后台建 Skill → 落 t_css_agent_skill（草稿）+ t_css_skill_config（绑知识库）
  → 改配置 + 发 MQ 刷缓存
  → 发布 → 原记录变已发布 + 克隆新草稿
  → 运营配壳 Agent → 填 expertConfig.skillGroup（引用 Skill guid）→ 落 t_css_agent
  → 用户进线 → 按壳 Agent code 查 DB 拿 AgentPO → 取 skillGroup → 查 t_css_agent_skill 拿 Skill 定义
  → 组装候选表 → 路由模型选一个 Skill
```

### E.6 缓存刷新靠 MQ

`AgentBuildCacheService` 用 Caffeine 缓存壳 Agent 和 Skill 定义，避免每轮都查 DB。改完 DB 后缓存还是旧值，靠 MQ 通知刷新：

- `updateGlobal` 改完 Skill 后发 `MqConstants.NOTIFY_TOPIC` 消息，type="skill"，key=skillCode。
- 消费端收到消息后失效对应的 Caffeine 缓存条目，下次查询重新从 DB 加载。

所以"改 DB 不发版"是对的，但"立即生效"要看 MQ 刷新——MQ 消费延迟内运行时可能还读到旧值。

### E.7 和 zuche 本地 SKILL.md 的区别

| 维度 | V2 expert（本附录） | zuche |
|------|---------------------|-------|
| Skill 载体 | DB 表 `t_css_agent_skill` 等 | 本地 `resources/skills/zuche/**/SKILL.md` + `meta.yaml` + `ivr.yaml` |
| 加载时机 | 运行时按需查 DB（带 Caffeine 缓存） | 启动时 `ZucheSkillManager.@PostConstruct` 扫描编译注册 |
| 改 SOP | 改 DB 配置，发 MQ 刷缓存，不用发版 | 改 SKILL.md，重新打 jar 发版 |
| 路由 | 路由模型从候选表选 Skill | `meta.yaml` covers/excludes 关键词 + 小模型分类 |
| 状态机 | `ReferenceStateMachine` 四态 | `SkillBranchRuntimeEngine` 按 SOP 编译产物执行分支 |

两套是同一仓库的不同模块，别混说。zuche 详见面试稿 Q14/Q16。

### E.8 面试追问要点

**壳 Agent 是什么。** DB 里 `t_css_agent` 的一条记录，装着 expertConfig（路由模型、承接模型、非业务意图模型、技能组）。本身不做推理，是个容器，声明"这个入口用哪一套配置"。运行时按 agentCode 查 DB 拿到壳 Agent，再用它的 expertConfig 驱动编排。

**一个 Agent 为什么装一组 Skill 而不是一个。** 一个业务线对应一个壳 Agent，但一个业务线有多个业务场景，每个场景一个 Skill。路由模型每轮从这组里选一个最匹配的 Skill。只装一个就不需要路由模型了。

**Agent 怎么知道用哪些 Skill。** 壳 Agent 配置里有 `expertConfig.skillGroup`（`List<SkillGroupDTO>`），每个组引用一组 Skill guid。运行时 `buildCandidates` 用这些 guid 从 DB 查出 Skill 定义，组装成候选表给路由模型选。

**Skill 怎么从 H5 后台到运行时。** 运营建技能落 `t_css_agent_skill`（草稿）→ 绑知识库落 `t_css_skill_config` → 改配置发 MQ 刷缓存 → 发布变已发布 + 克隆新草稿。运行时按 guid 查已发布版本，组装候选表。

**改 SOP 要发版吗。** V2 不用，改 DB 配置 + 发 MQ 刷缓存即可。zuche 要，改 SKILL.md 重新打 jar 发版。两套不同。

**缓存怎么刷新。** 改完 DB 后发 MQ（`NOTIFY_TOPIC`，type="skill"），消费端失效 Caffeine 缓存条目，下次查询重新从 DB 加载。MQ 消费延迟内可能还读到旧值。

**诚实边界。** 壳 Agent 表名 `t_css_agent` 是从 `AgentSkillPO.java:9` 注释风格推断的（`AgentSkillPO` 注释明确写"表：t_css_agent_skill"），`AgentPO` 本身没看到表名注释，需进一步核实；MQ 消费端的具体刷新逻辑没追，深问需补。

## 附录 F：V2 用户确认门禁方案（提案 + 批判性评审）

> 本附录记录一份针对"协商→处置推进时用户确认缺工程门禁"的架构提案，以及对其的批判性评审。用于沉淀设计思考，**非已实现功能**。

### F.1 背景与问题

当前 V2 状态推进流程：

```
路由模型理解对话
→ 输出 NEXT/HOLD/RESTART
→ 工程侧校验同一 Skill、同一订单、当前状态等
→ ReferenceStateMachine 推进状态
```

协商态进入处置态时，用户是否已接受退款方案，主要依赖路由模型输出 `NEXT`。

现有工程校验能防跳状态、串订单、关联工具失败后继续推进（`ConversationOrchestrator.resolveEffectiveTransition`，:810-843），但**不能证明用户真的确认了退款方案**。模型可能把"好吧"等模糊表达误判为同意，也可能直接幻觉"用户已经确认"。

**关键认知**（本附录前几轮已坐实）：状态机防的是**状态幻觉**（不信模型复述的 currentState，只信缓存里上轮已提交的状态），**不防同意幻觉**——状态机看不到用户消息，只接收路由模型的 NEXT/HOLD/RESTART 建议；用户是否同意是路由模型读上下文判断的，状态机只消费这个判断结果。

### F.2 提案核心思路

保留现有路由模型和状态机结构，不取消模型的 `NEXT`。新增工程侧用户确认门禁：

> 模型仍负责输出 `NEXT`；工程侧只有在 Redis 中找到与当前退款方案完全匹配的用户确认凭证时，才接受该 `NEXT`，否则降级为 `HOLD`。

做成公共能力，既供热线托管 V2 使用，也供其他托管模式和普通客服 Agent 使用。

### F.3 提案核心流程

**1. 生成待确认操作**：Agent 给出退款方案后，服务端不立即执行，创建待确认记录（`pendingId/sessionId/userId/orderGuid/skillGuid/actionType=REFUND/toolCode/refundAmount/toolArgs/actionHash/offerVersion/stateVersion/status=PENDING/expiresAt`），通过 SSE 返回确认卡片。

**2. 用户确认**：用户点"确认退款"后前端回传 `pendingId + decision=APPROVE`。前端不能自行提交退款金额、工具参数或可信的 `confirmed=true`。服务端按 `pendingId` 查原始记录，校验用户/会话/订单/有效期，状态 `PENDING → APPROVED`，并向模型上下文加入可信系统事件（"用户已确认订单123退款20元，actionId=abc"），只帮模型理解后续流程，不作执行授权。

**3. 保留模型 NEXT**：下一轮路由模型读确认事件，仍按现有协议输出 `stateTransition=NEXT`，模型保留状态流转建议权。

**4. 工程侧校验 NEXT**：在 `ConversationOrchestrator.resolveEffectiveTransition` 增加确认校验（不让 `ReferenceStateMachine` 直接访问 Redis）：

```java
if (transition == NEXT
        && committedState == NEGOTIATION
        && requiresUserConfirmation(action)
        && !confirmationStore.hasMatchingApproval(
                sessionId, orderGuid, skillGuid,
                actionType, amount, actionHash, stateVersion)) {
    return HOLD;
}
```

### F.4 提案匹配要求

不能只查 `confirmed=true`，必须确认用户批准的是当前这笔操作：当前用户和会话、当前订单、当前 Skill、当前退款金额、当前工具和参数、当前方案版本或状态版本、记录未过期、记录未被消费。例：用户确认的是退20元，模型随后准备退30元，校验必须失败。

### F.5 提案工具执行门禁

状态推进校验通过后，退款工具真正执行前还应再次校验，并原子消费确认凭证：`APPROVED → EXECUTING → EXECUTED`。要求：原子状态更新避免双击并发；工具调用带幂等键；执行冻结在 Redis 中的工具和参数；不允许模型在确认后重新修改退款金额；执行前重新检查订单状态和业务约束；失败时区分可重试和终态失败。

### F.6 提案普通 Agent 复用

V2 和普通 Agent 使用同一个 `UserConfirmationGate`，接入位置不同：

- V2：`模型 NEXT → 用户确认门禁 → 状态机推进 → 写工具执行`
- 普通 Agent：`模型 tool_call → 用户确认门禁 → 写工具执行`

抽象公共组件：`PendingUserActionStore` / `UserConfirmationGate` / `UserActionConfirmService` / `ConfirmedActionEvent`。工具配置声明 `confirmationMode=NONE/USER/OPERATOR`，只有退款、取消订单等需用户授权的写操作启用 `USER`。

### F.7 提案复用现有实现

1. `css-zuche-agent` 已实现 `PENDING_CONFIRM → 用户确认 → 服务端直接执行写动作`，可参考业务流程和待确认台账。
2. `css-agent-server` HITL 已有 `pendingId + approved` 请求、待确认工具和参数缓存、确认恢复接口，但当前只对 `TEST` 渠道启用（`AgentChatServiceImpl.java:648` 用 `SessionChannelEnum.TEST.getCode()`），语义是客服/测试人员审批，不能直接当成顾客授权上线。

建议复用基础存储和暂停思想，但重新抽象用户身份、订单、金额、版本、TTL、原子消费和幂等机制。

### F.8 批判性评审结论：有条件成立

方案识别的是真问题（路由模型 NEXT 不能证明用户真的同意），思路"模型 NEXT + 工程侧凭证双重条件"方向对，安全设计（全字段匹配、原子消费、幂等）方向对。但**当前形态在 V2 热线场景落不了地**，需解决两个关键项。

### F.9 关键前提与证据状态

1. **路由模型误判"好吧"为同意是需工程拦截的真实风险** — 待验证。如果路由提示词已强约束"明确同意才 NEXT"，风险可能没想象的高。提示词在 DB（`routerAgentCode` 指向的 Agent 配置），未核实。方案应先确认这个前提，否则可能过度设计。
2. **用户确认卡片能可靠产生** — **不成立/未解决**（见 F.10 失败场景1）。方案最大盲点。
3. **Redis 凭证足够可信** — 待验证。退款是钱，Redis 单点 + 持久化策略影响可靠性。
4. **门禁放在状态推进时比放在工具执行时更合适** — 存在争议（见 F.11 替代方案）。

### F.10 主要失败场景

**1. 热线渠道无法产生可信确认事件（严重程度：高）**

V2 是**热线托管**，用户打电话进来，IVR 转文本，Agent 流式生成回复再 TTS 播报。**用户没有前端 UI，点不了"确认退款"按钮。** 提案的 SSE 确认卡片是 IM 场景设计，热线场景完全用不上。

热线用户能做的只有：
- IVR 按数字键（"按1确认"）——但要和 IVR 系统对接，把按键事件转成带 `orderGuid/skillGuid/refundAmount/actionHash` 的 APPROVED 记录，这些字段按键事件本身不带，要从当前协商方案上下文取，取的时机和一致性是大问题。
- 语音说"确认退款"——又回到模型理解语音，"好吧"误判问题没解决，方案白做。

提案把这条列在"待审核问题"但没给方案。**如果热线渠道产生不了可信确认事件，整个门禁在 V2 热线场景就是空的**——这是决定性问题，不是边缘情况。

**2. 门禁放在状态推进时，匹配字段难（严重程度：中）**

提案把门禁放在 `resolveEffectiveTransition`（协商→处置推进时）。但推进时**金额/工具/参数可能还没最终确定**：协商态模型说"退20元"，到了处置态模型可能根据查询结果改"实际能退30元"。这时 Redis 里的 APPROVED 记录是20元，模型要退30元，对不上。

提案说"用户确认的是20元，模型准备退30元，校验必须失败"——方向对，但**失败之后怎么办**没说。回退协商态让模型重新报价？拦截报错？用户体验和状态机回归路径都没设计。这个场景在退款流程里很常见（查到新信息改方案），不是边缘。

**3. 用户确认了但模型给 HOLD（严重程度：中）**

用户点了确认（Redis 有 APPROVED），下一轮路由模型却给 HOLD（比如用户确认后又说了句无关的话）。如果保持 HOLD：用户确认了但流程不推进，体验卡死。如果工程侧覆盖成 NEXT：削弱模型建议权，且模型可能是有理由的 HOLD（用户确认后又改口"算了不退了"）。设计两难，方案必须明确选一个并说清理由。

**4. Redis 凭证可靠性（严重程度：中）**

退款是钱。Redis 凭证若因未持久化/故障丢失，用户确认了但凭证没了，流程卡住或要用户重新确认（热线场景重新确认体验很差）。提案说原子消费+幂等键方向对，但 Redis 单点不够——退款凭证应 DB + Redis 双写，DB 为准、Redis 加速。提案没提这点。

### F.11 关键反例

**热线退款金额变化场景**：用户打电话要退款。AI 协商态说"商家同意退20元，按1确认"。用户按1。IVR 把按键事件发后端。后端从当前协商方案上下文取金额20元，写 APPROVED 记录。状态推进到处置态。处置态模型调退款工具，但此时查到订单实际扣款是30元，模型把退款金额改成30元传给工具。工具执行门禁校验"APPROVED 记录20元 vs 工具调用30元"——失败拦截。**但用户其实只确认了20元，30元用户没确认，流程卡在处置态进退两难**：回协商态重新报价要再让用户按一次键，直接执行30元没用户授权。

这个反例说明：**金额在协商→处置之间可能变化，而用户确认只锁了协商态那一刻的金额，处置态改金额后旧凭证失效，方案没设计"改方案要重新确认"的回路。**

### F.12 替代方案：门禁放在工具执行时

**把门禁主要放在"工具执行时"而不是"状态推进时"**：

```
模型 NEXT → 状态机正常推进到处置态（不加门禁）
→ 处置态模型调退款工具（工具调用带金额/工具/参数）
→ 工具执行前校验 Redis APPROVED 凭证（全字段匹配，此时字段都确定）
→ 匹配：原子消费 + 执行；不匹配：拦截，模型重新报价走确认
```

优势：
- 工具执行时金额/工具/参数都已确定，全字段匹配简单可靠，不存在"推进时金额还没定"的问题
- 状态机保持原样不动，侵入小
- 和现有 HITL（`hitlEnabled`）同层，只是审批人从"客服/运营"换成"用户"，复用现有基础设施更自然
- 金额变化场景天然处理：模型改金额→新工具调用→旧凭证对不上→拦截→模型回协商态重新报价

劣势：
- 失去"状态推进前就早拦"——但早拦的匹配字段难，早拦价值有限
- 处置态模型可能调了工具才被拦，多一轮推理开销——但比状态推进时字段对不上卡死强

### F.13 修正结论与改进建议

方案**核心思路成立**，但**当前形态在 V2 热线场景落不了地**，需解决两个关键项：

1. **热线渠道如何产生可信确认事件**（决定性）：必须先设计 IVR 按键事件 → 带全字段 APPROVED 记录的转换链路，包括金额/订单/skillGuid 从当前协商方案上下文取的时机和一致性。这一步不解决，方案在热线场景是空的。建议先做这个 PoC，跑通了再谈后面。

2. **门禁位置改到工具执行时**：放在 `resolveEffectiveTransition` 匹配字段难、金额变化卡死；放在工具执行前（`confirmationMode=USER`，和 `hitlEnabled` 同层）匹配字段确定、状态机不侵入、复用 HITL 基础设施。状态推进时只做轻校验（协商态有未消费 APPROVED 才建议 NEXT，但不强制）。

其他建议：
- 凭证存储 DB + Redis 双写，DB 为准（退款是钱，Redis 单点不够）
- 处置态模型改方案（金额变了）要重新走确认，旧凭证失效，方案要设计这个回路
- 用户确认后模型给 HOLD 的处理：建议**有未过期 APPROVED 就覆盖成 NEXT**，因为用户意愿已明确，模型建议权让位于用户确认；但若用户确认后又有新发言表达反悔，模型 HOLD 是对的——这条要靠路由提示词约束"用户确认后改口要识别"，不能纯靠工程覆盖

### F.14 最值得优先验证的下一步

先核实路由提示词有没有"明确同意才 NEXT"约束（在 DB，`routerAgentCode` 指向的 Agent 配置）。如果提示词已强约束，"好吧误判"风险可能比想象低，方案的必要性要重新评估——可能只需要在工具执行时加 `confirmationMode=USER`，不需要在状态推进时加门禁。

### F.15 诚实边界

- 提案引用的现有实现已核实：`resolveEffectiveTransition`（`ConversationOrchestrator.java:810-843`）只防工具失败还推进；HITL `confirmHitlStream`（`AgentChatServiceImpl.java:648`）只对 `TEST` 渠道；zuche `PENDING_CONFIRM` 模式存在。
- 路由提示词内容在 DB，未核实——这是方案必要性的关键未验证项。
- 热线 IVR 按键事件如何回传后端、能否带全字段，未核实前端/IVR 对接代码。
- 本附录是设计思考沉淀，**非已实现功能**；落地前需先做热线渠道确认事件 PoC。

## 附录 G：具体场景——订单 A 的退款流程中切换到订单 B

### G.1 先看结论

这个场景的主线只有三步：

```text
进线订单 A 先成为会话当前订单
→ 切单 Skill 只能把“查单工具确实返回过的订单”切成新当前订单
→ 成功切到 B 后，清空 A 的业务进度和工具事实，再用 B 重新路由原退款诉求
```

这里没有 `confirm_order` 工具，也没有“当前订单号 + 已确认订单号”两份快照比对。那是另一套编排的机制，不属于热线托管 V2。V2 的关键保护是：

1. `state.orderGuid` 是本通热线会话的当前订单事实。
2. `orderQueryWhitelist` 记录查单工具真正返回过的候选订单，防止模型编造切单目标。
3. 只有切单 Skill 显式输出 `SWITCH`，且目标命中白名单，工程侧才提交切单。
4. 切单成功后，订单 A 的 Skill、reference 阶段、工具事实、白名单和 Memory 全部作废；原诉求和最近对话保留，用于订单 B 重新起流程。

下面按一通真实热线的时间顺序展开。为让状态快照具体，本例假设订单 A 的退款首轮没有执行工具；退款 Skill 的首个 reference 阶段用 `FIRST_REF` 表示，其实际业务名称由已发布 Skill 配置决定，不能仅凭 Java 代码写死为“确认诉求”。

### G.2 初始状态：进线前没有会话状态

用户还未进线时，`agentSession` 中没有该 `sessionId` 对应的 `expert_conversation_state`。`ExpertConversationStateStore.load` 查不到时会返回一个新的空状态对象，但只有调用 `save` 后才真正持久化。

```text
orderGuid = null
activeSkillGuid = null
currentState = null
executedTools = []
orderQueryWhitelist = []
pendingConfirmOrderGuid = null
pendingResumeMessage = null
pendingResumeReady = null
```

注意：`expert_conversation_state` 是状态对象在 Agent Session 中的逻辑 key；本文不把它描述成已经核实过的物理 Redis 完整 key。

### G.3 第 1 轮：用户带订单 A 进线，要求退款

#### 触发和输入

IVR 发起热线托管请求：

```text
sessionParam.orderGuid = "A"
message = "我要退款"
```

#### 第一步：订单 A 先落成进线种子

`AgentChatV2Service.queryStream` 在启动打断竞态和正式编排前调用 `ensureInboundOrderSeed`。只要当前渠道是 `ivr_hosting`、请求中有真实订单号、会话状态里还没有当前订单，就立即保存：

```text
state.orderGuid = "A"
```

这一步早于 `prepare/complete`，解决的是首轮被打断时的订单丢失问题：即使业务 Agent 还没完成，后续轮次也能从会话状态中读到 A。

#### 第二步：路由退款 Skill，并从首阶段开始

路由模型选择退款 Skill。`resolveOrderScope` 先看会话状态，读到 `state.orderGuid=A`，因此本轮订单作用域是 A。

`buildExecutionPlan` 随后判断：

```text
本轮候选 Skill = 退款 Skill
state.activeSkillGuid = null
→ sameSkillAndOrder = false
→ ReferenceStateMachine 返回 RESET
→ 本轮执行退款 Skill 的首个 reference 阶段 FIRST_REF
```

这里容易误解的 `退款SkillGuid::ORDER::A` 是 `ExecutionPlan.referenceStateKey`，表示“本轮计划属于哪个 Skill + 哪个订单作用域”。它不是 Redis key，也不是拿去 Redis 单独查询的缓存键。

#### 第三步：本轮成功后提交状态

业务 Agent 按 `FIRST_REF` 回复完成后，`complete` 才把执行结果提交到会话状态。假设本轮没有调用工具，状态可以理解为：

```text
orderGuid = A
activeSkillGuid = 退款 Skill guid
activeSkillCode = 退款 Skill code
currentIntent = 我要退款
currentState = FIRST_REF
executedTools = []
orderQueryWhitelist = []
pendingConfirmOrderGuid = null
pendingResumeMessage = null
pendingResumeReady = null
```

状态机只在本轮成功完成后提交 reference 阶段，避免模型、工具或流式输出中途失败时把状态提前推进。

### G.4 第 N 轮：用户提出换到订单 B，但 B 还没被查单工具返回

#### 触发和路由

用户说：“其实我要退另一笔订单 B。”路由模型选择切单 Skill。本轮 `resolveOrderScope` 仍返回 A，因为会话当前订单在切单成功前不能提前改成 B。

#### 先暂存原诉求

切单 Skill 正常完成并进入 `complete` 时，`captureOrderSwitchResumeContext` 第一次从业务 Skill 进入切单 Skill，会保存切单前尚未办完的原诉求：

```text
pendingResumeMessage = "我要退款"
pendingResumeReady = false
```

代码保存的是 `currentIntent`，没有固定添加“退款：”前缀；只有路由模型生成的 `currentIntent` 本身带前缀时，缓存里才可能出现该格式。`pendingResumeReady=false` 表示“只是暂存，还不能续接”，因为切单尚未成功。

#### 模型想切 B，工程侧不放行

假设切单模型输出：

```text
orderDecision = SWITCH
targetOrderGuid = B
```

`resolveEffectiveOrderDecision` 会先合并历史工具结果和本轮工具结果，维护查单白名单。本轮没有执行列表查单工具，因此：

```text
orderQueryWhitelist = []
B 不在白名单
→ effectiveOrderDecision = UNKNOWN
→ state.orderGuid 仍为 A
```

流式下发前，`resolveSwitchStreamCompletion` 还会把未经校验的模型切单回复替换为固定安全话术：

```text
抱歉，这笔订单暂时还没有确认成功。
```

#### 这一轮结束后，哪些状态变了

```text
orderGuid = A                         // 没切成
activeSkillGuid = 切单 Skill guid     // 当前已进入切单流程
currentState = 切单 Skill 本轮的状态   // 未绑定 reference 时为 null
executedTools = []                    // 本例仍无工具事实
orderQueryWhitelist = []              // B 尚未被工具查到
pendingConfirmOrderGuid = null
pendingResumeMessage = "我要退款"     // 保留，不会在失败切单轮清掉
pendingResumeReady = false             // 切单未成功，不允许续接
```

这是对一个常见误读的纠正：失败的切单轮本身仍是切单计划，因此不会命中“非切单计划才清理暂存”的分支。原诉求会保留，供后续继续查单并成功切换后再用。

### G.5 第 N+1 轮：查单返回 B、C，本轮明确切到 B

#### 查单结果先进入工程白名单

用户补充手机号等查询条件，切单 Skill 调用订单列表查询工具，工具返回 B 和 C。`resolveEffectiveOrderDecision` 会把本轮工具结果与历史工具事实合并，再由 `mergeOrderQueryWhitelist` 抽取订单号：

```text
orderQueryWhitelist = [B, C]
```

因为最新一次列表查询命中两笔，不是唯一候选，所以 `updatePendingConfirmOrderGuid` 不会保留某一笔作为缺省目标：

```text
pendingConfirmOrderGuid = null
```

`pendingConfirmOrderGuid` 不是“用户已经确认”的标记。它只在列表查询唯一命中一笔、而模型已经显式输出 `SWITCH` 却漏传 `targetOrderGuid` 时，用来补齐目标；多笔命中必须由模型显式给出要切哪一笔。

#### 同一轮可以校验并切到 B

模型本轮输出：

```text
orderDecision = SWITCH
targetOrderGuid = B
```

由于 `resolveEffectiveOrderDecision` 校验前已经合并本轮查单结果，B 在 `[B, C]` 中，本轮即可通过，不需要再等一轮：

```text
B 命中白名单
→ effectiveOrderDecision = SWITCH
→ state.orderGuid: A → B
```

这里工程侧验证的是“B 是否来自可信查单结果”，不是自己理解用户话术。是否输出显式 `SWITCH` 仍由模型根据对话决定；工程侧不会因为用户重复说“B”或多次查到 B，就自行推断用户同意切单。

#### 提交切单后，清理订单 A 的作用域状态

`isCommittedSwitch` 只有在以下三个条件同时成立时才返回 true：

```text
工程校验后的决定是 SWITCH
并且 previousOrderScope != orderScope
并且新 orderScope 是真实订单号
```

本例从 A 切到 B，满足条件，因此 `resetOrderScopedFlowState` 清理订单 A 的状态：

```text
清理：activeGroupCode
清理：activeSkillGuid / activeSkillCode
清理：currentIntent
清理：currentState / stateSummary
清理：executedTools
清理：orderQueryWhitelist
清理：pendingConfirmOrderGuid
清理：executionMemorySessionId，并删除旧执行 Memory

保留：orderGuid = B
保留：recentDialogue
保留：pendingResumeMessage = "我要退款"
```

随后 `markOrderSwitchResumeReady` 把暂存诉求标记为可续接：

```text
pendingResumeReady = true
```

所以本轮最终状态是：

```text
orderGuid = B
activeSkillGuid = null
activeSkillCode = null
currentState = null
executedTools = []
orderQueryWhitelist = []
pendingConfirmOrderGuid = null
pendingResumeMessage = "我要退款"
pendingResumeReady = true
executionMemorySessionId = null
recentDialogue = [...保留跨订单对话...]
```

为什么工具事实和白名单必须清空：它们证明的是订单 A 上发生过什么、查到过什么；带到 B 会让业务 Agent 把 A 的退款结果或候选订单误当成 B 的事实。为什么对话和原诉求保留：它们用于让 B 重新路由时保持上下文连续，但不会恢复 A 的 Skill、reference 阶段或工具执行进度。

### G.6 第 N+2 轮：IVR 静默激活，自动把退款诉求接到订单 B

“下一轮自动续接”需要说准确：当前代码是在**下一次热线静默激活轮**调用 `prepareSilenceReply` 时消费暂存诉求，不是任何请求一进来都无条件注入。

当它看到：

```text
pendingResumeMessage = "我要退款"
pendingResumeReady = true
```

会复制当前请求，把执行消息替换为“我要退款”，再调用正常的 `prepareForStream` 重新路由。由于当前订单已经是 B，而切单提交后 `activeSkillGuid/currentState` 已清空，所以：

```text
resolveOrderScope → B
路由模型重新选择退款 Skill
sameSkillAndOrder = false
ReferenceStateMachine → RESET
订单 B 从退款 Skill 的首个 reference 阶段 FIRST_REF 重新开始
```

这不是恢复订单 A 的旧退款进度，而是“拿保留下来的原诉求，在新订单 B 上重新办一次”。系统把 `currentUserMessage` 设为空，避免把自动续接的“我要退款”再次记成一条真实用户发言。

该非切单轮成功提交后，`clearOrderSwitchResumeContext` 清理暂存：

```text
orderGuid = B
activeSkillGuid = 退款 Skill guid
currentState = FIRST_REF
executedTools = []                    // 在 B 上重新累计
orderQueryWhitelist = []
pendingResumeMessage = null
pendingResumeReady = false
executionMemorySessionId = B 上新建的执行 Memory
```

如果切单成功后用户先主动说了新话，而不是进入静默激活轮，则正常路由以用户的新话为输入；非切单计划成功提交时也会清掉暂存诉求。也就是说，自动续接用于填补用户切单后的静默，不会压过用户新说的话。

### G.7 把整条状态变化压缩成一条线

```text
进线前
  当前订单=null，业务状态=null

第1轮：A + “我要退款”
  A 提前落种子
  → 退款 Skill 在 A 上 RESET 到首阶段
  → 成功提交 A 的退款状态

第N轮：想切 B，但没查过
  暂存“我要退款”，ready=false
  → 模型给 SWITCH+B
  → B 不在白名单，工程拒绝
  → 当前订单仍是 A，原诉求继续保留

第N+1轮：列表工具查到 [B,C]，模型明确选 B
  B/C 进入白名单
  → SWITCH+B 通过
  → 当前订单 A→B
  → 清 A 的 Skill/reference/工具/白名单/Memory
  → 保留原诉求和对话，ready=true

第N+2轮：IVR 静默激活
  用“我要退款”重新路由
  → B 的退款流程从首阶段开始
  → 成功后清 pendingResume，ready=false
```

面试时可以概括为：**V2 切单不是把订单号直接改掉，而是先用查单结果给目标订单做工程白名单校验；切换提交后把旧订单的业务状态整体作废，再通过暂存原诉求，在新订单上重新路由。这样既防模型编造订单，也防旧订单的工具事实和流程进度污染新订单。**
