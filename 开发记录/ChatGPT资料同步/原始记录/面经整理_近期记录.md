# 计算机网络八股文——前 10 题面试回答

## 1. 从输入 URL 到页面展示，发生了什么？

1. **URL 解析与缓存检查。** 用户在浏览器输入 URL 后，浏览器首先解析 URL，确定访问的协议、域名、端口和资源路径，并检查是否能够使用已有的缓存。如果缓存可以直接满足请求，就可以减少后续的网络通信。
2. **DNS 域名解析。** 如果需要向服务器发送请求，浏览器首先通过 DNS 查询将域名解析为服务器的 IP 地址。因为计算机在网络中主要通过 IP 地址定位目标设备，而用户通常使用更容易记忆的域名访问网站。
3. **建立网络连接。** 获得服务器 IP 地址后，浏览器与服务器建立连接。对于常见的 HTTPS over TCP，需要先完成 TCP 三次握手，再进行 TLS 握手，通过证书验证服务器身份、协商加密密钥，建立安全通信通道。
4. **发送 HTTP 请求并接收响应。** 连接建立后，浏览器向服务器发送 HTTP 请求，包括请求方法、请求路径、请求头和必要的请求体。服务器处理请求后，返回 HTTP 响应，其中包含状态码、响应头和 HTML 等资源内容。
5. **浏览器解析和渲染页面。** 浏览器收到 HTML 后，解析生成 DOM 树，解析 CSS 生成 CSSOM 树，然后结合两者构建渲染树，进行布局、绘制和合成，最终将页面显示出来。浏览器还可能继续加载 CSS、JavaScript、图片等资源，其中 JavaScript 的执行也可能修改 DOM 和样式，从而影响页面渲染。

## 2. TCP 三次握手的过程，以及为什么需要三次握手？

1. **第一次握手。** 客户端向服务器发送 SYN 报文，请求建立 TCP 连接，并携带自己的初始序列号 `seq=x`。发送后，客户端进入 `SYN-SENT` 状态。
2. **第二次握手。** 服务器收到 SYN 后，回复 SYN+ACK 报文，其中 `ack=x+1` 表示确认收到客户端的 SYN，同时携带服务器自己的初始序列号 `seq=y`。服务器进入 `SYN-RECEIVED` 状态。
3. **第三次握手。** 客户端收到服务器的 SYN+ACK 后，发送 ACK 报文，确认号为 `ack=y+1`。客户端发送后进入 `ESTABLISHED` 状态，服务器收到这个 ACK 后，也进入 `ESTABLISHED` 状态。这里确认号加 1，是因为 SYN 会占用一个序列号。
4. **为什么需要三次握手？** TCP 建立连接时，双方需要交换并确认各自的初始序列号。如果只有两次握手，服务器发送 SYN+ACK 后无法确认客户端是否收到自己的 SYN，可能出现服务器认为连接已经建立、客户端却没有成功建立连接的情况。第三次握手使服务器能够确认客户端已经收到服务器的连接建立信息。
5. **为什么不需要四次握手？** 服务器在第二次握手时，可以把确认客户端 SYN 的 ACK 和自己的 SYN 合并在同一个报文中发送，因此通常只需要三次交互就能够完成连接建立。

## 3. TCP 四次挥手的过程，以及为什么需要四次挥手？

1. **第一次挥手。** 客户端主动发送 FIN 报文，表示自己已经没有数据需要发送，请求关闭自己的发送方向。发送后进入 `FIN-WAIT-1` 状态。
2. **第二次挥手。** 服务器收到客户端的 FIN 后，回复 ACK 报文，确认收到关闭请求，并进入 `CLOSE-WAIT` 状态。客户端收到 ACK 后进入 `FIN-WAIT-2` 状态。此时客户端不再发送新的应用数据，但仍然可以接收服务器发送的数据。
3. **第三次挥手。** 服务器完成剩余的数据发送后，向客户端发送 FIN 报文，表示服务器也准备关闭自己的发送方向，随后进入 `LAST-ACK` 状态，等待客户端的最终确认。
4. **第四次挥手。** 客户端收到服务器的 FIN 后，回复 ACK 报文，进入 `TIME_WAIT` 状态。服务器收到这个 ACK 后进入 `CLOSED` 状态，而客户端通常需要等待 `2MSL` 后再关闭连接。
5. **为什么通常需要四次挥手？** 因为 TCP 是全双工通信，两个方向的数据传输可以独立关闭。服务器收到客户端的 FIN 时，可能还有剩余数据需要发送，所以会先回复 ACK，等自己的数据发送完成后再发送 FIN。因此 ACK 和 FIN 通常需要分开发送。如果服务器也已经准备好关闭，这两个报文也可以合并。
6. **TIME_WAIT 的作用。** 第一，如果客户端最后发送的 ACK 丢失，服务器可能重新发送 FIN，处于 TIME_WAIT 状态的客户端仍然能够重新回复 ACK。第二，等待 `2MSL` 可以让旧连接中可能残留的报文有时间过期，降低这些报文干扰后续连接的风险。

## 4. TCP 和 UDP 有什么区别？

1. **连接方式不同。** TCP 是面向连接的协议，传输数据前需要通过三次握手建立连接，并维护相应的连接状态。UDP 是无连接协议，发送数据前不需要进行 TCP 式的连接建立过程。
2. **可靠性不同。** TCP 提供可靠、有序的数据传输，通过序列号、确认应答、超时重传等机制处理数据丢失和乱序问题，并通过流量控制和拥塞控制调节发送行为。UDP 本身不保证数据一定到达，也不保证报文按照发送顺序到达，不提供 TCP 式的自动重传机制。
3. **数据传输形式不同。** TCP 是面向字节流的协议，将应用程序发送的数据组织为连续的字节序列，不保留每次发送时的消息边界。UDP 是面向数据报的协议，会保留每个数据报的边界，但数据报可能丢失或乱序。
4. **协议开销不同。** TCP 需要维护连接状态，并执行确认、重传、流量控制和拥塞控制等操作，因此协议机制相对复杂。UDP 的首部固定为 8 字节，而普通 TCP 首部至少为 20 字节，UDP 的协议机制更加简单，开销通常更低。不过实际传输性能仍然取决于网络条件和应用实现。
5. **应用场景不同。** TCP 适合文件传输、数据库连接、SSH 等对可靠性要求较高的场景。UDP 适合 DNS 查询、实时音视频和部分在线游戏等更关注实时性的场景。另外，基于 UDP 的应用也可以自行实现可靠传输，例如 HTTP/3 使用的 QUIC 协议。

## 5. HTTP 常见状态码和请求头字段有哪些？

1. **1xx：信息性响应。** 表示服务器在处理请求过程中提供的信息。例如 `100 Continue`，表示客户端可以继续发送请求体。
2. **2xx：请求成功。** 常见的有 `200 OK`，表示请求成功；`201 Created`，表示成功创建资源；`204 No Content`，表示请求成功，但没有响应体。
3. **3xx：重定向及缓存相关响应。** 常见的有 `301 Moved Permanently`，表示永久重定向；`302 Found`，通常用于临时重定向；`304 Not Modified`，表示缓存验证后资源没有发生需要重新下载的变化，客户端可以继续使用已有缓存。
4. **4xx：客户端请求错误。** 常见的有 `400 Bad Request`，表示请求存在问题；`401 Unauthorized`，表示缺少有效的身份认证；`403 Forbidden`，表示服务器拒绝访问；`404 Not Found`，表示请求的资源不存在。其中 401 主要涉及认证，403 主要涉及访问被拒绝。
5. **5xx：服务器错误。** 常见的有 `500 Internal Server Error`，表示服务器内部错误；`502 Bad Gateway`，表示网关从上游服务器收到无效响应；`503 Service Unavailable`，表示服务暂时不可用；`504 Gateway Timeout`，表示网关等待上游服务器响应超时。
6. **常见 HTTP 头字段。** `Host` 用于指定目标主机；`Content-Type` 表示消息体的数据类型，例如 JSON；`Content-Length` 表示消息体的字节长度；`Content-Encoding` 表示消息体采用的内容编码方式，例如 gzip；`Authorization` 用于携带身份认证信息；`Cache-Control` 用于控制缓存策略；`Connection` 在 HTTP/1.1 中可用于连接管理。

## 6. GET 和 POST 请求有什么区别？

1. **用途不同。** GET 主要用于获取资源，例如查询用户信息、获取图书详情；POST 主要用于向服务器提交数据并进行处理，例如创建订单、提交表单或者上传数据。
2. **参数传递方式不同。** GET 通常通过 URL 中的查询参数传递筛选条件，例如 `/books?page=2`。POST 通常通过请求体提交数据，可以使用 JSON、表单或者文件等格式。不过 POST 也可以同时携带 URL 查询参数。
3. **安全性不同。** 在 HTTP 协议语义中，GET 属于安全方法，也就是请求本身应当用于只读操作，不要求修改服务器资源状态；POST 允许执行创建资源等改变服务器状态的操作。另外，在信息安全方面，GET 的 URL 参数可能出现在浏览器历史记录或访问日志中，因此不适合放置密码等敏感信息。实际的传输加密主要依靠 HTTPS。
4. **幂等性不同。** GET 在 HTTP 语义上是幂等的，即重复执行相同请求，不会额外改变资源的预期状态。POST 默认没有幂等保证，例如重复发送创建订单的请求，可能创建多条订单。因此，支付、订单创建等业务通常需要通过唯一请求编号、幂等键等机制避免重复处理。
5. **缓存机制不同。** GET 请求的响应通常更容易被浏览器或代理缓存，适合重复获取相同资源的场景。POST 响应也可以在满足特定条件时被缓存，但实际使用较少，缓存条件相对严格。
6. **数据传输方面。** GET 的 URL 长度和 POST 的请求体大小都可能受到浏览器、服务器或代理配置的限制。POST 通常更适合提交结构复杂或体积较大的数据，具体选择仍然需要结合接口的业务语义。

## 7. 什么是强缓存和协商缓存？

1. **HTTP 缓存的作用。** HTTP 缓存主要用于减少重复的网络请求和资源传输，从而提高页面加载速度、节省带宽并降低服务器压力。按照缓存资源的使用方式，通常可以分为强缓存和协商缓存。
2. **强缓存。** 强缓存是指浏览器在缓存资源仍然有效，并且允许直接复用的情况下，不需要向服务器发送验证请求，就可以直接使用本地缓存。强缓存主要通过 `Expires` 和 `Cache-Control` 控制。`Expires` 指定资源的绝对过期时间，`Cache-Control` 可以通过 `max-age` 指定资源的新鲜期，单位是秒。当两者同时存在时，通常以 `Cache-Control: max-age` 为准。
3. **Cache-Control 的常见指令。** `max-age` 用于设置缓存的新鲜期；`no-cache` 表示缓存可以存储，但在复用前必须向服务器验证；`no-store` 表示 HTTP 缓存不应存储该请求或响应；`public` 表示响应允许被共享缓存保存；`private` 表示响应只能由私有缓存保存；`s-maxage` 用于控制共享缓存的新鲜期。
4. **协商缓存。** 协商缓存是指浏览器需要重新验证缓存时，向服务器发送条件请求，由服务器判断资源是否发生变化。如果资源没有变化，服务器通常返回 `304 Not Modified`，浏览器继续使用已有缓存；如果资源发生变化，则通常返回 `200 OK` 和新的资源内容。
5. **Last-Modified 与 If-Modified-Since。** 服务器首次返回资源时，通过 `Last-Modified` 告诉浏览器资源最后修改的时间。浏览器保存这个时间，之后需要验证缓存时，通过 `If-Modified-Since` 把上次记录的修改时间发送给服务器。服务器根据资源当前的修改时间判断是否发生变化。这种方式比较直观，但可能受到修改时间精度等因素的影响。
6. **ETag 与 If-None-Match。** 服务器首次返回资源时，可以通过 `ETag` 提供资源的版本标识。浏览器保存该标识，之后需要验证缓存时，通过 `If-None-Match` 携带原来的 ETag。服务器通过比较资源版本标识判断内容是否发生变化。ETag 可以提供更加灵活的版本验证方式。当两组条件头同时出现时，在适用情况下优先根据 `If-None-Match` 判断。

## 8. HTTP/1.0 和 HTTP/1.1 有什么区别？

1. **连接管理不同。** HTTP/1.0 默认使用非持久连接，一次 HTTP 请求和响应完成后通常关闭 TCP 连接，后续请求需要重新建立连接。HTTP/1.1 默认使用持久连接，也就是 Keep-Alive，可以在同一条 TCP 连接上发送多个 HTTP 请求和响应，减少重复建立和关闭连接的开销，提高资源加载效率。
2. **缓存机制不同。** HTTP/1.0 已经支持 `Expires`、`Last-Modified` 等缓存机制。HTTP/1.1 进一步引入 `Cache-Control`、`ETag`、`If-None-Match` 等机制，使缓存策略控制和资源版本验证更加灵活。
3. **请求管道化。** HTTP/1.1 支持管道化机制，允许客户端在尚未收到前一个请求的响应时，继续发送后续请求，减少发送请求时的等待。不过服务器仍然需要按照请求顺序返回响应，因此会出现队头阻塞问题。由于兼容性等因素，HTTP/1.1 管道化在实际浏览器中并没有得到广泛使用。
4. **Host 字段。** HTTP/1.1 要求请求携带 `Host` 字段，用于指定目标主机名。这样多个网站可以共享同一个 IP 地址，服务器通过 Host 字段区分不同的域名，从而支持基于主机名的虚拟主机。
5. **状态码和协议语义。** HTTP/1.1 对状态码和请求处理机制进行了扩展和完善，例如 `100 Continue` 可以用于请求体发送前的交互，`206 Partial Content` 用于表示服务器成功返回部分资源。
6. **带宽优化。** HTTP/1.1 标准化了 Range 范围请求，客户端可以通过 `Range` 字段请求资源的指定部分，服务器通过 `206 Partial Content` 和 `Content-Range` 返回相应内容，有利于实现断点续传。此外，HTTP/1.1 还支持分块传输编码，可以在不知道完整消息体长度时逐块传输数据。

## 9. HTTP/2 和 HTTP/1.1 有什么区别？

1. **二进制分帧。** HTTP/1.1 使用文本形式组织请求行和头部字段，而 HTTP/2 引入二进制分帧机制，将 HTTP 消息拆分为不同类型的帧，例如 HEADERS 帧和 DATA 帧。每个帧包含所属流的标识符，使接收方能够区分不同请求的数据，为实现多路复用提供基础。
2. **多路复用。** HTTP/1.1 虽然支持长连接，但在管道化模式下，响应必须按照请求顺序返回，因此存在队头阻塞问题。HTTP/2 支持多路复用，可以在一条 TCP 连接上同时处理多个 HTTP 请求和响应。每个请求通过独立的流传输，不同流中的帧可以交错发送，因此后发起的请求也可以先完成响应，从而提高并发传输效率。不过 HTTP/2 仍然基于 TCP，无法消除 TCP 层因丢包产生的队头阻塞。
3. **头部压缩。** HTTP/1.1 没有内置的 HTTP 头部压缩机制，多个请求可能反复传输大量相同的请求头信息。HTTP/2 使用 HPACK 算法对头部字段进行压缩，通过静态表、动态表和紧凑编码等机制减少重复字段的传输开销，从而降低请求和响应的头部数据量，提高网络传输效率。
4. **服务器推送。** HTTP/2 引入服务器推送机制，允许服务器在客户端尚未明确请求某些资源时，主动发送预计需要的资源。例如客户端请求 HTML 页面时，服务器可以提前推送相关的 CSS 或 JavaScript 文件，减少客户端再次请求资源的等待时间。不过服务器推送可能导致资源重复传输，实际性能收益并不稳定，因此现代主要浏览器已经逐步停止支持这一机制。

## 10. HTTPS 的工作原理是什么？HTTPS 怎样建立安全连接？

1. **HTTPS 的基本原理。** HTTPS 使用 TLS 协议对 HTTP 通信提供安全保护，主要实现数据的加密传输、完整性保护和服务器身份认证。它结合非对称密码学、数字证书、密钥协商和对称加密等机制，使客户端和服务器能够安全地交换数据。
2. **建立连接并发起 TLS 握手。** 对于常见的 HTTPS over TCP，客户端首先与服务器完成 TCP 三次握手，然后发送 `ClientHello` 消息，其中包含客户端支持的 TLS 版本、加密算法相关参数、随机数以及密钥协商所需的公开信息。服务器收到后返回 `ServerHello`，选择双方支持的安全参数，并提供服务器参与密钥协商的公开信息。
3. **服务器身份认证。** 服务器在 TLS 握手过程中向客户端提供数字证书，并证明自己拥有证书对应的私钥。数字证书由可信 CA 机构签发，包含服务器公钥、域名、有效期和数字签名等信息。客户端会验证证书的信任链、域名和有效期，并结合握手签名确认服务器身份，从而防止攻击者冒充服务器。
4. **密钥协商。** 在现代 TLS 1.3 中，常见的密钥协商方式是 ECDHE。客户端和服务器分别生成临时私有信息，并交换相应的公开信息。双方利用自己的私有信息和对方的公开信息，分别计算出相同的共享秘密，再通过密钥派生算法生成后续通信使用的密钥。这个过程不需要直接在网络中传输最终的秘密密钥，并且能够提供前向保密。
5. **加密数据传输。** 双方通过 `Finished` 等握手消息确认握手的完整性。TLS 握手完成后，客户端和服务器使用协商生成的对称密钥，通过 AES-GCM 等认证加密算法保护 HTTP 请求和响应。对称加密效率较高，适合大量数据传输，同时能够检测传输过程中未经授权的数据篡改。

# 计算机网络八股文——前 10 题面试回答

## 1. 从输入 URL 到页面展示，发生了什么？

1. **URL 解析与 DNS 查询。** 浏览器首先解析 URL，确定访问的协议、域名和资源路径，并检查是否可以使用缓存。如果需要向服务器请求资源，就通过 DNS 解析获取服务器的 IP 地址。
2. **建立连接。** 浏览器根据 IP 地址与服务器建立连接。以常见的 HTTPS over TCP 为例，需要先完成 TCP 三次握手，再通过 TLS 握手验证服务器身份、协商加密密钥，建立安全连接。
3. **HTTP 请求与响应。** 连接建立后，浏览器发送 HTTP 请求，服务器处理请求并返回 HTTP 响应，包括状态码、响应头以及 HTML 等资源内容。
4. **浏览器解析和渲染。** 浏览器收到 HTML 后，解析生成 DOM 树，同时解析 CSS 生成 CSSOM 树，接着构建渲染树，进行布局、绘制和合成，最终展示页面。在这个过程中，浏览器还会加载图片、CSS 和 JavaScript 等资源。

## 2. TCP 三次握手的过程，以及为什么需要三次握手？

1. **第一次握手。** 客户端向服务器发送 SYN 报文，携带初始序列号 `seq=x`，请求建立连接，随后进入 `SYN-SENT` 状态。
2. **第二次握手。** 服务器收到 SYN 后，回复 SYN+ACK 报文，其中 `ack=x+1`，同时携带服务器自己的初始序列号 `seq=y`，进入 `SYN-RECEIVED` 状态。
3. **第三次握手。** 客户端收到 SYN+ACK 后，发送 ACK 报文，确认号为 `ack=y+1`，随后进入 `ESTABLISHED` 状态。服务器收到第三次 ACK 后，也进入 `ESTABLISHED` 状态。
4. **为什么需要三次握手？** TCP 建立连接时，双方需要交换并确认各自的初始序列号。如果只有两次握手，服务器无法确认客户端是否收到了自己的 SYN，可能出现双方连接状态不一致的问题。第三次握手能够让服务器获得这个确认。
5. **为什么不需要四次握手？** 因为服务器可以将确认客户端 SYN 的 ACK 和自己发送的 SYN 合并成一个 SYN+ACK 报文，所以通常三次交互就足够了。

## 3. TCP 四次挥手的过程，以及为什么需要四次挥手？

1. **第一次挥手。** 客户端主动发送 FIN 报文，表示自己不再发送数据，进入 `FIN-WAIT-1` 状态。
2. **第二次挥手。** 服务器收到 FIN 后回复 ACK，进入 `CLOSE-WAIT` 状态。客户端收到 ACK 后进入 `FIN-WAIT-2` 状态，此时服务器仍然可以继续发送剩余数据。
3. **第三次挥手。** 服务器完成数据发送后，向客户端发送 FIN，表示自己也准备关闭发送方向，进入 `LAST-ACK` 状态。
4. **第四次挥手。** 客户端收到服务器的 FIN 后回复 ACK，进入 `TIME_WAIT` 状态。服务器收到 ACK 后关闭连接，客户端通常等待 `2MSL` 后再关闭。
5. **为什么通常需要四次挥手？** 因为 TCP 是全双工通信，两个方向的数据传输需要分别关闭。服务器收到客户端的 FIN 时，可能还有数据没有发送完，所以先回复 ACK，等数据发送完成后再发送 FIN。如果服务器也已经准备好关闭，ACK 和 FIN 可以合并发送。
6. **TIME_WAIT 的作用。** 一方面，如果最后的 ACK 丢失，客户端还可以处理服务器重传的 FIN，并重新发送 ACK；另一方面，等待 `2MSL` 可以让旧连接中残留的报文有时间过期，避免干扰后续连接。

## 4. TCP 和 UDP 有什么区别？

1. **连接方式不同。** TCP 是面向连接的协议，传输数据前需要通过三次握手建立连接；UDP 是无连接协议，可以直接发送数据报。
2. **可靠性不同。** TCP 通过序列号、确认应答、超时重传等机制提供可靠、有序的数据传输，并通过流量控制和拥塞控制调节发送行为。UDP 本身不保证数据一定到达，也不保证数据按照发送顺序到达。
3. **传输形式不同。** TCP 是面向字节流的协议，不保留应用层每次发送数据的消息边界；UDP 是面向数据报的协议，保留数据报边界。
4. **协议开销不同。** TCP 需要维护连接状态，并实现确认、重传等机制，协议开销相对较大。UDP 的首部固定为 8 字节，协议机制更简单，开销通常更低。
5. **应用场景不同。** TCP 适合文件传输、数据库连接等对可靠性要求较高的场景；UDP 适合 DNS 查询、实时音视频和部分在线游戏等对实时性比较敏感的场景。

## 5. HTTP 常见状态码和请求头字段有哪些？

1. **1xx：信息性响应。** 表示请求处理过程中的信息，例如 `100 Continue`，表示客户端可以继续发送请求体。
2. **2xx：请求成功。** 常见的有 `200 OK`，表示请求成功；`201 Created`，表示资源创建成功；`204 No Content`，表示请求成功，但没有响应体。
3. **3xx：重定向和缓存。** 常见的有 `301 Moved Permanently`，表示永久重定向；`302 Found`，通常用于临时重定向；`304 Not Modified`，表示缓存资源仍然有效，可以继续使用。
4. **4xx：客户端请求错误。** 常见的有 `400 Bad Request`，表示请求存在问题；`401 Unauthorized`，表示缺少有效身份认证；`403 Forbidden`，表示服务器拒绝访问；`404 Not Found`，表示请求的资源不存在。
5. **5xx：服务器错误。** 常见的有 `500 Internal Server Error`，表示服务器内部错误；`502 Bad Gateway`，表示网关收到无效的上游响应；`503 Service Unavailable`，表示服务暂时不可用；`504 Gateway Timeout`，表示网关等待上游服务器响应超时。
6. **常见 HTTP 头字段。** `Host` 用于指定目标主机，`Content-Type` 表示数据类型，`Content-Length` 表示消息体长度，`Content-Encoding` 表示内容编码方式，`Authorization` 用于身份认证，`Cache-Control` 用于控制缓存策略。

## 6. GET 和 POST 请求有什么区别？

1. **用途不同。** GET 主要用于获取资源，比如查询用户信息；POST 主要用于向服务器提交数据并进行处理，比如创建订单。
2. **参数传递不同。** GET 通常通过 URL 查询参数传递条件，POST 通常通过请求体传递数据，例如 JSON、表单或文件。不过 POST 也可以携带 URL 参数。
3. **安全性不同。** 在 HTTP 协议语义中，GET 属于安全方法，主要用于只读操作；POST 可以用于修改服务器资源状态。另外，GET 的 URL 参数可能被浏览器历史记录或访问日志保存，因此不适合放置敏感信息。
4. **幂等性不同。** GET 在 HTTP 语义上具有幂等性，重复执行相同请求不会产生额外的预期状态变化。POST 默认不保证幂等，例如重复提交创建订单的请求，可能生成多条订单，所以实际业务中通常需要考虑防重复提交。
5. **缓存不同。** GET 响应通常更容易利用 HTTP 缓存，POST 响应的缓存条件相对严格，实际使用较少。

## 7. 什么是强缓存和协商缓存？

1. **强缓存。** 强缓存是指浏览器在缓存资源仍然有效、且允许直接复用时，不需要向服务器发送验证请求，就可以直接使用本地缓存。主要通过 `Expires` 和 `Cache-Control` 控制，其中 `Expires` 指定过期时间，`Cache-Control: max-age` 指定缓存的新鲜期。
2. **协商缓存。** 协商缓存是指浏览器需要重新验证缓存时，向服务器发送条件请求，由服务器判断资源是否发生变化。如果没有变化，通常返回 `304 Not Modified`，浏览器继续使用缓存；如果发生变化，则返回 `200 OK` 和新的资源内容。
3. **Last-Modified 和 If-Modified-Since。** 服务器首次返回资源时，通过 `Last-Modified` 告诉浏览器资源最后修改的时间。浏览器再次验证时，通过 `If-Modified-Since` 携带这个时间，由服务器判断资源在此之后是否发生变化。
4. **ETag 和 If-None-Match。** 服务器首次返回资源时，通过 `ETag` 提供资源的版本标识。浏览器再次验证时，通过 `If-None-Match` 携带原来的标识，由服务器判断资源版本是否变化。相比修改时间，ETag 可以提供更加灵活的版本验证方式。
5. **两者的区别。** 强缓存命中时不需要向服务器发送验证请求，网络开销更低；协商缓存需要向服务器确认资源是否变化，即使返回 `304`，也会产生一次请求和响应，但可以避免重新传输完整资源。

## 8. HTTP/1.0 和 HTTP/1.1 有什么区别？

1. **长连接。** HTTP/1.0 默认使用非持久连接，一次请求和响应完成后通常关闭 TCP 连接；HTTP/1.1 默认使用持久连接，也就是 Keep-Alive，可以在同一条 TCP 连接上处理多个 HTTP 请求，减少重复建立和关闭连接的开销。
2. **缓存机制。** HTTP/1.0 主要使用 `Expires`、`Last-Modified` 等字段控制缓存；HTTP/1.1 引入 `Cache-Control`、`ETag` 等机制，使缓存策略和资源版本验证更加灵活。
3. **管道化。** HTTP/1.1 支持请求管道化，允许客户端在收到前一个请求的响应之前继续发送后续请求。不过响应仍然需要按照请求顺序返回，因此存在队头阻塞问题。
4. **Host 字段。** HTTP/1.1 要求请求携带 `Host` 字段，用于指定目标主机名，使多个不同域名的网站可以共享同一个 IP 地址。
5. **状态码。** HTTP/1.1 扩展和完善了状态码及相关协议语义，例如 `100 Continue` 和 `206 Partial Content`。
6. **带宽优化。** HTTP/1.1 支持 Range 范围请求，允许客户端只获取资源的指定部分，有利于实现断点续传；同时还支持分块传输编码，可以在不知道完整消息体长度时逐块发送数据。

## 9. HTTP/2 和 HTTP/1.1 有什么区别？

1. **二进制分帧。** HTTP/1.1 使用文本形式组织请求行和头部，而 HTTP/2 引入二进制分帧机制，将 HTTP 消息拆分为 HEADERS 帧、DATA 帧等不同类型的帧。每个帧携带所属流的标识符，为多路复用提供基础。
2. **多路复用。** HTTP/1.1 在管道化模式下，响应需要按照请求顺序返回，存在队头阻塞问题。HTTP/2 可以在一条 TCP 连接上同时处理多个请求和响应，不同流中的帧可以交错传输，因此后发起的请求也可以先完成响应。不过 HTTP/2 仍然存在 TCP 层因丢包造成的队头阻塞。
3. **头部压缩。** HTTP/1.1 没有内置的头部压缩机制，多个请求可能重复传输大量相同的头部字段。HTTP/2 使用 HPACK 算法，通过静态表、动态表和紧凑编码等机制压缩头部信息，减少重复字段的传输开销，提高网络传输效率。
4. **服务器推送。** HTTP/2 引入服务器推送机制，允许服务器在客户端尚未明确请求某些资源时，提前推送预计需要的 CSS、JavaScript 等资源，以减少额外请求带来的延迟。不过由于可能造成重复传输，现代主要浏览器已逐步停止支持该机制。

## 10. HTTPS 的工作原理是什么？

1. **基本原理。** HTTPS 使用 TLS 协议对 HTTP 通信提供安全保护，主要实现数据加密传输、完整性保护和服务器身份认证，涉及数字证书、非对称密码学、密钥协商和对称加密等机制。
2. **建立连接并发起 TLS 握手。** 对于常见的 HTTPS over TCP，客户端先通过 TCP 三次握手与服务器建立连接，然后发送 `ClientHello`，携带支持的 TLS 版本、加密参数和密钥协商信息。服务器返回 `ServerHello`，选择双方支持的参数，并提供自己的密钥协商信息。
3. **服务器身份认证。** 服务器向客户端提供数字证书，并证明自己拥有证书对应的私钥。客户端验证证书的 CA 信任链、域名、有效期以及服务器的握手签名，从而确认服务器身份，防止攻击者冒充服务器。
