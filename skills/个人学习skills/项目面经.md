# 项目面经

## 适用范围

适用于“项目面经”“项目拷打”“追问”“帮我把项目整理成能口述的答案”“只保留三星题”等请求，包括 LangGraph / Agent、FastAPI、内容策略、风控、数据分析项目。基础技术概念问答交给“后端八股讲解”（backend-interview-bagua）。本skill自行核对项目陈述的事实依据；不自动承担简历制作。

## 内容依据与真实性

1. 优先以用户本次提交的项目代码、文档、日志、简历和亲身陈述为准。原文未提供的信息不得补成用户“做过”的事实。
2. 项目中的技术实现、量化效果、用例数、性能指标、服务部署状态分别标明“已验证”“自述/原材料”“待补实测”。保留原文【待填数据】占位符，不编造数字。
3. 处理不同版本之间的差异时，以用户指定的最新版本为准；若没有明确最新版本，先核对再改。
4. 对问题的追问必须准确：例如“为什么选单 Agent”“怎样定位工具守卫绕过”“为什么缓存按会话隔离”，分别聚焦决策、故障排查和并发正确性。

## 核心组织规则：保证连贯口述

- 每题围绕一个完整的因果链：**场景和目标 → 具体问题/权衡 → 采取的方案 → 实际验证与结果 → 有必要时说明局限**。这是检查答案完整性的内部逻辑，**不要把它机械地写成五个加粗小标题**。
- 原文按连续自然段呈现时，优先保留原文的叙述顺序、具体情境、关键日志和排查动作；做轻度裁剪与润色，不把故事改成孤立的关键词列表。
- 只有确实包含独立的多个机制或执行步骤时才使用编号 `1. 2. 3.`，不使用 `01 02 03`。无需为了整齐强行分点；每一点都必须是一段连贯的可口述完整回答。
- 不在每段开头生造“关键挑战”“问题归因”“解决方案”这类加粗导语；不写模板化反转句（如“不是……而是……”）。
- 面试回答应当有可以直接说出口的完整句子，内容具体，减少大而空的抽象概括与相同意思的反复总结。短题简短，复杂题可以更长，依据问题难度决定篇幅。
- 技术准确性优先：区分“模型可见工具”和实际 ToolNode 执行注册表、缓存命中与源数据查询、会话隔离与单例服务、规则与真实性能测试等边界。

## 深挖与校验

- 涉及故障时交代：复现条件、错误表现、日志/数据证据、定位到的调用链、修复位置、回归验证；不要只有一个“后来优化了”。
- 涉及性能、成本、效果时说清口径、样本数、比较基线、在线/离线性质，不能把本地原型当生产上线。
- 提供附加追问仅限高度相关的 1–2 项，且用户只要求整理答案时不自动加题、加扩展知识或加结尾总结。

## 已确认的交付与示例

保留用户题目顺序和优先级标记；指定三星题时只处理三星题。按问题需要完成连贯答案，不生造“背景、方案、效果”标签。涉及格式化、PDF、模板和保存时调用“文档整理与制作”；只要求答案时直接在对话输出。

口述结构示例（仅示范组织，不是用户真实履历）：原流程遇到某个明确故障，我先通过日志和复现条件定位到具体环节，再解释采用该修复而非其他选项的原因，最后说明已做的验证、结果与仍未核实的部分。不要把这个骨架原样填成空泛套话，更不能填造数字。

普通表达遵循“回复格式”。本skill不维护字体、颜色、目录和视觉模板，也不引用已删除的skill。

## 配套规则可用性

本套共5个Skill，建议一并安装。引用其他配套Skill时按其规范名定位；若尚未安装，不声称已调用，不因此阻塞当前可独立完成的内容，必要时说明缺少的模板或能力。
