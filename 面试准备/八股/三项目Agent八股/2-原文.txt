一、概念与边界
1. Skill 是什么？它解决了什么工程问题？√
Skill 本质上就是一个文件夹，里面必须有一个 SKILL.md 文件。这个文件开头是一段 YAML 元数据，至少要有 name 和 description 两个字段,再往下就是 Markdown 写的指令正文。文件夹还可以带上三个可选的子目录：scripts/ 放确定性的代码，references/ 放篇幅比较大的参考文档,assets/ 放要进最终产物的模板、图标、字体。这就是 Skill 的全部形态。
那它解决什么工程问题？我总结下来主要是三个：
一是长 prompt 没法沉淀。随着版本演进，prompt 越写越长，哪一条约束是当初为了修哪个 case 加的，过几个月就没人说得清了，最后谁都不敢删。
二是调好的 prompt 换个项目就失效。因为里面混进去大量项目特有的约定，没有边界，搬不走。
三是团队里每个人给 Agent 的指令都不一样。同一件事十个人十种说法，输出质量完全看谁在用。
所以 Skill 的定位一句话：把"这件事该怎么做"这种流程性的知识,封装成可以复用、可以分发、需要的时候才加载的一个包。
它跟"把提示词存成文件"最大的区别在三点。第一,有独立的触发面,就是 description 那一段文字,模型判断用户的话跟这个 description 匹配才会去读正文,不匹配就不进上下文。第二,分层加载,常驻在上下文里的只有元数据那一小段,正文命中才加载。第三,它能进版本管理、能跑评测,是一个能被度量的工程对象,而不是散落在各处的文本。
2. Skill、Rules / System Prompt、Tool、Subagent 这几层怎么分工？
这四层各管一件事，判断标准其实就两条：内容是不是每一轮都用得上，以及它是一个原子能力还是一个编排。
Rules 或者 System Prompt 是全局纪律，每一轮都常驻在上下文里，装的东西比如"回答用中文"、"输出格式必须是 JSON"、"绝对不能输出密钥"这种红线约束。凡是每一轮都要遵守的，都放这里。
Skill 是流程知识，命中之后才把正文加载进来。装的东西是多步流程、每一步的判据、输出规范。比如一个 PR 评审 Skill，会写清楚"先检查什么、再检查什么、发现 blocker 怎么办、最终输出什么格式"。
Tool 是原子能力，工具列表本身常驻。它是最小的动作单位，比如读写文件、调一个 API、执行一条命令。
Subagent 是一个独立的执行单元，有自己的上下文和工具集。它的核心价值不是"把 prompt 分开写"，而是上下文隔离加工具集收窄。比如我不想让评审角色看到写操作的工具，就单独派一个 Subagent 出去。
三个判断依据：每一轮都要遵守的进 Rules；十次里只用一次、篇幅还不小的做成 Skill；Tool 是原子，Skill 通常在编排多个 Tool。
一个容易漏掉的差异：Skill 属于标准层，写一次能在多个平台复用；Rules 属于产品层，不同平台的落点不一样（有的叫 Rules、有的叫 AGENTS.md、有的叫 project instructions），要逐个映射。

**MCP **解决的是Agent 如何触及外部世界的问题，它定义了 Agent 连接外部工具和数据源的协议，提供的是动作能力。比如连接数据库、调用 API。
Agent Skills
解决的是Agent 如何做好一件事的问题，它提供工作流和领域知识，告诉 Agent 在特定场景下应该按什么步骤、用什么标准、产出什么格式。
几个维度对比：加载方式上，MCP 是远程协议需要 server，Skills 是本地文件夹按需加载；提供内容上，MCP 是 tool 列表加参数 schema，Skills 是 Markdown 指令加可选脚本；分发标准上，MCP 走 Anthropic 自己的协议，Skills 走 agentskills.io 开放标准。
他们配合使用的话，最典型的配合模式是
Skills 编排 MCP
，由 Skills 提供工作流和领域知识，由 MCP 提供原子动作能力，再由 LLM 做最终判断。比如：用户说"帮我检查一下数据库健康度"，Agent 通过 description 匹配触发对应的 Skill；Skill 内的指令告诉 Agent 做什么；执行每一步检查时，Agent 调用 MCP 提供的工具拿真实数据；拿到数据后再按 Skill 里定义的评分标准生成分级报告。
4. Skill 和 RAG 什么关系？什么时候用哪个？
这两个不是二选一，通常是同时存在的，因为它们取的是不同类型的知识。
RAG 取的是事实性知识——"文档里写了什么"、"某个客户的账期是多少"、"合同的第三条内容是什么"。它的形态是索引加检索服务，在需要事实的时候检索出来。失败表现是召回不准或者压根检索不到。
Skill 取的是过程性知识——"这类任务该怎么做"、"审查合同要走哪几步"、"每一步的判据是什么"。它的形态是文件夹加 SKILL.md，任务匹配的时候加载。失败表现是不触发或者流程走偏。
正确的写法是在 Skill 正文里明确写清楚什么时候去检索。比如"第三步到知识库检索对应的合同模板,检索不到就走人工确认分支"。Skill 负责编排,RAG 负责取事实。
一个常见的错误做法是把几万字的产品手册整本粘到 SKILL.md 正文里，这属于用错工具。正确的做法要么放到 references/ 里按需读，要么直接走 RAG 检索。
举个合同审查的场景：Skill 定义流程——先识别合同类型,再按类型取对应审查清单,逐条比对,最后输出风险分级。其中"对应审查清单"和"同类历史条款"走 RAG 检索,检索到就继续,检索不到就按 Skill 里预先写好的分支转人工，绝对不允许模型凭空补一份清单出来。
5. 什么场景不该做成 Skill？
主要是五种情况，每一种都有更合适的落点：
一次性任务不用做成 Skill。做完就不用了，做成 Skill 只是白增加常驻的元数据成本。这种直接写在当次对话里就行。
需要强确定性和事务保证的逻辑不做 Skill。比如金额计算、数据一致性校验、事务提交,这些应该写成脚本或者后端服务,不能交给模型判断。
每一轮都要遵守的全局纪律不做 Skill。放 Rules 里，比如"输出必须是 JSON"、"不能输出敏感字段"。
纯事实查询不做 Skill。走 RAG 或者直接查数据库。
需要严格权限控制的操作不做 Skill。要走带鉴权的工具层,权限不能靠正文里的自然语言约束——模型说改就改，不可靠。
举个具体例子。"发票核销"这个业务里有三种东西要分开处理：核销金额必须两位小数、误差零容忍——这种计算逻辑写成脚本；核销流程分几步、每步的判据、异常怎么升级——这种做成 Skill；某个客户的账期是多少天——这种走查库。判断标准就一句话：要确定性的交给代码，要判断和权衡的交给 Skill，要事实的交给检索。
二、规范与格式
6. SKILL.md 的最小合法结构和硬约束是什么？√
最小结构就是：YAML frontmatter 开头,至少要有 name 和 description 两个字段,后面是 Markdown 写的指令正文,正文本身没有强制格式。
典型的目录长这样：
skills/pr-review/
├── SKILL.md        # frontmatter + 指令正文
├── scripts/        # 可执行代码
├── references/     # 按需加载的文档
└── assets/         # 进最终产物的模板、图标、字体
SKILL.md 里 frontmatter 大概这样：
---
name: pr-review
description: 用于按团队规范评审 Pull Request，当用户提到代码评审、review、能不能合时使用。
---
硬约束主要在 name 上：name 必须和目录名完全一致，而且只允许小写字母、数字、连字符这三种字符。三个可选目录不是必需的，但一旦出现就要各守其位。
最好把这几条固化到 CI 里做格式校验——frontmatter 字段是否齐全、name 和目录名是否一致、description 长度有没有超限。改目录名忘了同步 name 会直接导致引用断裂或者重复安装,这种问题不应该靠人肉发现。
7. scripts/、references/、assets/ 三个目录的职责边界是什么？
判断标准就一句话：这段内容是给模型跑的、给模型读的，还是要进最终产物的。
scripts/ 放确定性、重复性、结果可验证的逻辑——格式转换、数据清洗、打包、校验这些。它的关键收益是执行过程不进上下文，能省 token、结果稳定、还能单测。比如跑测试、解析测试框架的输出、提取失败用例和堆栈、生成 diff 摘要，这些全部下沉到 scripts/，模型只看结构化的摘要，不看几千行原始日志。
references/ 放篇幅大、按需读取的文档——规范细则、变体流程、字段字典这类。它命中才加载，不命中零成本。有一条经验：references/ 里单文件超过 300 行，建议在文件内加个目录，让 Agent 能定位到具体小节而不是全量加载。
assets/ 放模板、图标、字体这种要进最终产物的文件，用来保证输出格式统一。
还有一个原则：需要判断和权衡的部分要留在正文里交给模型，不要试图用脚本写死。反过来，重复性、确定性的逻辑也不要留在正文里让模型每次自己算一遍。
多变体场景要特别注意。比如同一个技能要支持 AWS、GCP、Azure 三套流程，正确的做法是主 SKILL.md 只放工作流和"怎么选变体"的逻辑，具体三套流程拆到 references/ 下按变体命名，只加载命中的那一个。反模式是三套平铺在正文里，token 直接浪费三倍。
8. description 该怎么写？为什么它是整个 Skill 最重要的一行？√
因为模型在决定要不要读这个 Skill 的时候，手上只有 name 和 description 两个东西，正文是触发之后才会加载的。所以所有"什么时候用这个 Skill"的信息都必须写在 description 里，写在正文里等于没写。
写 description 有四个要点：
一是两件事必须同时写清楚——做什么（功能、数据来源、输出形态），和什么时候用（触发场景加真实的用户话术）。只写"做什么"是最常见的错误。
二是写主动一点。当前的模型普遍是欠触发，不是过触发，所以要显式列出触发词和场景，甚至可以明确写"即使用户没有说某个词也要使用"。
三是注意字符上限。Anthropic 那边是 1024 字符,写到 1000 以上就要留改动余量了。
四是需要收窄的时候写排除条件，比如"不要用于纯数据查询"。
举个改写的例子。原来是"生成报告的技能"，这就是典型的没写清楚。改完之后应该是："用于生成季度经营分析报告,数据来自数据仓库,输出为带图表的 Markdown 报告。当用户提到季度总结、经营分析、月报、复盘、业绩回顾时使用,即使没有明确说'报告'也要使用；不要用于单纯的指标查询。"
改动做了三件事：补做什么、补什么时候用（列真实话术）、补排除条件。改完还要用触发评测集验证，而不是靠读一遍觉得顺就完事。
还有一个坑要注意：堆关键词确实能提升召回，但会同时抬高误触发率，而且技能一多就会跟语义相近的技能抢触发。所以堆词必须配合负样本评测一起做，不能凭感觉堆。
9. allowed-tools 这种权限字段现在能依赖吗？
了解即可，不看也行。
不能。allowed-tools 在标准里还属于实验性字段，各平台的支持程度也不一致，写了不一定生效。
真正可靠的权限约束在两个地方：执行环境和工具层。
执行环境这一层，靠的是沙箱强制——目录白名单挂载、网络出口白名单、只读根、非 root、资源上限、凭证不注入沙箱环境变量。这些是硬约束，模型再怎么"发挥"也突破不了。
工具层这一层，靠的是工具集本身收窄——评审角色只挂载读工具，不挂载写工具。想改也没那个能力。
把安全押在 frontmatter 声明上是一个重大的设计错误。技能正文里即使写了"只允许读取"，那也只是一个提示,不是边界。模型完全可能忽略。
还有一个跨平台的补充：同一个 skill 在 Claude Code、Copilot、Cursor 上目录位置不一样（.claude/skills、.github/skills、~/.copilot/skills），加载判断的原理是一致的——都是看用户 prompt 和 description 决定要不要注入正文，但路由策略、是否支持 hooks、是否支持自定义命令，各家有差异。所以哪些字段"写了也不生效"，是要逐个平台确认的。
10. 技能正文里为什么要写失败回退策略？
失败分支的作用是给模型一个明确的出口。如果不写清楚，失败的时候模型只有两种行为：要么反复重试烧时间，要么编一个看起来合理的结果交上来。
典型的写法是这样：拿不到日志的时候,先判断是权限问题还是工具不可用并明确提示,然后改走本地复现路线；如果本地复现也不行，就停下来，把已经拿到的信息和卡点输出出来,交回人工。
有两个必须写进正文的分支。
一个是环境类失败。依赖装不上就直接回报"环境有问题"，不要在沙箱里反复重试烧时间和 token。
另一个是目标类失败。测试连续三次没通过，就必须停下来，输出当前的变更、失败原因、卡点，交回人工，不允许通过修改断言让测试变绿。这一条尤其要写，因为模型的默认倾向是把"测试通过"当成目标，而不是"功能正确"。它一急就会去改测试而不是改代码。
现场写 SKILL.md 的时候，失败分支是最常见的丢分点。所以宁可写多也别漏。
三、机制原理
11. 大模型加载 Skills 的过程是怎样的？√
Skill 是分三层加载的，这一点非常关键。
第一层是元数据，也就是 name 加 description，每一轮都常驻在模型的上下文里。哪怕一个 Skill 都没命中，这一层的成本也要付。所以 Skill 的常驻成本不是 0，是"元数据 × 技能总数"。
第二层是正文。当模型基于 description 判断当前任务和某个 Skill 匹配的时候，才把这个 Skill 的正文加载进来。没命中的 Skill，正文永远不会进上下文。
第三层是 references/ 和 scripts/。正文里会写清楚"什么情况去读哪个文件"，模型按照正文里的指引再去加载。references 是命中才读的文档，scripts 是被调用才执行的代码，执行的过程不进上下文，只有结果回填。
这个设计之所以重要，是因为上下文是稀缺资源。常驻成本只有元数据那一层，所以能力可以近乎无限扩展而不会撑爆窗口。
关于正文长度，有一条经验值：500 行或者 5k tokens 是软上限。但这是经验值，不是校验规则。逼近上限的时候正确的做法是加一层层级——把细节下沉到 references/ 里，正文里只留主流程和"什么情况读哪个 references"。
有一个反例：一个测试类技能要支持 Python、Node、Java 三种仓库。错误做法是三套细节流程平铺在正文里，token 直接浪费三倍。正确做法是主 SKILL.md 只保留"怎么判断这个仓库是哪一类"和"通用的四步流程"，三套具体细节拆到 references/ 下按语言命名，命中一个读一个。
12. Skill 的触发机制到底怎么工作的？
技能是以 name 加 description 的形式出现在 Agent 的可用技能列表里的，Agent 根据 description 决定要不要去读正文。这个过程不是关键词精确匹配,也不是正则路由,本质上是模型的一次判断。
有一个关键机制要说清楚：Agent 只会在自己搞不定的任务上去咨询技能。单步的、简单的查询，比如"读一下这个 PDF"，即使 description 完全匹配也可能不触发,因为模型用基础工具就能直接完成，不需要 Skill。
这带来两个推论：
一是复杂、多步、专业化的任务，才是技能能可靠触发的场景。
二是简单的 query 不能当触发测试用例。无论 description 写多好都不会触发，用这类样本做评测只会污染结果。
我举一个具体例子。构造触发评测集的时候,"这个函数是干什么的"这种单步问题必须从"该触发"样本里剔除。它不触发是机制正确,不是 description 有问题。如果把这种样本留在评测集里，就会一直在改 description 但触发率不见涨，其实问题根本不在那里。
13. 一个 Skill 被触发后实际吃掉多少 token？怎么算？
不能只算正文的字数，这样算不准。真实的开销要拆成四项：
第一项是元数据常驻成本乘以技能总数。每一轮都要付这笔钱，哪怕一个都没命中。所以哪怕这个技能这次没触发，只要挂载了，它的 name 和 description 就在上下文里。
第二项是命中技能的正文长度。这是大头之一。
第三项是本轮实际读取的 reference 大小。如果正文里写了"读 aws.md"，那 aws.md 的内容就进来了。
第四项也是最容易被低估的——脚本输出回填进上下文的内容。一份原始的测试日志或者 diff 输出回填进来，往往比正文本身还要大。
控制成本要分先后顺序。先控制技能总数，把僵尸技能下线掉；然后正文瘦身，把细节下沉到 references/；再把确定性逻辑改成脚本执行；最后是工具输出必须做摘要，不要原样回填。做完这些之后按技能统计增量 token，设预算告警。
量化的方法是做开关对照。同一批任务，挂载和不挂载某个技能各跑一轮，直接比 token 账单，就能得到这个技能的增量成本。
其中收益最大的一步通常是"工具输出做摘要"。原始测试日志几千 token，提取成"失败用例名 + 断言差异"之后一两百 token 就够用了。
14. 上下文污染和自动压缩对 Skill 有什么影响？
避免 Skills 的上下文污染，可以从三个层面来讲。
第一个层面是机制层，靠渐进式披露天然防住大头。
Skill 本身是三层加载的——name 加 description 常驻,正文命中才加载,references 和 scripts 是正文里明确指引才读。所以只要按规范写 Skill,光是"正文不主动进上下文"这一步,就已经把污染的大头挡住了。只有真正命中的那个 Skill 的正文才会进来，无关技能的内容不会被塞进窗口。
从架构上来说,只要严格按渐进式披露的规范写,80% 的污染问题已经从设计上被解决了。
第二个层面是生态层，防止错误的 Skill 被加载进来。
这一层很关键，因为一旦触发错了，错误 Skill 的整个正文会灌进上下文，这才是最严重的污染源。
三个手段：
一是 description 必须写准，包含"做什么 + 什么时候用 + 排除条件"三部分。举个例子,如果 docx skill 和 pdf skill 的 description 都写"用于文档处理",Agent 看见 PDF 任务也可能去触发 docx。改成"仅用于 .docx 文件"并在末尾补一句"不适用于 PDF 或其他文件类型",误触发率就明显下来。
二是单一职责。一个 Skill 只管一件事,PDF 和 PPT 必须拆开。看起来 Skill 数量变多了,但每个的 description 都变得极度纯粹,路由准确率反而更高。
三是定期审计下线。没人用的、评测分数长期不达标的 Skill 该下就下。因为每多一个 Skill,它的 description 就在常驻层抢注意力,没人用的技能就是纯负担。
第三个层面是内容层，防止单个 Skill 触发之后自己污染主上下文。
即使触发对了，Skill 本身也可能污染上下文，主要有三种表现：
一是正文里的历史约束在任务切换之后还在生效。上一轮说"改代码前先备份"，下一轮已经不是改代码任务了这条还在影响输出。应对是关键约束在每个阶段的输出里显式复述,别指望模型自己记得。
二是 references 里的示例被模型当成事实。示例里写"读取 /tmp/data.csv"，模型直接拿这个路径去干活。所以 references 里的路径、参数一定要标成占位符,写成
<your_path>
或者
example.com
这种明显是占位的形式，不要写成看起来可用的真实值。
三是工具返回的长日志把关键指令挤到窗口边缘。正文里要明确写"工具输出先摘要再进上下文",比如 CI 日志先提取失败用例名和顶部堆栈,几百 token 就够了,不要原样回填几千行原始日志。
关于自动压缩，可以顺带补一句。
长对话触发自动压缩之后，模型可能只记得"我在按某个流程做"，但每一步的判据丢了。应对是把长流程拆成可断点续跑的阶段,每个阶段之间传结构化的交付物（比如固定字段的 JSON），下一阶段只吃这个交付物,不继承上一阶段的完整对话。这样即使压缩了,关键判据也还在交付物里。
15. "先摘要、后细节"这个模式解决什么问题？
不重要，不看也行。
这个模式有两层价值。
第一层是成本。日志、网页、长文档这种场景，先用一个摘要型工具拿概要，需要细节的时候再去取原文的对应部分,不要一次性把全文塞进上下文。一份 CI 失败日志几千行，全塞进去几千 token；先摘要成"失败用例名 + 断言差异 + 顶部堆栈",几百 token 就够,而且信息量对模型判断已经足够。
第二层是安全，这一层答出来直接加分。外部内容进入上下文越少，提示注入的暴露面就越小。很多提示注入是藏在日志、issue 正文、网页里的，如果不整段读进来，它就没机会被当成指令执行。
举个 CI 失败排查的正确顺序：先拉失败摘要（失败用例名、断言差异、顶部堆栈），模型看完之后判断需要哪个文件的细节，再定向拉那个文件的原文。读 issue 和外部文档也一样，先过一层摘要，而且摘要这一步交给脚本或者独立环节做，摘要的结果才进主流程。
反过来说，一上来就 cat 全量日志、把整个 issue 描述贴进来，既烧 token 又把提示注入的暴露面全打开了，属于双输。
四、排障
16. Skill 该触发却没触发，排查顺序是什么？
按顺序走，别乱猜：
第一步，看 description 里有没有写"何时使用"，还是只写了"做什么"。这是最常见的问题。
第二步,看用户的实际说法和 description 里的词汇是不是对不上。比如用户说"帮我看看这份合同有没有坑"，description 里只写了"合同审查流程"，这两个词汇差得远。
第三步，判断任务是不是太简单，Agent 直接就做掉了。这是机制性不触发,改 description 也没用（见触发机制那题）。
第四步，看是不是有另一个技能的 description 覆盖了这个场景,把触发抢走了。
第五步，确认技能是不是真的挂载到了当前作用域。
对策也是三条：description 要写主动，把触发词写全；补真实的用户话术，别用官话；评测集里区分"该触发"和"不该触发"两类样本，一起跑。
第三步是这道题的关键区分点。面试官经常追问"哪些是改 description 解决不了的"，能主动指出"任务太简单是机制性不触发"，说明真正调过 Skill,不是只看过文档。
排查顺序反了会怎样？会出现"改了五版 description 还是不触发"的情况，但真实原因其实是任务太简单，或者技能压根没挂到当前作用域。
17. 技能触发了，但 Agent 没按流程走，怎么办？
线上排障：技能触发了，但 Agent 没按流程走。
先排查五个原因：
一是正文太长，中段的指令被稀释了。模型对开头和结尾的敏感度比中间高。
二是步骤描述有歧义，一句话有多种理解。
三是缺少每一步的完成判据。模型自己解释"做完了"就交差。
四是长对话被压缩之后约束丢了。
五是工具返回的长内容挤占了窗口，指令被推到边缘。
对策依次是：正文瘦身、判据显式化、阶段性复述关键约束、限制工具输出长度。
其中最高频的是第三条，缺判据。举个例子：正文写"跑测试确认通过"，模型跑了个子集就报告通过了,因为"确认通过"这句话它可以自行解释。改成"必须执行全量测试,输出中必须包含 passed 与 failed 计数,failed 不为 0 即进入回退分支"之后,问题就消失了。
结论：判据必须写成可以外部验证的形式,每一步的产出都要能被检查，不能写"确认没问题"这种依赖模型自我解释的说法。
五、工程方法论
18. 一个 Agent 装了 1000 个 Skill 会发生什么？怎么优化？√
如果 Skills 太多了，假如你给项目配置了 1000 个 Skills，大模型对于 Skills 选择就不准确，怎么进行优化？
这是实际会遇到的问题。装到 1000 个之后会出现两类问题：
一是成本问题。1000 个技能的 description 全部常驻在上下文里，每一轮都要付这笔钱,一个都没命中也要付。
二是路由退化，这个更麻烦。描述空间被塞满之后，模型判断"哪个技能匹配"的准确率会明显下降,语义相近的技能会互相抢触发，而且很难定位是哪两个在抢。
对策有四条，按优先级来：
第一条也是最有效的一条：作用域收窄。技能不要全局挂载，按项目、按角色、按用户组分组挂载。多角色 Agent 系统天然可以做作用域收窄——评审角色看不到部署技能，调研角色看不到写操作技能。既降低常驻成本，也直接减少抢触发,比在 description 里反复加排除条件有用得多。
第二条：建立技能注册表和准入机制。重复功能的合并掉,不允许随手新建。每个技能有 owner、有评测集、有调用量看板。
第三条：用路由层或者索引技能做二级分发。先路由到类别（比如"这是代码类任务"），再路由到类别内的具体技能。这样每次决策要判断的技能数量就从 1000 降到几十。
第四条：定期按调用量下线僵尸技能。调用量长期为 0、评测分数长期不达标、功能被别的技能覆盖的，直接下线。
有个具体的量化建议：想给出"多少个技能开始退化"的经验值，做法是固定一个评测集，按不同挂载数量分档跑触发准确率,看从哪一档开始明显掉分。没实测过就说清楚自己的观察边界,不要凭空编一个数。
19. 误触发严重怎么办？两个 Skill 语义重叠怎么处理？
误触发的处理有四个手段：
一是在 description 里显式写排除条件，比如"不要用于纯数据查询"、"不要用于单条指标问答"。
二是收窄触发词，去掉过于泛化的词。
三是把过宽的技能拆成两个，让每个的边界都更清楚。
四是用负样本评测集把误触发率卡住。
这里必须指出一个双向权衡。把 description 写主动、召回率上去了，误触发同时也会上去。所以正负样本必须一起跑，看两个数——触发率和误触发率——而不是只看一个数。只优化一侧一定翻车。
语义重叠的处理，优先选合并。如果确实要分开,就给出互斥判据,而且必须写进双方的 description，不能只写一边。写完之后再用邻域负样本跑一遍,确认互抢率下降。
举个例子。"代码评审"和"测试修复"这两个技能会在"测试挂了帮我看看"这句话上抢触发。解法是互斥判据双写：有失败测试就走测试修复，没有失败测试、只是评估改动风险就走代码评审。两边 description 各写一句指向对方。
还有一个说法要准备：让用户显式点名调用技能是可靠的兜底，但它把路由成本转嫁给了用户,技能一多没人记得住名字。所以显式点名只能作为高危技能的保险机制，不能当成路由失败的兜底方案。
20. 怎么量化 description 写得好不好？√
要把 description 当成一个能跑分的工程变量，五步：
第一步，构造触发评测集。一批"该触发"的真实 query，加一批语义邻近但"不该触发"的负样本。这两批必须一起有,只有一批没意义。
第二步，每条 query 重复多次，3 次是常见起步。单次结果方差太大,跑一次得到的触发率不可信。
第三步，数据集划分训练集和留出集,60/40 常见。改完 description 之后两边都跑,最终版本按留出集的分数选。不划留出集就会过拟合到你手上的那批 query 的措辞，线上换个说法就失效。
第四步,迭代循环——跑评测、看失败样本、让模型基于失败样本提候选 description、重跑、收敛。一般 5 轮之内就收敛了。
第五步,评测 query 必须足够复杂。太简单的机制上就不触发（见触发机制那题），进去全是噪声。
有一个容易被合并、但必须分开的点：触发率和任务成功率是两组指标。"压根没触发"和"触发了但流程走偏"是完全不同的问题，混成一个数就没法定位问题在哪。
一次完整的迭代长这样：40 条正样本加 40 条邻域负样本,按 60/40 划分,每条跑 3 次。基线版 description 跑出触发率和误触发率两个数。针对失败样本补真实话术和排除条件,重跑。5 轮之内两个数都不再明显变化就收敛，最终版按留出集选。改一版就上线、不留基线，等于没量化。
21. 怎么证明 Skill 真的有用，而不是心理安慰？√
怎么证明你的 skill 真的有用，而不是心理安慰？
定量和定性两条一起做。
定量：同一批任务做两组对照，一组挂载这个技能，一组不挂载。比四个数——任务成功率、平均步骤数、token 消耗、人工返工率。这四个数才能说明技能到底有没有让事情变得更好。
定性：人工评审输出样本,看是不是踩到了已知的坑点。
配套还有三件事经常连着问：
一是评测集怎么构造。query 要来自真实流量，覆盖典型场景、边界场景、邻域负样本。输出可客观校验的任务（比如文件转换、数据抽取、代码生成、固定流程）优先做断言式评测，主观输出走人工评审。
二是 LLM-as-judge 的坑。有位置偏好、有长度偏好、跟被测模型同源会导致自我偏袒、评分标准还会漂移。对策是把主观判断拆成可判定的检查项（断言化）、盲评、打乱顺序、抽样人工复核对齐。
三是回归测试。技能改动、底座模型升级、工具接口变更都要重跑评测集。评测跑进 CI。每一版的评测快照都要保留,方便定位是哪次改动导致的退化。
有一点特别关键：成功的判定必须可断言，不能靠人的感觉。比如代码类任务定成"测试全绿加评审结论里没有 blocker"，两条都能被外部检查；报告类任务定成"必备章节齐全加数字与数据源一致加无禁用词"。
报数字的时候把口径一起给出——样本量、每条重复次数、判定标准。只说"用起来感觉稳多了"或者"跑过一次提升明显"，没有对照、没有重复、没有口径,这在面试里是一票否决。
22. Skill 怎么做版本管理和团队分发？
版本管理：技能进代码仓库，改动走 PR 评审。每个版本要有版本号加 changelog,写清楚这一版加了什么、为什么加——半年后没人记得某条约束是为了修哪个 case 的。更新的时候要保持 name 和目录名不变，改名会直接导致引用断裂和重复安装。大改动之前先跑一遍评测基线,改完之后跟基线对比。
分发主要有三种形态：打包成技能包（zip 形态的 .skill）、放到内部的插件市场、走仓库同步。企业内部大多数会选自建私有源加白名单同步，因为公共市场有安全风险。
CI 里怎么测：改动触发评测流水线，跑触发率和任务成功率；scripts/ 走常规单测和依赖扫描；SKILL.md 做格式校验，检查 frontmatter 字段齐全、name 与目录一致、description 长度合规；分数低于基线就阻断合入。
灰度和回滚：按用户组或者项目作用域灰度上线，保留上一版可以一键切回。观察窗口里盯任务成功率和人工返工率。技能版本要和底座模型版本绑定记录，出问题才能定位。
有一个特别容易漏的点：底座模型升级的时候必须重跑一遍所有技能的评测基线。同一个技能换模型之后,触发率和指令遵循度都会变。不重跑就分不清是技能改坏了还是模型换了——这也是为什么日志里要把技能版本和模型版本一起记。
六、场景与实操
23. 设计一个面向公司内部的 Agent 技能平台，支持 200 人、上百个技能
回答这种题必须先给分层,不给分层就直接判负。自下而上分五层：
底层是执行环境。沙箱隔离、目录白名单、网络出口管控、凭证不注入。这一层保证任何技能出问题都不会伤到宿主。
再上是工具/MCP 层。统一网关,统一鉴权,统一记账。所有外部调用都从这里过。
再上是技能层。私有源加白名单同步公共市场的技能,离线审计后入库；每个技能有 owner、有评测集、有版本。
再上是路由和作用域层。按角色、按项目、按用户组挂载,不允许全局挂载所有技能。技能多了之后加二级路由。
最上是评测和可观测层。触发评测、任务成功率评测、增量成本看板、下线看板。
四个评分维度对应四句话：
一、怎么处理技能数量增长——靠作用域挂载和二级路由,不是等退化了再补救。
二、安全要进设计而不是当补丁——最小权限靠执行环境强制,第三方技能离线审计后进私有源并锁定版本。
三、要有度量闭环——没有评测的平台就是技能垃圾场，只增不减。
四、分阶段落地——先用 10 个高频技能把"写、评测、灰度、看板、下线"这条完整闭环跑通,然后再开放自助创建。
几个常问的变体：
从 10 个涨到 200 个的治理：作用域挂载而不是全局装载；建注册表和 owner 机制；做重复度检测；上调用量看板并定期下线；分类目录加索引技能做二级路由；准入评审卡新增。
客服 Agent 技能化改造：按业务流程切分（退换货、物流查询、发票、投诉升级），每条流程一个技能；共用话术规范放 Rules；工具接入走 MCP；每个技能建评测集,逐个替换旧的巨型 prompt；灰度对比新旧的解决率和转人工率。
MCP 加 Skill 配合排查 CI 失败：MCP 提供 workflow run 列表、日志读取等工具；技能正文写清流程——先取失败摘要，再按需拉细节日志，拉不到就提示权限问题并转本地复现；输出格式固定为"失败原因加定位加修复建议加风险"。这题考的就是"先摘要后细节"和"失败回退"有没有落到正文里。
24. 如何编写高质量Skills? → 精准description + 单一职责 + 确定性优

第一，
description 要写得足够具体
。不能只写"做什么"，还要明确"什么时候该用、什么时候不该用"，最好直接给触发关键词和典型场景。描述模糊，模型就会该用的时候不用，不该用的时候乱用。
第二，
遵循渐进式披露
。SKILL.md 主文件保持精简，只放核心判断逻辑和工作流；详细的参考资料、代码模板、边界情况，拆到子文件里按需加载。这样既不会撑爆上下文，需要的时候又能拿到足够信息。
第三，
多用正反例
。光说应该怎么做不够，把常见的错误做法也写出来，尤其是那些看起来对但其实错的情况。
第四，
指令要可执行、详细、可验证
。少写生成高质量代码这种空话，多写写完必须跑测试、必须过 lint这种能落地的步骤。
最后
用真实用例反复迭代
，看模型在边界情况下表现怎么样，再回过头修描述和指令。
追问问题：
你的团队如何管理的Skills？
版本管理，整个 skills 目录直接进 Git 仓库就行，每个 skill 一个文件夹，改动有 commit 历史，团队成员 pull 一下就同步了。这也是 Skills 比传统 Prompt 工程强的地方，Prompt 散在各种文档里根本没法版本化，Skills 天生就是文件，天生适合 Git。
如何评估一个Skill的好坏？
可以用开源的评估skills来评估，从这
8 维度评分体系
，分三个阶段对应 Skill 的整个生命周期。
阶段一·能不能被发现（D1，15%）
D1 元数据质量：description 写得准不准、关键词全不全、有没有"什么情况别用我"的排除条件。这是唯一决定 Skill 生死的指标，过了这关才有资格谈后面。
阶段二·跑起来顺不顺手（D2/D4/D5/D6，共 50%）
D2 执行引导清晰度（15%）：触发后 Agent 知不知道下一步往哪走，每个动作清不清楚
D4 工作流完整性（15%）：从头到尾的流程通不通，有没有异常处理和分支逻辑
D5 输入输出清晰度（10%）：输入要什么、输出长什么样，有没有定义清楚
D6 资源利用（10%）：scripts/ 和 references/ 的使用是否合理，并被 SKILL.md 正文引用（
没引用 = 白占空间还扣分
）
阶段三·有没有存在的价值（D3/D7/D8，共 35%）
D3 领域知识密度（15%）：Skill 存在的根本理由，必须有通用大模型拿不到的干货——具体阈值、行业陷阱、内部经验
D7 写作质量（10%）：结构清晰、术语准确、Agent 能快速抓住重点
D8 范围与聚焦（10%）：专注做好一件事，明确边界
实操方法论补两点：
第一，每轮只改一个变量。最容易犯的错是一次性把所有毛病都改了，结果分数涨了不知道是哪个改动的功劳，跌了也不知道是哪个搞砸的。正确节奏是：改一个变量 → 跑一次评估 → 记录变化 → 决定下一步。
第二，关键决策上多模型交叉评审。单模型有偏见、有波动、有盲点（同一个 Skill 不同模型可能差一个等级）。日常迭代用单模型够了，但上线决策、团队定标杆、有争议时，让多个模型独立打分 → 互相质疑（差 2 分以上必须引证据） → 主模型仲裁，得出的共识更可靠。
25. 实操：写 / 改 / Review 一个 Skill
A. 现场写一个 SKILL.md（大概 15 分钟）
按七步走，评分点也是这七条：
一、frontmatter 里两个必填字段（name、description）要齐。
二、name 合规——小写字母加连字符，跟目录名一致。
三、description 要写清"做什么 + 什么时候用 + 排除条件"三部分。
四、正文要有步骤,而且每一步要有完成判据。
五、要有失败回退分支。
六、篇幅大的拆到 references/,确定性逻辑拆到 scripts/。
七、规定输出格式。
B. 改写一个很差的 description（大概 10 分钟）
坏例子："生成报告的技能。"
三个方向补齐：补做什么（数据来源、输出形态）加补什么时候用（季度总结、经营分析、月报、复盘都要命中）加补排除条件（单纯的指标查询不用本技能）。
C. Review 一个有问题的 skill
常埋的坑照着过一遍：name 跟目录名不一致；description 只写功能不写触发场景；正文 1200 行没分层；整本手册粘在正文里；scripts/ 里有 curl 管道执行；硬编码 API Key；没有失败分支；声明了 allowed-tools 就以为安全了。
一个可直接套用的骨架，以"PR 评审"技能为例：
第一步取改动范围和关联测试。
第二步逐项检查——接口兼容性、金额与精度、异常处理、测试覆盖，每一项都要给出结论和证据（文件加行号）。
第三步汇总输出,格式固定为"风险等级 + 问题清单 + 修复建议"。 失败回退：拿不到 diff 就报权限问题,不允许凭猜测评审。
检查清单细则放到 references/,diff 解析放到 scripts/,报告模板放到 assets/。这样一个技能就搭起来了。
