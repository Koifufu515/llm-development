## 2. 系统到底在做什么

它是办理订单相关事务的客服 Agent。与单纯回答问题相比，它还需要调用工具、推进流程，并处理用户中途更换订单、重复发起请求和电话中断。

最核心的分工是：模型负责理解用户意图、提出流程建议、组织回复；工程代码负责认定当前状态、限制工具、校验订单和提交结果。

资料里的示例流程包括“取证 → 判责 → 协商 → 处置”。我们先复现一个模拟订单争议办理场景，不连接公司内部接口、不执行真实资金操作。

## 3. 按一轮请求看完整链路

1. 入口收到会话 ID、用户消息、请求标识，以及可能携带的订单信息。
2. 热线编排层尽早并发准备四项任务：查打断、业务路由、非业务意图识别、承接话术生成。
3. 业务路由读取已提交的会话状态，让路由模型选择 Skill、概括意图，并建议 HOLD、NEXT 或 RESTART。
4. 工程状态机结合已提交状态、是否更换技能或订单、上一轮工具结果，算出本轮阶段。
5. 编排器加载该阶段的办理说明和允许使用的工具，生成执行计划，保留读取时的版本号。
6. 输出仲裁先看是否打断，再看是否由非业务流程接管；正常业务路径放行后，先输出承接话术。
7. 承接结束、业务路由就绪后，再查一次打断，然后执行业务 Agent。工具执行前还有硬性拦截。
8. 执行完成时校验版本，提交状态、工具结果和对话。旧轮次过期时丢弃状态回写。

注意：模型建议 NEXT 不等于本轮立刻已提交；准备阶段产生的是执行计划。资料还存在首轮订单种子预先写入等入口逻辑，不能把“准备阶段只读”扩大成“整个请求完成前绝不写任何数据”。

## 4. 先分清六个概念

| 概念 | 通俗含义 | 示例 |
| --- | --- | --- |
| Skill | 办哪一类事 | 订单争议处理、切换订单 |
| State | 这件事已经走到哪一步 | 当前处于协商阶段 |
| Reference | 当前阶段的办理说明 | 协商时应解释哪些信息 |
| Tool | 真正查询或改变业务数据的接口 | 查订单、提交处置 |
| Memory | 模型继续对话所需的消息上下文 | 前面讨论过的方案 |
| 工具台账 | 工程保存的执行事实 | 某工具已经成功执行 |

State 和工具台账不能只存在模型 Memory 中。流程切换时可以清理 Memory，但不能因此忘记已经发生的业务操作。

## 5. 第一个要亲手实现的模块：纯状态机

第一节暂时不依赖模型、Redis、HTTP。输入是普通数据，输出也是普通数据，便于看清规则。

输入：是否同技能同订单、已提交阶段、模型建议、有序阶段表。上一轮工具失败时，编排器先把 NEXT 降级成 HOLD，再传给状态机。

| 条件 | 输出阶段 | 输出动作 |
| --- | --- | --- |
| 没有阶段表 | 空 | NONE |
| 更换技能或订单 | 新流程首阶段 | RESET |
| 同流程，HOLD 或没有建议 | 当前阶段 | CONTINUE |
| 同流程，NEXT，尚有下一阶段 | 下一阶段 | ADVANCE |
| 同流程，NEXT，已经是末阶段 | 当前阶段 | CONTINUE |
| 同流程，RESTART，已经是末阶段 | 首阶段 | RESTART |
| 同流程，RESTART，尚未到末阶段 | 当前阶段 | CONTINUE |

这里有两套枚举：HOLD/NEXT/RESTART 是模型建议；RESET/CONTINUE/ADVANCE/RESTART/NONE 是工程决策结果。不要混成同一套。

第一节验收：能自己实现上述规则；为每条规则构造输入并验证输出；能解释为什么不能直接让模型输出“当前阶段”。

缺失状态、非法阶段等未被上表完整覆盖的输入，需要在复现中明确制定校验规则，不能凭空称为原项目行为。

## 6. 后续按这个顺序做

主实现沿用资料的 Java 21、Spring Boot、Redis 方向。框架的复杂部分逐步加入，不要求第一天掌握全部 Reactor 和 AgentScope。

| 阶段 | 实现什么 | 怎么证明做对了 |
| --- | --- | --- |
| 1. 状态机 | 阶段枚举、建议枚举、确定性决策函数 | 覆盖决策表，失败工具阻止推进 |
| 2. 会话与执行计划 | 会话状态、订单作用域、prepare/complete、Redis 存取 | 中途失败不误推进；不同会话相互隔离 |
| 3. 工具约束 | 按阶段装配工具、操作类工具拦截、执行台账 | 查询可重复；同一轮第二个操作工具被拦截 |
| 4. 切换订单 | 查单白名单、合法切单、旧上下文清理、原诉求暂存 | 不能切到未查到的订单；切到 B 后不复用 A 的工具结果 |
| 5. 并发提交 | 版本号与原子比较更新 | 两轮读取同版本，只能有一轮成功提交；旧轮不能覆盖新状态 |
| 6. 模型接入 | 路由结构化结果校验、阶段提示词、业务工具调用 | 同一场景先用固定路由结果验规则，再用真实模型验识别 |
| 7. 热线编排 | 四任务并发、最终决策、承接先行、打断处理、SSE | 未放行不输出承接；接管分支不混入业务回复；中断后停止后续输出 |
| 8. 资源隔离实验 | 模拟慢工具、模型流读取、专用执行资源、并发上限 | 对比共享资源与隔离资源下的排队、超时、首响应数据 |

每一节都按同样方式推进：用业务例子讲解 → 明确输入输出 → 看最小实现 → 你补一个分支或测试 → 故意制造一次失败 → 对应到面试追问。

不是把整套代码一次性生成后让你背。你需要能改规则、加场景、解释测试失败的原因。

## 7. 三条最终演示链路

### 正常办理

用户围绕订单 A 发起争议处理，阶段逐步推进；前置阶段只暴露对应工具，到处置阶段才允许执行操作。执行结果与最终状态能够查证。

### 中途换单

订单 A 的协商中，用户要求处理订单 B。先查询验证 B，再完成切单，清理 A 的阶段和 Memory，并在模拟的静默激活事件中续接原诉求。资料中的续接由特定静默激活路径触发，不是任意下一条请求都自动续接。

### 并发与中断

两轮请求故意重叠，让旧轮更慢完成；验证旧状态不会覆盖新状态。模拟电话中断，验证不再开始后续主 Agent 执行，并记录已经发生的工具副作用。

## 8. 原资料里需要特别辨清的地方

- 单轮 AtomicBoolean 工具拦截，只能限制该轮操作类工具数量，不等于跨请求、跨进程的业务幂等。真正的重复提交保护需要额外设计业务幂等键和存储约束，这是可独立实现的增强。
- 版本校验与保存必须原子完成，才能可靠处理并发。仅从文档描述无法确认原实现是否满足；复现时采用原子比较更新，并写并发测试。版本冲突丢弃状态，也不能撤销已经发生的外部工具操作。
- 状态机约束阶段，不自动证明用户同意。附录 F 的用户确认门禁属于提案；不能混作现有完成项。后续可以做成我们的增强模块，并单独验收。
- 取消信号、Future 中断、停止 HTTP 请求是不同层次。取消是否传到底层，需要通过日志或模拟服务验证，不能把“发出了 cancel”讲成“全部工作立即停止”。
- 承接话术优化的是用户何时先听到回复，不代表主模型生成变快。首响应时间、正式答案时间、全流程时间分别测量。
- Spring MVC 异步处理可以释放入口请求线程，但响应写入仍可能阻塞，不能背成“SseEmitter 写出完全不占线程”。依据：[Spring MVC 官方说明](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-ann-async.html)。
- 虚拟线程适合大量等待 I/O 的任务，不会直接让模型推理变快。仍要限制下游并发。依据：[Java 21 官方说明](https://docs.oracle.com/en/java/javase/21/core/virtual-threads.html)。
- 两份材料对自动摘要压缩的适用范围描述不同。先按 V2 明确描述的裁剪、隔离、台账机制实现；取得具体版本代码后再确认摘要功能。
- 文档中的池大小和队列上限是配置，不是实测 QPS；现有材料不支持填写线上性能提升百分比。
