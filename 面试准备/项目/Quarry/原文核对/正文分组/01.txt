项目介绍
一、项目简介
quarry-rag 是一个开源、可自部署、面向多应用复用的企业级 RAG 检索平台。
它不生成答案，只交付证据。给定一次查询、一个集合和调用方的 API Key，它返回一组经过混合召回、重排和同节去重的证据：每条证据带着命中原文和能对回原文的字符区间、交给大模型读的上下文、各路分数，以及其中易变数值的核实状态与核实日期；整个响应再附一个"建议拒答"的信号。上游的"知行旅行助手"拿这些证据去写行程、校验预算；换一个上游应用，平台不用改。
定位：一个只返回证据、可被任意上游复用的检索平台。

二、项目背景
2.1 产品亮点
只返回证据，不替上游作答，所以能被复用。
市面上的 RAG 教学项目大多把"检索 + 拼 prompt + 调模型"焊死在一个函数里，换个场景就得重写。本项目从第一天就把职责切开：平台负责"找到并证明"，生成留给上游。平台里没有生成端点，连"把证据拼进提示词"这一步也放在交给上游的客户端文件里。这条边界决定了接口的响应形状、拒答信号的职责划分，也决定了评测只评证据、不评答案。
两个容器起全栈，第一节课就能跑出检索结果。
基础设施全程只有 postgres + pgvector 和 redis-stack 两个现成镜像。向量检索、全文检索、元数据与权限过滤、事实数据、评测记录、API Key、查询日志都在同一个 PostgreSQL 里，Redis 只管接入队列和限流计数。不装 Elasticsearch，不装独立向量库，不自建数据库镜像；到第八章上线时，才加一个用项目 Dockerfile 构建的接口容器。没有 API Key 也能用 fake 向量把第一章跑通。
直面"检索对了但答案过期"这个真问题。
比如旅行场景里门票价格、开放时间全是易变数值：检索命中的段落完全正确，照抄出来的数字却可能是两年前的。项目用一个独立的事实层处理它：离线从正文里抽出易变数值，对照运营维护的官方数据；查询时把上下文里的数字换成占位符，把核实过的值、核实日期和"已核实 / 已过期 / 未核实"三种状态一起交给上游。上游能写进答案的数字，只剩平台给的那一个。
评测不是最后一章的收尾，是调参的前提。
重排值不值得开、事实层有没有拖累别的指标，第五、六章只留下问题，第七章用数字回答：用标注集跑一条基线，每次只改一个开关，逐题列出哪些问题变好、哪些变坏，再用一道回归闸门守住以后的每一次改动。没有量具就调参数，是"感觉变好了"；有量具，才是"知道调对了"。
每一种静默失败，都配一道当场报错的闸。
RAG 系统里最难查的错都不报错：共享 CTE 让向量索引白建，强过滤下返回 0 条，重排接口挂了按原顺序返回，同一个 chunk_id 在两个集合之间撞车，改过的语料忘了重新接入。课程把这类坑逐个标出来，每个都配一道会响的检查：数据库约束、校验脚本、冒烟测试、红线用例、回归闸门。
可以直接交给上游的交付形态。
一个
/v1/search
接口：API Key 决定调用方的权限标签和可访问的集合，按 key 限流，整条链路 5 秒总超时，错误统一形状并带
request_id
，每个请求留一行只记问题、块 ID 和耗时的查询日志。一个单文件 Python 客户端：重试策略、错误分类、提示词拼装都已写好，复制进上游项目就能用。再加一份不含向量、校验和可复现的索引快照，留给想自建索引的下游。
2.2 技术亮点
单条 SQL 完成过滤、双路召回与 RRF 融合。
向量召回和全文召回是同一条 SQL 里的两个子查询，FULL OUTER JOIN 之后按倒数排名融合，一次数据库往返拿到结果，两路权重和 RRF 的 k 都是参数。四个过滤条件在两路里各写一遍，不提成共享 CTE：共享 CTE 被引用两次就会被物化，向量那一路从此用不上 HNSW，而在几千行的数据上完全看不出来。融合按数据库主键对齐，不依赖任何进程内的哈希。
内容决定标识，接入管道幂等。
chunk_id 由"集合短名、来源、标题路径、归一化后的正文"算 sha256 得出，跨进程、跨机器都稳定；数据库主键是
(collection_id, chunk_id)
，同样的内容进了两个集合也不会互相覆盖。文档级 sha256 让没改过的文件整条管道跳过，块级 chunk_id 决定要不要重算向量：改一个字只重算那一个子块，删掉的小节当轮清成孤儿块，旧版本的块在新版本就绪后退役。接入队列是至少一次投递，重复处理由幂等兜底；换模型、换切分策略走集合级的蓝绿切换，部分唯一索引保证同一时刻只有一个 active 集合。
结构感知切分与父子块合表。
按标题栈建树，不按固定字符数切；表格和代码块整块保留，超长段落在句末标点处切开。一个标题小节是一个父块，下面打包若干 400 字左右的子块，两者同在 chunks 表里用 level 区分，三条 CHECK 约束挡住形状错误。检索只查子块，命中后再回捞父块和前后邻块。每个块的 [char_start, char_end] 都能从原文逐字取回，有脚本全量校验。
强过滤下的召回保障。
HNSW 先按距离取一批候选、再做过滤，调用方只能看极少数文档时会返回 0 条，而且不报错、不告警。项目用 pgvector 0.8 的迭代扫描兜住：relaxed_order 加 max_scan_tuples，用 SET LOCAL 限定在事务里，不污染连接池。配套的压测脚本造出一份可复现的数据，把 ef_search 从 40 调到 1000 时返回条数一格一格补齐的过程跑出来；分区裁剪讲清适用边界，不落地。
权限允许制，从数据库一路守到接口。
块上冗余存一份权限标签，混合召回以及父块、邻块、事实提及的回捞 SQL，都在数据库层用数组重叠强制过滤。接口层的权限标签跟着 API Key 走，请求体里夹带的标签一律无效，集合另有白名单。11 条红线用例里有 9 条和权限有关，而且都带反向验证：该看不到的看不到，该看到的也看得到。
半精度向量与部分索引。
halfvec(1024) 让向量存储和 HNSW 索引都小一半，排序几乎不受影响。HNSW 和全文 GIN 都是只建在子块上的部分索引，查询不带 level = 1 就用不上，课件用 EXPLAIN 当堂验证。m、ef_construction、ef_search 三个参数按成本讲清：前两个在建索引时一次付清，最后一个每次查询都要付。
重排是一段可以关掉的链路。
Reranker 协议下有两个实现：对接百炼 qwen3-rerank 的托管实现，和什么都不做的空实现（代码里的默认档，也是对照组）。重排失败不抛异常，按原顺序降级，这也意味着配置写错时它会悄悄失效，所以配了一个冒烟测试，按 rerank_score 是否为空判断"真的重排过"。开不开由第七章的对照实验说话：召回涨了多少、P95 多了多少，两个数字摆在一起。
原文、上下文、引用分开交付。
text 是命中原文，只用来高亮；context 交给大模型读，按"带邻块、只有本节、只有命中块"三档，在 6000 字的预算内逐条降档，同一小节多次命中只留一条。引用带定位粒度：Markdown 精确到字符，Word 只到段落，做不到的事写进响应，不让上游误用。
拒答信号：平台给建议，上游做决定。
用召回结果里最高的余弦分和集合自己的阈值比较。融合分只反映名次，有答案和没答案的问题挤在同一个区间里分不开；重排分会随重排开关出现或消失，也不适合当基准。阈值用"有答案、没答案"两组查询标定后写进集合配置，开关重排都不用重新标定。
事实层：遮住易变数值，补上核实过的值。
大模型用 JSON 模式从父块里抽出门票价格和开放时间，只让它逐字抄出原文片段，位置由代码去找，不合契约的条目直接丢弃；每个块抽过就记一笔，内容不变就不重复花钱。官方值来自运营维护的 CSV，整体替换导入，按名称和别名匹配。查询时正文里的数值换成〔F1 门票价格〕这样的占位符，真实值、核实日期和三种状态放进证据的事实列表；核验全在离线完成，查询时只多一条 SQL。
先有量具再调参：三层评测加一道闸。
第一层是确定性的红线、单元与契约测试，进 CI。第二层是标注集上的检索指标：召回率、MRR、首位命中率、误拒率、正确拒答率，命中与否看引用区间是否落在金块之内。第三层是裁判模型给出的证据支撑率，它只判断证据够不够回答，不评答案。对照工具逐题列出变好和变坏，回归闸门拦住指标大跌，结果渲染成一个能直接发出去的单文件 HTML 报告。
全链路异步，CPU 活进线程池。
检索链路从头到尾是异步的，查询向量化（网络 I/O）和 jieba 分词并发执行。jieba 是纯 Python 实现，放进线程池解决的是"不堵事件循环"，不是并行加速，课件用一次压测对照把差别量出来。日志写盘也走独立线程，一样不卡事件循环。
2.3 学习收获
一套能对外交付的检索平台，而不是一个 notebook 里的 RAG demo。
数据模型、接入管道、检索引擎、重排与上下文、事实层、评测、对外接口，全链路自己写过一遍，最后得到一个带鉴权、限流、日志、能容器化部署的服务。
"先有量具再调参"的工程直觉。
这是本课最想留给你的东西：拿到一个效果不好的 RAG 系统，第一反应是建标注集、跑基线、逐题对照、用单次查询的分段结果定位原因，而不是改 prompt 或换更贵的模型。
在 PostgreSQL 上把检索做深。
HNSW 参数、halfvec、GIN 与算子类、部分索引、用部分唯一索引做蓝绿切换、迭代扫描、单 SQL 双路召回、用 EXPLAIN 确认索引真的被用上，这些能力在任何用 PG 的团队里都能直接复用。
幂等与可重建的设计习惯。
内容决定标识、两级短路、孤儿清理、至少一次投递配幂等、校验和可复现的快照，这套思路不只属于 RAG，任何数据管道都用得上。
对技术选型的判断力。
课程里明确讲了三个"不选"：不选 Elasticsearch、不选独立向量库、不选重型解析服务，每个都给了引入判据和失效条件。面试里能把"什么时候该引入第二个检索后端、代价是什么"讲清楚，比做过一个跑不满负载的双后端更站得住。
RAG 系统的真实失败模式。
重排为什么会悄悄失效、强过滤为什么会漏召回、共享 CTE 为什么让向量索引白建、chunk_id 为什么会在蓝绿切换时撞车、事实层该给哪些集合开、标注集为什么要固定不动，这些是踩过才知道的东西，课程直接给。

接口层只做翻译和把门。
认 key、限流、校验参数、把结果转成 JSON、记日志，任何检索逻辑都不写在这一层。

接入链路（第三章）
文件 → 解析 → 切分 → 算 chunk_id → 查库挑出新块 → 只给新子块算向量 → 一个事务里写入并清掉孤儿块 → 新版本就绪后退役旧版本。批量接入用脚本跑，单个上传走 Redis Stream 队列异步处理。
检索链路（第五、六章）
查集合 → 混合召回 → 重排 → 同节去重 → 回捞父块、邻块和文档信息 → 事实层遮蔽 → 按预算组装证据 → 拒答信号。每一段都有分段计时，整条链路的延迟预算是 P95 ≤ 800 毫秒（不含上游生成答案的时间）。评测不走接口，直接调
search_evidence()
跑标注集。
