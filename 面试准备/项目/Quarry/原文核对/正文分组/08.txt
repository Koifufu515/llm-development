3.4 索引构建
这一节把前面两步串起来：文档 → 解析 → 切分 → 向量化 → 写入。核心是

3.4.1 幂等是什么，以及两级短路
幂等
的意思是同一个输入，操作一次和操作一百次，结果完全一样。
打个比方：电梯的上行按钮是幂等的，按一次和按十次，电梯都只来一趟。抽号机不是幂等的，按十次出十张号。接入管道必须做成电梯按钮那种。
依据是第二章 2.7 的稳定块标识。
chunk_id
由集合短名、来源、标题路径、归一化后的正文四样东西算出来，内容没变则 ID 不变。
本项目有两级短路，粗的挡在前面，细的兜在后面：
文档级短路挡住"文件完全没动"；块级短路挡住"文件动了，但大部分内容没动"。改一个字，文档级拦不住，块级会把没动的块全部放过，只重算那一个。

旧块清理：文档里删掉或改掉的内容，索引里也要跟着消失

一份大文档解析要几十秒，不能占着 API 进程
进程崩了，任务不能丢
一次上传 100 份文档，要能多个进程一起处理
打个比方：前台收件和后厨做菜是两件事。前台收下单子给你一张小票就让你走，后厨按单子做。单子贴在墙上，厨师换班也不会丢。Redis Stream 就是那面墙。
3.5.1 Redis Stream 是什么
Stream 是 Redis 5.0 引入的持久化消息日志，专门为"消费者组"这种用法设计。先对比一下常见方案，看清楚它补了什么：
三个概念要记住：
① Stream 是一本只能往后写的流水账
。生产者用
XADD
追加一条，每条有唯一 ID，形如
时间戳-序号
。
② 消费者组是一群人共用一份进度
。同一个组内，一条消息只会被组里的一个人收到。用
XREADGROUP
读，处理完用
XACK
销账。
③ PEL 是"已领走但还没销账"的清单
。用
XREADGROUP
读到的消息不会立刻从组的视角消失，而是进入 Pending Entries List。只有
XACK
之后才算彻底完成。消费者崩了，PEL 里的消息可以被别人用
XCLAIM
认领接着做。这就是"至少一次投递"的基础。

3.5.4 消费者
写文件：

五个处理

**①

**② **

**③

**④ 失败不 **
