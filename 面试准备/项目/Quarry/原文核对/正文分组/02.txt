八、能力边界说明
明确不做的事，写进课件第一节，避免期待错位：
不做答案生成。
平台里没有生成端点，也不做查询改写和 HyDE。提示词拼装由客户端文件里的
render_for_prompt()
替上游做好，调模型、写答案是上游的事，理由在第 1.3 节展开。
不做多模态检索。
图片、音视频不在语料范围内。
解析只覆盖两档。
Markdown 与纯文本（A 档）、Word（B 档）。PDF、Excel 给了实现思路但没有注册进解析器，扫描件和复杂版式（C 档）只给协议。Word 文档的引用只能定位到段落，不能定位到字符。
不做实时数据源。
事实层的官方值来自离线维护的数据文件，查询时不联网核验。超过 90 天没有重新核实的值会标成"已过期"照常交付，不会被当成新的。
事实层只管两类数值。
门票价格和开放时间，季节只分全年、旺季、淡季；只对打开了开关的第三方语料集合生效。
不做跨语言检索。
语料与查询默认中文，英文文档按中文链路处理，效果不做保证。
不做多版本并存。
文档出了新版本，旧版本的块直接删除，文档行留着审计；要比较两套索引，走集合级的蓝绿切换。
只有一种接入方式。
对外是 REST 接口加一个 Python 客户端文件，不提供 MCP 服务端，也不提供其他语言的 SDK。
限流不精确。
按 API Key 的每分钟固定窗口计数，窗口交界处最多能放进两倍请求；它防的是上游写出死循环，不是计费。
性能结论有适用规模。
所有实验在教学语料（几十份文档、一千来个子块）和 5000 块的合成压测数据上得出；"单机 PG 能承载几百万到千万级子块"是经验值，课程没有实测。

1.3 一条必须先讲清的红线：只返回证据，不替上游作答
这门课全程会有一个诱惑：既然检索都做完了，顺手调个模型把答案写出来不是更完整吗？
不行
。一旦平台开始生成答案，三件事立刻发生：
职责边界消失
。上游要改 prompt 得来改平台，平台的版本发布被上游的业务节奏绑架。
评测目标被污染
。生成质量的波动会盖住检索质量的变化，你再也说不清"这次改动到底让召回变好了没有"。
复用性归零
。第二个上游应用来接的时候，它要的答案格式和第一个不一样，平台里就会长出一堆
if
。
所以红线是：
平台交付证据，上游负责作答
。整个项目里没有生成端点，也不做查询改写和 HyDE。连"把证据拼进提示词"这一步，都放在第八章交给上游的客户端文件里（
render_for_prompt()
），而不是放在平台里。
记住这句话，它会决定后面好几章怎么落地：拒答信号为什么是"平台给建议、上游做决定"（5.6.1），评测为什么只评证据不评答案（7.1.1），接口层为什么只做翻译和把门（8.1.1），全都从这条红线派生。

2.2 为什么全链路异步
平台最终是要扛并发的服务，而且检索链路里全是长 I/O：向量化调用、重排调用、数据库查询。第一章就用异步写自检脚本，第四章的检索代码直接是异步的，到第八章塞进 FastAPI 不必推倒重写。
