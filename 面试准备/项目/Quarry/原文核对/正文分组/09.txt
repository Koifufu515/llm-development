4.1 向量检索
4.1.1 HNSW 怎么工作
HNSW 的全称是 Hierarchical Navigable Small World，翻译过来是"分层的可导航小世界图"。名字唬人，原理用交通网就能讲清楚。
想象你要在一座城市里找"离我最近的咖啡店"：
最上层是高速公路
。出入口很少，但一脚油门能跨半个城市
中间层是主干道
。密一些，能到每个片区
最底层是街巷
。每家店门口都通，但一步只能走一小段
搜索的过程是先上高速，几步开到大概区域，再逐层下沉，最后在街巷里仔细比较。这样既快（不用挨家挨户算距离），又比较准（最后一段是仔细找的）。
两个必须记住的性质：
① 它是近似的，不保证找到真正的前十名
。只保证大概率找到。正常情况下这个概率很高，但在"只能看极少数文档"的强过滤场景下会明显下降（4.5）。
② 索引要常驻内存才有意义
。图搜索是随机跳跃，在磁盘上随机读比算向量距离慢好几个数量级。一旦索引装不进内存，性能是断崖式下跌，不是线性变慢。这也是第二章 2.4.2 选

的根本原因。

4.3.5 RRF：倒数排名融合
公式很短：
为什么用排名而不是原始分数
。dense 用的是余弦距离，范围大约 0 到 2；sparse 用的是
ts_rank_cd
，范围大约 0 到 1，实际值常常小于 0.1。两个尺度完全不同，直接加权相加没有意义，等于把体重和身高加起来。倒数排名把两者归一化到同一把尺子上：第 1 名得 1/(k+1)，第 2 名得 1/(k+2)，和原始分数长什么样无关。
k 是干什么的
。它决定"排名靠后衰减得有多快"。k 越大，第 20 名和第 40 名的分数越接近，也就是越不在乎具体名次；k 越小，前几名的分数差距越大。60 这个值来自 RRF 的原始论文（Cormack 等，2009），在很多任务上被验证是个通用的起点。本项目把它做成参数
$10
，方便第七章调。
权重怎么调
：
改权重之前先有量具：第七章的标注集能告诉你改完是变好还是变坏。
思考题
：一个块在 dense 里排第 1，在 sparse 里完全没上榜。另一个块在 dense 里排第 3，在 sparse 里排第 2。默认权重和 k=60 的情况下，谁分高？
答案
：第一个块 0.5/61 ≈ 0.0082。第二个块 0.5/63 + 0.5/62 ≈ 0.0079 + 0.0081 = 0.0160。
第二个块接近第一个的两倍
。这就是 RRF 的性格：它强烈奖励"两路都认可"。理解这一点，4.8 的调试台里很多看起来奇怪的排序就都解释得通了。
4.3.6 融合键：chunk_id 稳定的价值
回看第二章 2.7.3 那张表里的两行：
hash(content)
：Python 每次启动换一个随机盐，进程间不一致
id(对象)
：两路返回的是不同的 Python 对象，永远对不上
本项目的融合发生在 SQL 里，用的是数据库主键

这是第二章那一节的兑现点
。如果当时用了会变的 ID，FULL OUTER JOIN 这一步会退化成简单拼接：两路都命中的块会被当成两个不同的块，各自拿一份低分，然后双双沉底。不报错，只是效果变差。

4.4 过滤与权限
4.4.1 过滤必须在 SQL 里做
先看一个反例：
这个做法在三个地方错：
① 排名被污染
。你按分数取前 100 名，过滤掉没权限的，可能只剩 3 条。你想要 10 条，但剩下那些排名太靠后，早就被
LIMIT 100
截掉了。用户看到的不是"他能看的内容里最相关的 10 条"，而是"最相关的 100 条里碰巧他能看的那几条"，这两件事差别很大。
② 多一层出错空间
。应用层的过滤代码可能改错、可能在某个分支里忘了调用、可能被新加的接口绕过。写在 SQL 的 WHERE 里，是数据库在每一次查询上强制的。
③ 白白搬数据
。100 条里过滤剩 3 条，97 条的网络往返、内存拷贝、反序列化全是浪费。
正确做法是过滤条件进 WHERE，让索引扫描阶段就用上
。4.3.3 那条 SQL 的两个子查询里各有四行 WHERE，就是这件事。
4.4.2 元数据过滤：JSONB 包含
@>
读作"包含"，判断左边的 JSON 是否把右边整个含在内。第二章 2.4.3 已经在 psql 里试过。第二章 2.6.3 建的

用的是

算子类，专门为

优化，规划器会自动选它。
用起来是这样：
第三章的接入脚本给父块和子块都写了

（原文链接、许可证、抓取日期），所以这里按任何一个键过滤都有结果。在 psql 里确认一下子块的

**没有过滤条件时传 **
{}
。任何 JSONB 都"包含"空对象，

永远为真，相当于不过滤。所以

这个参数第八章会开放成
