一、项目整体

介绍一下这个项目 ★★★

简短版

这是一个基于 LangGraph 的多步骤旅行规划 Agent。用户从"我想出去玩"开始，通过多轮对话一路走到拿到逐日行程和预算。核心设计是一个 Agent 加一张步骤配置表来驱动整条规划流程，经 MCP 接了 12306、航班、酒店、地图、天气等 9 个真实数据源。车次、票价、天气这些事实数据全部来自实时查询，并且由代码渲染，模型只负责理解用户和组织表达。配套有 SSE 流式接口、行程清单落库，以及在线、离线两道质量评测。

详细版

做这个项目，起因是直接让大模型做旅行规划会出现很多幻觉：编一个看起来很像的车次；多城行程把三段交通全按出发日去查；或者是预算靠心算。这些错都不报错，用户拿到手才会发现。所以整个项目的思路，是把模型做决策这部分和工程基础设施分开：模型负责理解和表达，段数、日期、查询、校验、落库全部交给确定性代码。

结构上分四层。最外面是编排层：一条消息进来，按直查、快速、状态机三条通道分流。中间是状态机 Agent：TravelState 里记着当前步骤，自定义的 AgentMiddleware 每轮按步骤注入提示词和工具，前向工具负责推进，回退工具负责跳回。下面是工具层：状态机工具、MCP 工具、RAG 检索工具，还有多段高铁、航班、自驾、多城住宿四类并行能力包。最底下是持久化：会话状态存在 PostgreSQL 的 Checkpointer 里，用户的长期偏好存在 Store 里，业务表存用户、会话、消息和行程清单。

对外是 FastAPI，发消息走 SSE 流式返回，前后端约定了 8 种帧。质量这块，每份落库的行程会在后台按完整性、需求匹配度、真实性三个维度打分；开发期踩过的坑沉淀成 pytest 回归用例。

开场后最常见的追问是"有没有上线、多少用户"。这是个人项目，没有线上流量，简历上的数字都是本地实测，被问到就如实说。

流程是"8 步"：需求、目的地、交通、住宿、餐饮、行程、预算、报告。终版里报告这一步合并掉了，行程正文和预算表由代码在行程步直接渲染，预算汇总就是流程终点。被追问"第 8 步在哪"就这么说。

一条消息从发出到返回，经过了哪些模块？★★★

前端调接口，带上会话 id 和内容，JWT 放在 Authorization 头里。端点先鉴权，再校验这个会话是不是当前用户的，然后调编排入口 run_chat_turn。这个函数立刻返回一个事件流对象，真正的编排丢到后台任务里跑，端点拿到流就开始 async for，来一帧推一帧。

后台的编排函数按顺序做六件事：存用户消息；读最近 4 条历史做意图路由，同时过一遍直查门禁；按三条通道分流执行；如果走到了行程或预算步，就生成行程清单落库；推 done 帧；长回复压缩成摘要存进 content，全文放进 extra_info，再落库。

状态机通道里，执行器拉起 Agent，用 astream_events 流式跑一轮，回合结束读状态机快照，再按当前步骤做几处代码后处理，比如渲染真实班次表、天气、行程正文，最后把四样东西交回给编排层：最终文本、当前步骤、本轮是否落库、逐日结构。

项目里最大的难点是什么？★★★

我觉得最难的是一类不报错的失败：结果看起来正常，其实是错的。我挑查得最深的一个讲：车票工具的守卫被绕过了。

背景是 12306 单次返回能有几百趟车、几万字，我实测过一次 287 趟、4.5 万字。模型被这么长的返回淹没之后，会编出真实数据里根本不存在的车次。所以我给车票工具包了一层守卫：入参做别名归一和上下文回填，结果按发车时间排序只留前 12 趟、一趟一行。

第一版我是在"按步骤取交通工具"的那个函数里套的守卫，日志看着像是生效了。但真实跑图的时候，ToolMessage 里还是三万多字的 12306 原文，日志里一条"车票结果裁剪"都没有，还把模型的输入长度上限撑爆了。

排查下来，原因是中间件注入给模型的工具，和 ToolNode 实际执行的工具不是同一批对象。中间件改的只是"给模型看哪些工具"；模型吐出工具名之后，ToolNode 是按名字去 create_agent 注册的那张总表里取对象执行的，那张表里放的是原始工具。所以修法是在注册的地方也同样套一遍守卫，两边用的是同一个包装对象。

这件事之后我定了一条规则：中间件管的是"给模型看什么"，管不了"实际执行哪个对象"。后面这条规则又用上了一次：手动确认模式下，中间件已经把"住宿加餐饮一站式确认"这个工具从工具表里摘掉了，模型照样能调用它，所以我在工具内部再判断一次当前是不是自动确认模式，不是就拒绝，而且不写任何状态。

同一类不报错的问题还有一个：表单只勾了航班，系统推荐的目的地是苏州，苏州没有民用机场，航班卡片每轮都是空的，兜底话术让用户"改选高铁"。用户回了"高铁吧"，可状态里的交通方式还是航班，下一轮命中同一个分支，连续三次回复同一句话，错误日志里一条记录都没有。修法是交通步在跑 Agent 之前，先由代码识别用户的改选并落库；同时区分两种空：没有机场码是结构性的，直接降级高铁并说明原因；数据源这次没返回才提示稍后重试。

二、状态驱动的单 Agent 编排

为什么是一个 Agent 加状态机，而不是每步一个 Agent 或者是多 Agent？★★★

每步一个 Agent 看起来职责清楚，但会遇到三个问题。第一是状态传递：目的地 Agent 选完的结果要交给交通 Agent，8 个 Agent 之间要接 7 根状态线。第二是对话历史断开：每个 Agent 有自己的历史，用户说"改回上一步"，上一步在哪个 Agent 里、历史怎么接回来，都不好处理。第三是排查困难：出了问题，得先猜用户当时在跟哪个 Agent 说话。

所以我用一个 Agent，让 State 里的 current_step 记住当前在哪一步，自定义的 AgentMiddleware 每轮调模型之前，按 current_step 换提示词、换工具。状态一份、历史一份、Checkpointer 一份，回退就是把 current_step 改回去，再清掉后面的数据。步骤之间的差异全部收在一张 StepConfig 配置表里，每一步是"提示词、工具列表、前置依赖字段"三项，加一个步骤主要就是加一项配置。

代价也有：中间件会越写越重，终版大概七百行，里面除了换配置，还有确认闸门、卡片接管、历史修复这些逻辑；所有步骤共用一个模型配置，没法按步骤换模型。

追问：为什么不直接画一张 8 个节点的 LangGraph 图？ 子图我也用了，目的地推荐就是手搭的 StateGraph，那是固定的并行分支，适合画成图。主流程是对话驱动的，每一步都要等用户回复，还要能在任意步骤之间回退，画成图就是一堆条件边。用状态字段加中间件，回退就是改一个字段，更简单。

"单 Agent"指的是一个 Agent 定义。被问"是不是全局只构造一次"要如实说：执行器每一轮都会调 create_travel_agent 重新组装。

一轮请求里，Middleware 具体做了什么？★★

中间件实现的是 awrap_model_call，每次调模型之前执行一遍，按顺序做这几件事：

  1. 读 current_step。新会话还没有这个字段，默认从需求收集开始。

  2. 去 StepConfig 里取这一步的提示词、工具和前置依赖。

  3. 校验前置依赖。比如预算步要求 itinerary 字段已经有值，没有就直接抛异常。宁可报错，也不让模型拿着一个空字段往下写：不校验的话，空值会被渲染成字符串 "None"，模型看到"逐日行程：None"就会编一份出来。

  4. 加载用户长期记忆，失败不阻塞。

  5. 用 Jinja2 把 State 里的字段渲染进提示词，同时注入确认模式的说明文案、多段行程的"当前第几段"。

  6. 按条件裁剪工具表：手动确认模式的闸门、卡片模式下摘掉查询工具。

  7. 修复残缺的工具调用历史，按用户轮裁剪过长的上下文。

  8. 用 request.override 一次性换掉系统提示词、工具和可选的 tool_choice。override 返回新对象，不改原来的请求。

  9. 把本轮的出发地、目的地、段日期、当前段写进一个 ContextVar，给车票守卫回填参数用。

最后才把请求交给下一环，真正调用模型。

每一步暴露几把工具？为什么要控制？★★

每一步暴露给模型的工具在【每步工具数】把左右，总表一共注册了【总表工具数】把。总表是在 create_agent 时一次性注册的，中间件按步骤从里面挑一部分给模型看。

控制工具数，是因为给模型看的选项越少，它的行为越集中。交通步要是能看到"选餐饮"的工具，模型就可能去推进餐饮。回退也做成了 7 把不用传步骤名的快捷工具，比如"回到目的地"，模型不用自己把"换个目的地"这句话翻译成一个步骤名字符串。

但工具筛选只是引导，不是防线。ToolNode 是按工具名去总表里取对象执行的，模型只要吐出了某个工具名，不管这一步有没有给它看，都能执行。所以关键的工具内部还要再判断一次，比如一站式确认工具判断是不是自动确认模式，回退工具判断用户有没有真的要回退。

数字来源：日志里的"已注入步骤配置: N 个工具"和"Travel Agent 创建完成，注册了 N 把总工具"。总表数会随在线的 MCP 服务变化，写启动时那次。

前向工具为什么用 Command 同时写数据和推进步骤？★★

每个推进工具都返回一个 Command，update 里同时放三样东西：给模型的一条 ToolMessage、这一步的业务字段、新的 current_step。比如选目的地的工具，写入 selected_destination，同时把 current_step 改成交通规划。LangGraph 把这个 update 合并进 State，再存一份 checkpoint。

放在一个 Command 里是为了原子性：不会出现"目的地写进去了、步骤没推进"或者反过来的中间状态。校验不通过时，Command 里只有一条以 ❌ 开头的错误消息，不写字段、不推进，模型看到后改参数重新调用。要么正确写入，要么完全不写。

这里有个坑：current_step 是单值通道，一步之内只能写一次。自动确认模式下，模型经常在同一轮里先后调"选住宿"和"选餐饮"两个工具，两个 Command 都写 current_step，就会报 InvalidUpdateError。我有两种处理。一是给自动模式做一个合并工具，住宿和餐饮在一个 Command 里写完，步骤只写一次。二是给 itinerary、budget 这类产物字段挂一个自定义 reducer，规则是新值为空就保留旧值，这样同一步里一个工具写空、一个工具写结果，既不会冲突，也不会把结果冲掉。

代码里直接改状态的地方也一样，aupdate_state 要一次写全，同一个线程分两次写会报 Ambiguous update。

追问：ToolMessage 为什么必须带 tool_call_id？ LangGraph 要靠它把工具结果和那一次工具调用对上。对不上，历史里就会留下"有工具调用、没有结果"的残缺记录，之后每次调模型都返回 400。

回退是怎么实现的？为什么要级联清空？★★

靠两张登记表：一张记步骤的顺序，一张记"每一步会写哪些字段"。回退到第 X 步时，把 current_step 改成 X，同时把 X 以及之后每一步登记的字段全部置为 None。X 本身也要清，因为用户回来就是要重新做这一步。

必须清空，是因为不清会串数据。用户在住宿步说换目的地，State 里已经有按旧目的地选好的车次和酒店；只改步骤不清数据，用户选了新目的地三亚，后面还挂着"北京→天津"的车次。

置为 None 而不是删掉字段，是因为 checkpoint 按增量合并，增量只能表达"改成什么"，表达不了"删掉"。

最容易漏的是流程游标。交通步登记的字段里有段游标、每段的选择、每段的票价，住宿步有城游标和每晚房价。游标不清，它就停在旧值上：用户重选目的地后去确认第 1 段，代码按残留的游标认为该确认第 2 段，直接判成传错段，流程就卡住了。

加步骤、改字段只改这两张表，回退函数本身不用动。最后一步是终态，不允许回退到那里，直接拒绝。

回退为什么要加意图守卫？为什么只加在一部分回退工具上？★

实测模型会自己决定回退：在交通步的第一轮，它自己调了"回到目的地"，把用户刚确认的目的地清空了。

所以我给回退工具加了守卫：取最近一条用户消息，用统一的意图词表判断用户有没有表达"换、改、重新选"的意思。判断分两层，一层是单独出现就算数的短语，比如"重新选""不想去"；另一层是动作词和对象词同时出现，比如"换"和"目的地"。用户没表达这个意思，就拒绝回退，并告诉模型"用户没要求换目的地，继续当前步骤"。

守卫只加在回到需求、回到目的地、回到交通这三个工具上，因为它们清掉的是后面所有步骤都依赖的根数据，误调的代价大。回到住宿、餐饮、行程、预算只影响后面一小段，误调了也容易恢复，加守卫反而可能挡住用户真实的意图。

词表故意写得比较宽，因为用户不会用工程师的说法。误退了，用户说一句就能拉回来；该退没退，用户反而不知道该怎么说。

有了状态机，模型会不会不问用户就自己往下推进？★

会，这是手动确认模式下最常见的问题：模型一轮里把"查询、展示、替用户选"全做完了，用户还没开口就推进到了下一步。提示词里写了"等用户确认后再调用"，约束不住。

所以我在中间件里做了一个确认闸门。判断依据是最后一条用户消息是不是纯确认语：整句去掉末尾标点后，正好是"确认、好的、可以、没问题"这类词才算。不是确认语，就从工具表里摘掉所有推进工具，模型只能展示和追问；是确认语，就放行，并且用 tool_choice 强制调用这一步的推进工具，防止模型只回一句"已确认"却不动状态机。

比如用户说"G1630 吧"，这是选择，不是确认，不放行，模型只能输出这趟车的详细信息并问"是否确认"；用户下一轮回"确认"，才真正推进。

另外还加了一个轮数上限：同一次发言里，每一步的查询最多 2 轮，换了步骤重新计数。因为模型被摘掉推进工具之后，会换着不同的查询工具一直调。需求收集、行程、预算这些产出内容的步骤不设上限，否则会打断正文。

〔选讲｜统计过才保留〕开发期日志里，闸门一共触发了【闸门触发次数】次。

会话状态和长期偏好是怎么持久化的？Checkpointer 和 Store 有什么区别？★★★

三样东西要分清楚。State 是一轮执行时的内存状态。Checkpointer 按 thread_id 存整个 State 的快照，LangGraph 每轮结束自动写，服务重启后按会话 id 能读回来，我这里 thread_id 就是会话表的 id。Store 按命名空间加 key 存用户级的数据，和具体哪个会话无关，由业务代码自己显式读写。

用户画像和出行历史在 Store 里分成两个 key，命名空间的第二段是 user_id。拆开是为了局部更新时不用把整条记录读出来再写回去。

两个组件都是单例，各自持有一个 PostgreSQL 异步连接池，最小 2、最大 20，初始化用双重检查锁，防止并发请求创建出两个实例。启动和关闭放在 FastAPI 的 lifespan 里，用 async with 嵌套，关闭顺序和启动顺序相反。

追问：Windows 上遇到过什么问题？ psycopg 的异步驱动不支持 Windows 默认的 ProactorEventLoop。启动脚本在 import 任何东西之前，先把事件循环切成 SelectorEventLoop，相关模块的 import 放进 lifespan 函数里。

追问：对话越来越长怎么办？ 中间件里有个窗口裁剪：消息超过 40 条时，按"用户轮"整轮丢掉最旧的，切的位置只落在用户消息上，不会把一次工具调用和它的结果切开，当前这一轮永远不裁。裁的只是发给模型的这一次请求，checkpoint 里的完整历史不动。

长期记忆是怎么写进去、又怎么用上的？★★

写入靠 5 把记忆工具：旅行风格、饮食禁忌、口味偏好、住宿偏好、出行历史。用户在对话里随口说一句"我对海鲜过敏"，模型就调对应的工具写进 Store。同类偏好用集合合并去重，住宿预算新旧值取平均。工具按步骤挂：餐饮步挂饮食禁忌和口味，住宿步挂住宿偏好。没有 user_id 时，工具只返回一条提示，不抛异常，因为记忆是锦上添花，记不成不应该卡住规划。

读取在中间件里，每一轮都读：画像和历史两次查询用 asyncio.gather 并行，格式化成一段"用户历史偏好"拼进提示词。每轮都读，是因为用户可能上一轮刚说了新的偏好。加载失败只记日志，按"没有记忆"继续往下走。

效果是第二次来规划时，模型知道用户去过哪里、对什么过敏，推荐会避开去过的地方，餐饮不会推海鲜。

三、事实归代码、表达归模型

"事实归代码、表达归模型"具体指什么？★

判断标准是：这件事错了有没有实际代价。有代价的、能用规则算出来或者能查出来的，交给代码；需要理解意图、组织语言的，交给模型。

归代码的有三类。第一类是算出来的：交通段数、每段的乘车日期、每个城市住几晚、预算、预算等级。第二类是查出来再渲染的：车次表、航班表、天气、行程正文和预算表都由代码拼出来，模型自己写的同类内容会被删掉。第三类是流程状态：当前在哪一步、确认到第几段第几城、本轮有没有落库，全部从状态机快照里读，不信模型自己说的"已经生成好了"。

归模型的是：理解用户想要什么、写目的地推荐的介绍、安排逐日行程里每个时段具体去哪、怎么玩，还有闲聊。

这条线不是一开始就划好的，是一个个坑踩出来的：模型编车次、按出发日查所有段、漏返程、心算预算、正文缺天缺时段，每遇到一次，就把那部分收回到代码里。

段数、段日期、住宿晚数是怎么算的？为什么不让模型算？★★★

交通段：把出发地、各个目的地、再加上出发地按顺序排成一条路线，相邻两个城市组成一段，首尾相同的段跳过。北京出发去天津、上海，就是北京→天津、天津→上海、上海→北京三段，最后一段是返程；北京到北京是本地游，0 段。

住宿晚数：第一站固定 1 晚，剩下的晚数在后面几站平均分，除不尽的余数分给靠前的站。这是一个简单固定的规则，不是最优的分配方法，我更在意的是交通和住宿用同一套规则。

段日期：去程是出发日；城际转场是出发日加上前面各站的晚数，也就是下一个城市的第一天；返程是行程最后一天。住宿窗口用同一套晚数推算，每一站的离店日正好是下一段的乘车日。

不让模型算，是因为实测它会算错：多城的会话里三段城际全按出发日去查，相当于同一天既在重庆又在北京又在天津；还会漏掉返程段。之前住宿和交通各算各的时候，还出现过"天津的酒店写着还在住，当天早上 6 点已经坐车离开了"。

还有一个相关的点：用户在表单里填了天数，模型传参时偶尔会读错。天数是后面所有计算的源头，它一错，住宿、餐饮、预算、正文全跟着错，所以需求收集工具会先从本轮表单里读"旅行天数"，和模型传的不一样，就以表单为准。

被问"第一站为什么只住 1 晚"：这是课程给的固定规则，主要照顾"出发地也在目的地里时，先在本地住一晚再走"。如实说这是简化的规则，可以补一句你会怎么改，比如按每个城市的景点数分配。

多段交通是怎么一段一段确认的？★★

这是手动模式、不走卡片时的做法。State 里有一个整数游标，记着"确认到第几段了"。游标由代码维护，模型碰不到，读的时候还会限制在合法范围内，防止残留的旧值越界。

模型提交选择时，交的是结构化的对象：出发城市、到达城市、车次、时刻、席别、票价，而不是一句话。代码用"出发城市和到达城市字段完全相等"去找当前待确认的那一段。早期是交一句话、用子串匹配，出过一个错：当前该确认北京→天津，模型交的是返程"天津→北京"，子串匹配发现两个城市名都出现了，就当成了去程。

这个工具有三种结果。交的不是当前段，或者字段缺了，就拒绝，并在错误消息里写清楚当前是第几段、段名是什么、对象应该怎么写，模型一般一轮就能改对。交对了但后面还有段，就记下这一段、游标加 1，current_step 不动，同时告诉模型下一段是哪段。最后一段确认完，一次性写入所有段的记录，推进到住宿步。

记录的时候存两份：一份是展示用的文本，给行程正文引用；一份是纯数字的票价，给预算直接用。

预算是怎么算的？票价从哪来？★★

预算工具全部用代码算。交通是人均票价乘人数；住宿是每晚房价乘晚数乘房间数，N 天住 N-1 晚，两个人一间；餐饮按每人每天 150 元；门票有真实票价就按真实的算，没有就按每人每天 200 元估；再加一项杂费。人均多少、有没有超预算的结论也由代码给。

票价分三级取：模型调用时显式传了值，就用传的；没传就读数字账本，也就是交通卡片和住宿卡片提交时存下来的每段票价、每城房价；还没有，才用估算值。

数字账本是后来单独加的。早期预算是从展示文本"二等座 662 元"里用正则把数字抠出来，那串文本是我们自己拼的，哪天文案一改，正则就抠不到了，预算会悄悄退回估算值，也不报错。拆出来单独存数字之后，取价就是读一个字段。账本里只记有真实价格的条目，查不到价格的不写，这样"没有价格"和"0 元"才能区分开。

天数和预算上限两个参数可以覆盖。用户说"多玩一天""预算加到 4000"，模型调用时传新值，算完把新值写回需求记录。不写回的话，其他地方还按旧天数排，前后就对不上了。

〔选讲｜遇到过才保留〕加数字账本之前，我发现不管选多贵的车和酒店，人均预算永远是同一个数。查下来是模型调预算工具时没有传价格，每次都用的是估算值。

行程正文为什么不让模型直接写？结构化提交怎么校验？★★

早期是模型自由写正文，"天数全覆盖、每天四个时段、最后一天有返程"这些规则写在提示词里，再用正则事后补救。实测照样会漏，比如第 3 天缺中午和下午，或者把 13:01 写在上午里。

现在模型不写正文，只调一个提交工具，交一个逐日列表：每一天有天序号、城市，上午、中午、下午、晚上四个时段各是一个列表，再加当天的小贴士。用 Pydantic v2 校验，分两层。字段层面，四个时段都要求至少一条，空的时段当场就被拒。跨字段的规则放在 model_validator 里：天序号不能重复，必须正好覆盖第 1 到第 N 天，最后一天晚上要有返程，每条有最低字数，每天至少一条小贴士。旅行天数不是模型里的字段，是校验时通过 validation context 传进去的，同一个模型可以按"这次几天"来校验。

报错全部用中文写清楚是第几天、哪个时段、差多少字，因为这些报错是回给模型看的。

校验通过以后，正文和预算表由代码渲染：已确认的交通和住宿、逐日安排、预算明细，人均和结论都是代码算的；缺预算数据就不出预算表，不编数字。模型这一轮自己写的正文作废。如果模型在这一步一直不提交结构，中间件会用 tool_choice 强制它调用提交工具。

代码渲染没有逐字输出的过程，一开始是整篇一次推完，用户看到的是一大段突然出现。后来改成每 48 个字一段、每段间隔 25 毫秒推送，看起来还是流式的。

校验不过，为什么不让模型重写，而是由代码来补？★★★

因为重写会陷入"拒绝、重写、再被拒绝"的循环。实测连续被拒 4 次，每次重写一份 5 天的结构要 30 秒左右，极端情况会撞上 LangGraph 默认 25 步的递归上限，整轮报错，清单也生成不出来。

现在的做法是：第一次校验不过，由代码按天数做一次规范化，再校验一次。规范化只做两件事：删掉不合法的，补上缺的。超出天数的天、重复的天删掉；缺的天和空的时段补上；太短的条目补一段通用说明；最后一天晚上没有返程就补一句，优先用用户已经确认的返程班次。模型已经给出的有效内容一个字不改。补的文案按天轮换，并写上当天所在的城市，免得 6 天的行程里好几天出现同一句话。

原则是：必须满足的规则由代码保证，内容写得好不好由模型负责。代价是补进去的内容信息量低，所以补了几处、补了什么都会记日志。规范化之后还不通过，才把错误回给模型，按设计这一步不应该发生。

另外我也把递归上限调到了 60，给多轮工具调用留余量，但没有调太大：真陷入死循环时，60 步能及时报错，调到几百只会白白跑下去、浪费调用费用。

走卡片路线时，为什么要把模型的查询工具摘掉？★★

多段高铁、航班、自驾和多城住宿走卡片路线时，代码已经并行查完了所有段，把候选做成卡片推给前端。如果模型手里还有车票查询工具，它会按提示词里原来的习惯，自己再一段一段查一遍，然后把查到的班次写进正文。结果同一个屏幕上出现两套班次，卡片里一套，正文里一套，还可能对不上。

所以中间件判断这一步走卡片路线时，就从工具表里摘掉对应的查询工具和推进工具。推进由卡片的提交接口完成，模型这一轮只说一句"请在下方卡片里选择"。高铁、航班、自驾按这个优先级接管，三个都勾了时高铁优先。本地游没有城际段，也把交通查询工具全摘掉，直接跳到住宿步。

有一个细节：确认轮原本会强制调用推进工具，如果这个工具刚好被摘掉了，必须同时取消强制，否则模型被要求调用一个工具表里没有的工具，请求会直接报错。

不走卡片的候选轮，执行器会把正文里带车次号、时刻、价格的行全部删掉，只留下引导语，班次表由代码根据本轮工具的返回直接渲染。

四、MCP 统一接入与容错

9 个数据源是怎么接进来的？★★ 为什么用 MCP？★★★

MCP 是统一的工具协议。用它的好处是，加一个数据源只要在客户端配置里加一项，上层 Agent 的代码不用改；再用 langchain-mcp-adapters 把 MCP 工具转成 LangChain 工具，Agent 直接就能用。

9 个数据源分两类。自建的两个用 fastmcp 写，走 stdio：天气接的是高德天气，搜索接的是 Tavily。外接的有 12306 余票（npm 包，也是 stdio）、VariFlight 航班、aigohotel 酒店、高德地图、百炼联网搜索等，走 HTTP。stdio 是在本地起一个子进程，快，也不用鉴权，适合自建的服务；HTTP 适合第三方托管的服务。

自建服务有一条规矩：工具永远返回字符串，出错了也把错误包成 JSON 返回，不抛异常。因为 stdio 模式下抛异常，堆栈会进 stderr，客户端在 stdout 上收不到响应，只能一直等到超时。

工具拿到之后按业务分类，比如车票类、航班类、酒店类，按工具名里的关键词筛选，各个步骤按需挂载。

追问：Windows 上有什么坑？ psycopg 要求用 SelectorEventLoop，而 stdio 需要起子进程，Windows 上只有 ProactorEventLoop 支持子进程。我的做法是主循环用 Selector，MCP 的会话全部放在一个专门的 Proactor 后台线程循环里，工具调用用 run_coroutine_threadsafe 跨线程执行。Linux 和 macOS 上没有这个矛盾，直接 await 就行。

"按服务隔离加载"是什么意思？调用失败怎么处理？★★

先说加载。最早是一个客户端装所有服务的连接，放在同一个 TaskGroup 里，任何一个远程服务抖一下，所有工具都加载失败。后来改成每个服务一个独立的客户端，用 asyncio.gather 并行加载；单个服务失败，先等 2 秒重试一次，还失败就返回空列表跳过它，其他服务照常能用；只有全部失败才抛错。启动日志会打印"N 个工具，k/9 服务在线"。

再说调用。每个 MCP 工具的调用外面包了一层：失败后等 1.5 秒重试一次；还失败，就清空客户端和工具缓存，下次取工具时按配置重新建立全部连接，不用重启服务；同时返回一段降级文本，意思是"外部服务暂时不可用，请告诉用户暂时没查到，建议稍后重试或跳过，不要暴露技术细节"。

不抛异常，是因为工具抛异常会让整轮对话出错。返回降级文本，模型会自然地转告用户，流程不会中断。住宿步看到这个降级标记，还会由代码补一段常见连锁品牌的参考，只给品牌和档位，不编具体门店和价格。

〔选讲｜做过才保留〕我做过故障注入：故意把一个服务的 key 改错，启动日志显示【在线服务数】/9 在线，规划流程照样能走完，用到这个服务的那一步给出降级提示。

车票工具的入参守卫做了哪些事？★★

12306 查票工具有三个必填参数：日期、出发站、到达站。模型实际调用时经常出错：把日期写成 trainDate，漏传出发站，传一个已经过去的日期。直接发给服务端会被拒绝，用户看到的就是"查询出错"。

守卫是一个包装类，工具名、描述、参数结构原样透传，模型看到的工具一模一样，只在调用时检查入参：

  1. 别名归一：trainDate、departureDate 统一成 date，from、fromCity 统一成 fromStation，以此类推。别名的键要删掉，因为服务端不接受多余的字段。

  2. 缺参回填：用本轮上下文补。多段行程时更严格，日期和出发、到达站一律用"当前正在确认的那一段"，模型传了什么都覆盖掉，因为它经常三段都填出发日。

  3. 还是缺参数，就返回一句看得懂的提示，告诉模型缺哪个参数、应该怎么写，而不是把服务端的报错原样交给它。

  4. 日期早于今天，直接拦下，让模型先和用户确认日期，不替用户换一个日期。

哪些工具需要包装，是按参数结构判断的：必填参数里同时有这三个才包，不写死工具名，MCP 服务升级改了名字也不受影响。

本轮上下文存在一个 ContextVar 里，中间件每轮调模型之前写一次。用 ContextVar 而不用全局变量，是因为它按异步任务隔离，两个用户同时规划不同的城市，各自读各自的，不会串。

为什么要裁剪 12306 的返回结果/怎么做的裁剪？★★★

因为返回太长，模型会编造。我实测热门线路单次返回 287 趟车、4.5 万字，模型被淹没之后，编出了 G1001、G1003 这种真实数据里根本不存在的车次，连票价都是编的。提示词里写"不要编造"没有用，根源在数据量太大。

裁剪在守卫里做：先解析出每趟车的车次、区间、时刻、历时和各席别票价，按发车时间排序，只留前 12 趟，每趟压成一行，票价按二等座、硬座、一等座这样的常用顺序挑一个展示。解析失败就截取原文前 2000 字作为降级，不报错。模型只看到十几行，就不会被淹没了。

在我的环境里，【原始字数】字、【原始趟数】趟，压到了【压缩后字数】字、【压缩后趟数】趟。

还有一个配套的设计：能力包那边并行查询，用的是原始工具而不是守卫版，因为它需要完整的结构化字段自己解析；万一拿到的是守卫压缩过的单行格式，也有解析函数能读回来。

五、段级并行查询

多段查询是怎么并行的？单段失败怎么办？★★★

多段高铁、航班、自驾和多城住宿这四类能力，查询流程是一样的：校验入参，找到查询工具，每一段起一个查询协程，用 asyncio.gather 一起等，组装成卡片数据，再写进缓存。所有段同时发出去，总耗时大约等于最慢的那一段。在我的环境里，3 段高铁串行查要【串行耗时】秒，并行是【并行耗时】秒。

单段失败不影响其他段：每一段的查询函数自己 try/except，任何异常都返回一个候选为空的段，不往外抛，所以 gather 不会整体失败。前端拿到空段就显示成灰色。所有段都是空的时候，不推空卡片，返回"空"的状态，由调用方在正文里如实告诉用户。

灰色的段在提交时不算漏选，会写成"实时班次暂不可用，可现场购票或改期"，预算对这一段用估算值。不然这一段永远没法选，用户就一直卡在交通步。

航班还多一层：时刻表和票价是两个接口，也是并发查的，用 return_exceptions 收结果，票价接口失败只是没有价格，航班照常展示。

数字测法：串行的基准自己写一个 for 循环逐段 await，和并行版各跑几次取中位数。要能讲出"并行耗时约等于最慢的一段"。

候选的身份为什么用 option_id，不用车次号？★

因为在 12306 的真实数据里，同一段、同一个车次号可能有好几趟。比如 G1308 08:36 发车，一趟终点是石家庄，一趟终点是正定机场。用车次号当身份，前端这两趟会同时被勾上，后端回写时取到第一趟，到达站和票价就全错了。

所以身份是"车次-发车时刻-到达站"拼成的 option_id，选中、校验、回写都认它。提交里缺 option_id 就直接拦下，让用户重新选，不拿车次号去凑合匹配，免得悄悄写错。航班也一样，用"航班号-起飞时刻-到达机场"。住宿的候选 id 会重新编号成"段号-序号"，比如 h2-1，防止两站各自从 1 开始编号撞在一起。

候选缓存为什么按会话分桶？签名缓存又是干什么的？★★

有两种缓存，作用不一样。

第一种存的是"最近一次发给前端的候选"，提交校验只认它：用户选的东西必须在这份候选里。它按会话 id 分开存。最早是一个进程级的全局变量，两个用户同时规划，后发的会覆盖先发的，提交时就拿别人的候选来校验了。

第二种是查询缓存，key 是"会话 id 加段签名"，段签名就是"北京→天津@日期|天津→上海@日期"这样拼起来的字符串。同一个会话、同一批段再次访问时直接复用，不重复调外部服务。卡片每一轮都会重新推，靠它保证重推的时候不重新查。容量是 32，满了就删最早写入的。

要不要写进查询缓存，由一个判断函数决定，每一类不一样。高铁要求每一段都有候选才写：某一段偶尔查到空，要是被缓存了，用户重试时会一直拿到这份空结果，那一段永远查不出来，我把这个叫"空段死锁"。航班、自驾、住宿只要有一段有结果就写，因为航班的空段多半是城市没有机场码，重新查也还是空，不值得每次都把所有段重查一遍。

卡片提交时做了哪些校验？幂等是怎么做的？★★

基础的合法性校验按顺序有几关：没发过候选就提交，拦下；提交为空，拦下；缺 option_id，拦下；段 id 不存在，拦下；选的不在这一段的候选里，拦下；有候选的段没选，拦下。全程不比较段与段之间的时间先后，比如上一段到站晚于下一段发车，这个判断留给用户看着卡片自己决定。

校验通过之后、写库之前，还有一道步骤检查：只有状态机还停在交通步，才允许写入并推进。已经过了交通步，说明是重复提交，比如前端连点了两下，直接返回成功，并带回已经选好的内容，不重复写；如果在其他步骤，返回步骤不匹配。

写库是一次 aupdate_state 写全：每段的选择、票价账本、游标拉到最后、交通方式、推进到住宿步。

四类能力有什么不同？代码是怎么复用的？★

四类的结构一样，都是三个文件：数据结构定义、查询和校验、和状态机的衔接。公共的部分抽成了一个基础包：两种缓存写成泛型类，一份代码装四种卡片数据；还有段签名、读取会话状态这几个辅助函数。新加一类能力，主要只写查询和校验。

不同的地方：

  • 优先级：高铁、航班、自驾都勾选时，由高铁接管卡片，其次是航班，最后是自驾。

  • 航班查询前要先把城市换成机场三字码，没收录的城市不查。票价接口要的是城市三字码，和机场码是两张表，北京一个是 PEK、一个是 BJS，用混了会整段查不到。

  • 自驾每一段只给高德默认策略的一条路线，用户只能确认，提交时只带段 id。

  • 住宿每一站单独判断模式：查到门店就是门店模式；查不到就降级成品牌模式，按档位给几个常见的连锁品牌，不编门店和价格。

自动确认模式下由代码替用户选：高铁先排除无票的，再比耗时、比价格；航班比价格，不知道价格的排在后面；自驾所有段都查到就推进；住宿取每一站的第一个候选。

卡片提交之后，流程怎么接着往下走？★

卡片提交不是一条对话消息，单独走一个 REST 接口，但返回的是 SSE 流。只把选择存下来是不够的：推卡片的那一次 SSE 早就结束了，没有东西驱动下一步，用户会停在原地。

接口里分四步。第一，调能力包做校验并写库推进，没通过就推一个错误帧和结束帧，卡片保持展开让用户重新选。第二，把"已提交、每段选了什么"写回卡片所在的那条消息，这样刷新页面后卡片还是锁定状态。这里是 JSON 列，必须整列重新赋值，直接改字典里的某个键，SQLAlchemy 识别不到变化，不会写进库。第三，立刻回显一条"已确认您选择的车次"，内容由服务端按真实的候选拼出来。第四，用一句合成的用户发言，调用同一个编排入口继续往下跑。

继续跑的时候带三个参数：强制按规划处理，不经过不稳定的意图路由；这句合成发言不存进历史，因为用户没说过这句话；把状态机实际推进到的步骤传进去，反馈文案按它来取。

住宿的合成发言特意写的是"请直接为我生成完整行程报告"。早期写的是"请继续安排餐饮"，模型就顺着去讲餐饮的选项了，行程正文一个字都没出来。

六、流式编排与三通道分流

流式接口是怎么设计的？为什么选 SSE？★★★

大模型对话是单向的：用户发一次请求，之后只有服务端在推文本、推状态、推卡片。SSE 走的是标准 HTTP，Nginx 和 CDN 都支持；WebSocket 的双向能力用不上，连接管理和心跳的成本却要承担。所以选了 SSE。浏览器原生的 EventSource 只支持 GET，也不能带 Authorization 头，所以前端用 fetch 自己读流。

每一帧是 data: {json} 加两个换行，值为空的字段去掉，中文原样输出。帧的结构全后端只有一种：role、content、code。role 一共 8 种，分三类：文本类是 assistant 和 assistant_reset，后者是撤掉本回合已经推出去的文本、准备重新推；业务状态类是 skills（正在用什么技能）、skill_ui（可交互的卡片，带完整数据）、itinerary_plans（清单生成中、成功、失败）；控制类是 done、error、end。code 只在 done 和 end 上带。前端按 role 分别处理，一套解析逻辑覆盖所有接口。

响应头有三个：no-cache、keep-alive，还有 X-Accel-Buffering: no，用来关掉 Nginx 的缓冲。Nginx 默认会攒到 8KB 左右才转发，本地没有 Nginx 时一切正常，一上线就变成隔几秒蹦出一大段。

还有一条规定：done 永远是最后一帧，done 之后什么都不推。前端一般把收到的帧挂到消息列表的最后一条上，done 之后再推的东西会挂到用户的下一条消息旁边。

生产者-消费者的事件管道是怎么实现的？★★★

编排在后台任务里跑，SSE 端点在前台等，中间需要一个队列。我把它包成了一个 EventStream 类：

  • push 用 put_nowait 同步投递。队列是无界的，不会满，用同步接口没有代价；好处是流式回调里的同步函数也能直接 push。

  • close 往队列里放一个结束标记。这个标记是一个 object() 对象，比较时用 is，不会和任何业务数据相同。用 None 或者 "END" 做结束标记，迟早会和真实数据撞上。

  • 实现了 aiter 和 anext，取到结束标记就抛 StopAsyncIteration，消费方直接写 async for。

编排入口用 create_task 把生产者放到后台，然后立刻返回这个流，端点马上就能开始读。如果改成 await 等编排跑完再返回，就没有流式效果了。

生产者用 try/except/finally：成功时推 done，失败时推 error、再推一个带 500 的 done，close 放在 finally 里。忘了 close，消费者会一直卡在取队列那一步，前端一直转圈，而且这个问题只在出异常时才出现，平时测不出来。我写了一个冒烟测试，用 patch 让路由抛异常，验证流能正常结束。还要注意，create_task 之后不 await，生产者里的异常不会传给调用方，所以生产者必须自己处理异常。

〔选讲｜量过才保留〕自动确认表单会在路由之前先推一帧"正在为您规划行程"，首帧在【表单首帧延迟】以内；普通消息要等路由跑完，首帧是【普通首帧延迟】。

统一响应格式怎么做到不影响 SSE？★

普通的 JSON 接口统一返回 code、msg、data 三个字段，前端拦截器只用配一次。统一格式是一个 HTTP 中间件，有三种情况直接放过：文档和静态资源的路径；content-type 不是 application/json；响应体已经是统一格式了。SSE 的 content-type 是 text/event-stream，按类型判断自然就放过了，不用在中间件里维护一份路径列表。

读响应体有个坑：中间件拿到的是流式响应对象，没有现成的 body，要自己把 body_iterator 读出来，而且只能读一次，读完原对象就空了，所以要用读出来的内容重新构造响应，并保留原来的响应头。CORS 的头在原响应上，丢了浏览器就会报跨域错误。这个中间件最后注册，在最外层，这样异常处理中间件生成的统一格式不会被再包一层。

三条通道是怎么分流的？意图路由是怎么做的？★★

三条通道是：直查、快速、状态机。

直查通道处理带城市的单项查询，比如"查一下明天福州到深圳的高铁"或者"明天杭州天气怎么样"，由确定性的规则判断，命中后代码直接查、直接渲染表格。快速通道处理勾了"全程交给 AI 自动确认"的表单。剩下的规划请求走状态机；闲聊也从执行器进来，但不走 Agent，直接调用模型流式输出。

意图路由用的是结构化输出：定义一个 Pydantic 模型，三个字段，分别是是不是行程规划、判断过程、本轮可能用到的技能。用 with_structured_output 一行就拿到类型明确的结果，温度设为 0。路由时带上最近 4 条历史，也就是两轮对话。单看一句"确认"或者"杭州"，很像闲聊，会被判错，需求收集就断了；带上上一轮助手问的"是否确认选择杭州"，就能判断出这是规划的延续。

直查规则的结果优先于路由结果。路由是概率性的，同一句"查明天福州到深圳的高铁"，有时判成规划，有时判成闲聊；直查规则都是确定的判断，命中就说明用户明确要查票，不会判错。卡片提交之后继续往下跑时也不走路由，代码直接指定按规划处理。

简历写的是"确定性门禁先拦单点查票（0 次 LLM）"，指的是直查通道本身不调模型。按课程代码，路由是在直查规则之前调用的，直查命中时这次路由的结果被丢掉。被追问就如实说，并说可以把直查规则挪到路由前面，省掉这次调用。如果你已经挪了，就直接说"直查命中时全程不调模型"。

直查通道的规则是怎么判断的？★

一共四关，都是确定性的判断。第一，消息里有查询对象（高铁、车票、航班、天气这类词），并且有查询动词或者日期词。第二，不包含"规划、行程、攻略、旅游"这类词，出现了就说明用户要的是规划，交回原来的通道。比如"我想坐高铁去杭州玩，明天的"，有对象词也有日期词，但有一个"玩"，就不走直查。第三，能解析出出发和到达的城市。第四，对应的工具已经加载好了。任何一关不过，就返回空，原来的分流照常进行。

城市解析是全国城市列表优先、正则兜底。只用正则按"到、去"来切，"从深圳出发去福州"会切出"出发"这个假城市；城市列表里没有"出发"，只会匹配到深圳和福州，再按它们在原句里出现的先后决定出发地和目的地。日期是明确写出的日期优先，相对日期其次，都没有就默认今天；相对日期表里"大后天"要排在"后天"前面，不然会先匹配到"后天"。

命中之后，代码查 12306，按段渲染表格；航班查不到直飞，就带一句说明，改查同一天的高铁，不把用户推去"航空公司官网"。每个返回的地方都调用同一个"推帧并返回"的函数，早期漏推过一次，用户只看到"正在查询"，表格一直没出来。

这些意图词表原来散在七个地方，同一个词在一处能识别、另一处不能，比如"高铁"在直查规则里没有，在交通清单的处理里有。后来全部收到一个意图模块里，一次扫描得出一份意图结果，各处读字段。

快速通道为什么能把端到端时间降下来？★★★

状态机是为"一步一问"设计的，每一步都要模型思考一次，一次 8 到 17 秒。用户在表单里已经把需求填全了，还勾了"全程交给 AI 自动确认"，再一步一步问就是纯粹的浪费。实测这种表单走状态机，全程要【状态机耗时】秒。

快速通道的流程是这样的：

  1. 两层判断。第一层是 0 毫秒的词表筛选，"全程交给 AI 自动确认"是前端写死的文案，普通消息在这一层就被挡掉了。命中了才做第二层：一次结构化提取，把表单抽成出发地、日期、天数、人数、预算、偏好这些字段，没有出发地或者没勾自动确认，就回到状态机。

  2. 没填目的地的话，调一次模型直接选一个城市，结果用结构化输出拿回来。

  3. 并行收集：每一段交通、每个城市的酒店和天气，全部用 gather 同时查，每个查询外面包一层，失败只返回空，不影响别的。

  4. 按规则替用户选，不用模型：高铁在有票的车次里，取"历时分钟数加票价除以 10"最小的那趟；在评分 4.5 以上的里面选最便宜的。规则能说清楚为什么选这一趟，几毫秒就算完，没有成本，同样的输入永远得到同样的结果。

  5. 调一次模型生成逐日行程，用强制 tool_choice 让它按状态机里同一个行程结构提交，校验和规范化也用的是同一套。

  6. 预算由代码算，正文由代码渲染。

如果拿不到合格的行程结构，就放弃快速通道，回到状态机，不会只给用户一个预算。按单城 3 天来算，端到端时间从【状态机耗时】秒降到了【快速通道耗时】秒，一轮的模型调用从【状态机LLM次数】次降到了【快速通道LLM次数】次。

模型调用怎么数：路由 1 次、结构化提取 1 次、行程生成 1 次、清单提炼 1 次；没填目的地再加 1 次选城市，正文超过 2000 字再加 1 次压缩。用 LangSmith 数调用记录，或者给模型调用包一层计数。耗时一定写明"单城 3 天"，多城会更长。

快速通道跑完后，用户还想改怎么办？★★

快速通道绕开了状态机，LangGraph 的线程里什么都没有。用户接着说"预算再加 2000"，就会进入状态机，而状态机不记得前面的任何内容，只能从头问"从哪里出发"。

所以清单写库之后，把这次的结果一次性写进 LangGraph 线程：需求、已经选好的交通住宿餐饮、行程、当前步骤。步骤停在预算汇总，因为这一步挂的回退工具最全，用户想改预算、天数、交通都可以直接改。写入必须一次写全，同一个线程分多次写会报 Ambiguous update。写进去的助手消息截到 2000 字，防止 checkpoint 越存越大。

行程清单是怎么生成和落库的？★★

正文推完之后，前端要显示一个"查看清单"的按钮，点开是卡片式的清单：每天每个时段的景点、介绍、图片、坐标，还有驾车路线。

提炼清单用的是 DeepSeek，用 bind_tools 而不是 with_structured_output。原因是 DeepSeek 的思考模式不支持强制 tool_choice，会直接返回 400，而 with_structured_output 内部依赖强制调用。bind_tools 只是告诉模型"有这个工具可以用"，我自己取出第一个工具调用的参数，再用 Pydantic 校验。

提炼可能失败：欠费、偶尔不返回工具调用、参数不合规。这时手里有状态机里已经校验过的逐日结构，代码直接用它拼一份清单。这个兜底版本的介绍没那么丰富，但能保证清单一定生成出来。之后用高德的地点搜索补坐标和封面图，用驾车路线接口补每天的路线；没有实景图但有坐标的，就生成一张静态地图当封面。

写库按会话覆盖：同一个会话已经有清单就直接更新，plan_id 不变，前端手里的 id 一直有效。每次都新插一条的话，用户反复改天数，库里会存一堆互相矛盾的清单。

前端会依次收到清单帧的三个状态：生成中，然后是成功或失败，最后才是 done。生成清单要同时满足三个条件：意图是规划、步骤到了行程或预算、有可以用的原始内容；手动模式要求更严，要走到预算步才生成。

〔选讲｜统计过才保留〕【清单统计次数】次规划全部生成了清单，其中【兜底次数】次用的是结构兜底。

状态机回合里的首轮缓冲、泄漏清洗、重复折叠是怎么回事？★

一个用户回合里，Agent 往往会调用好几轮模型：第一轮说"我来查一下"然后调工具，工具执行完再一轮写正文。直接用 astream_events 往前端推，会有三个问题。

第一，第一轮多半是调工具前的过渡话，推出去之后又会被正文替换，前端会闪一下。所以第一轮只缓存不推，从第二轮开始，收到就推。

第二，模型会把系统协议和指令写进正文，比如工具协议的标记、"请记住只有在收集到足够信息后才能调用工具"这类指令、整段的工具参数，还有"行程清单已生成，可在下方查看"这种它根本不知道真假的话。协议标记在进缓存之前就丢掉；其他的在每一轮结束时清洗：整块删掉指令和参数段，逐句删掉泄漏的句子和没根据的承诺，把"请确认以上行程是否符合需求"改写成不需要用户回复的邀请语。

第三，同一个回合里会换个说法重复，或者把整篇正文再贴一遍。每轮结束时对普通段落做相似度比较，和之前出现过的段落有一长串连续相同的内容就删掉；"请稍等"这类预告语每个回合只留第一次；回合结束时对长段落做整篇去重，保留靠后的完整版本。

回合结束时再决定怎么交给前端：一直没推过，就把整段推出去；推出去的内容里有泄漏或重复，就推一个 assistant_reset 清空，再推清洗后的版本；第一轮是空的或者是过渡话，已经推出去的就是完整答案，一个字都不动。早期这里的做法是"挑最长的一轮清空重推"，结果把跨了两轮的预算表抹掉了。

还有一种情况：交通、目的地、行程这些步骤，回合结束时会由代码接管正文。这些步骤整个回合只缓存、一个字都不推，文本交给执行器，处理完统一推一次，前端不会看到"先出一版、再换一版"。原则是谁决定最终内容，就由谁来推；推给前端的和存进库的是同一份。

七、Advanced RAG 与目的地推荐子图（项目这里是这样的，rag部分要是想更深入可以看 ）

RAG 做了哪几层加强？各自解决什么问题？★★★

普通的 RAG 有四个问题，每一层对应解决一个：

  • 切块太小缺少上下文，太大又检索不准：用父子分块，小块用来检索，大块作为上下文。

  • 向量检索对专有名词、编号不敏感，关键词检索识别不了同义词：BM25 和向量两路召回，用 RRF 合并。

  • 用户说的是口语，文档写的是书面语，用词对不上：用 Multi-Query，让模型把一个问题改写成 3 种不同说法，分别检索再合并。

  • 召回的结果里有不相关的内容，模型对长上下文中间部分的信息不太重视：用 LLM 重排，再把最相关的放在开头和结尾。

再加一层 Redis 缓存：问题加条数算哈希作为 key，缓存 1 小时，同样的问题第二次直接返回；Redis 不可用时自动退化成不用缓存。

数量是一层层减少的：混合检索取 9 个子块，重排后留 6 个，换回父块，最后取 3 个交出去。底层用的是 Chroma 加通义的 text-embedding-v2。查询改写和重排用的是 qwen-turbo，因为这两步每次检索都要跑，用大模型又慢又贵，而改写问题和打分这种任务小模型够用了。

RAG 包装成工具给 Agent 用，和联网搜索分工：攻略、景点介绍这类不常变的知识走知识库，开放时间、今年开没开这类有时效性的信息走联网搜索。

〔选讲｜量过才保留〕冷查询走完整流程要【冷查询耗时】秒，命中缓存在【缓存命中耗时】毫秒以内。

简历没写 RAG 的召回指标，面试官大概率会问"你怎么知道 RAG 效果好"。没做附录 A1 就如实说"没单独做召回评测，参数是初始值"，并说清楚要做的话打算怎么做。

父子分块是怎么做的？参数怎么定的？★★

检索和生成对块大小的要求是反的。检索希望块小，因为向量是定长的，一个块里包含三件事，向量就是这三件事的平均，跟任何一个具体问题都不够像。生成希望块大，只给模型两句话，指代、前提、条件都丢了，答案容易残缺或者编造。

所以把这两件事拆开：小块负责被检索到，大块负责交给模型。

怎么切？我不是按固定字数切的，是按文档结构切。

父块对应一个完整的语义单元。在 Markdown 里就是某级标题下的整块内容，在我这份文档里就是一个景点、一条路线、一个条目。切出来长度不齐，有的三百字有的一千二，这是正常的，因为文档本身就不齐。

长度只作为两条红线。超过一千二百字，就在内部的次级边界再切开，优先找子标题，没有就找段落空行，切开的几块共享同一个标题路径。不足一百五十字，就和相邻的同级块合并，合到够长为止。

子块是在父块内部按句子累加的。逐句加到两百字左右就断，断点一定落在句末，不会出现半句话。向量化之前，在子块文本前面拼上标题路径，比如"交通、机场大巴、票价"，再加正文，然后送去 embedding。

只有子块进向量库。命中之后按 metadata 里记的 parent_id 换回父块，去重，按 token 预算装填，交给模型。

混合检索和 RRF 是怎么做的？★★★

同一个问题同时走两路。BM25 那一路按关键词打分；向量那一路用 Chroma 的相似度检索，它返回的是 L2 距离，越小越相似，我换算成"1 除以（1 加距离）"。两路各取 2 倍数量的候选，宁可多取一点，再合并。

合并用 RRF：一个文档的分数，是每一路的权重除以"60 加上它在这一路的排名"，再加起来，没进某一路排名的就不加分。BM25 的权重是 0.4，向量是 0.6，因为用户的问题大多是自然语言。不直接把两路的分数相加，是因为两边分数的范围完全不同，BM25 没有上限，向量相似度在 0 到 1 之间；RRF 只看排名，可以直接比较。去重用文档前 200 个字算哈希，两份攻略引用了同一段话也能识别出来。

用 Multi-Query 时，每个改写后的问题各跑一遍上面的流程，结果按顺序拼在一起、去重，取前 k 个。

追问：多个改写的结果直接拼起来，合理吗？ 不是最好的做法。现在是按改写的顺序拼，原问题的结果排在最前面。更好的做法是把所有改写的排名一起再做一次 RRF，这样被多个改写都召回的文档会排到更前面。

先查自己的 retriever.py：BM25Retriever.from_documents 有没有传分词函数。LangChain 默认按空格切词，中文一整句会被当成一个词，BM25 那一路基本没用。没传就补上 preprocess_func=lambda t: list(jieba.cut(t))，补了再说"BM25 用 jieba 分词"；没补就别提 jieba，把这条放进第 52 题的不足。

检索结果里出现别的城市的攻略怎么办？★★

知识库的内容有限，比如只有一份西安的攻略。查上海的时候，向量检索会返回它认为最相似的内容，也就是西安的，模型拿到之后可能写出"上海必去兵马俑"。

所以检索结果在交给模型之前先按城市过滤：只保留正文里出现了目标城市的文档。全部被过滤掉，就如实告诉模型"知识库里没有这个城市的资料，请基于常识给建议，不要编造门票价格和开放时间"。

目标城市怎么传给工具是个问题：工具是被子图里的 Agent 调用的，参数传不进 create_agent 的执行过程。我用的是 ContextVar：子图的节点一开始先设置城市，工具里再读出来。不能用普通的全局变量，两个请求一个查上海、一个查西安同时在跑，后设置的会把先设置的覆盖掉，而 ContextVar 是每个异步任务各有一份。车票守卫的本轮上下文用的也是这个方法。

目的地推荐子图是怎么搭的？为什么用 Send？★

用户问"杭州适不适合去"，需要两样东西：攻略来自知识库，天气来自实时接口，两者互不依赖。所以"查目的地信息"这个工具内部是一张手搭的 StateGraph，跑一遍，返回一份报告。

图的结构是：分类节点看用户的问题，决定派哪些子 Agent；分类节点后面是一条条件边，路由函数返回一个 Send 列表；攻略节点和天气节点并行执行；两个分支都连到汇总节点，然后结束。

用 Send 是因为分支的数量要运行时才知道。普通的边在建图时就固定了；条件边是运行时选一个节点走；Send 列表里有几个，就同时开几个分支，可能派 1 个，也可能派 2 个，以后加别的子 Agent 也一样。Send 发过去的是一个只包含子问题和目的地的小字典，不是整个状态，所以下游节点的入参就是这个字典。发之前按"派给谁加子问题"去重，因为模型偶尔会重复输出同一个任务，不去重就会白跑一遍。

几个小设计：表示"派给谁"的字段用 Literal 限定成两个节点名，防止分类器输出一个不存在的节点；攻略节点内部是一个 create_agent，挂了四把检索工具，做成延迟创建的单例，因为它不保存状态，可以重复使用；汇总节点只是把两段内容拼起来，两段本身都是完整的，拼起来就够用，不再调模型。

多个并行分支写同一个字段，怎么做到不冲突？★★

靠 reducer。LangGraph 的状态默认是覆盖更新，两个分支都写结果字段，后回来的会把先回来的覆盖掉。我把结果字段声明成 Annotated[list, add]，告诉框架这个字段用列表相加的方式合并：攻略分支交一条，天气分支交一条，最后得到两条。每个分支只负责返回自己的那一份，合并由框架完成，代码里不用加锁。

主状态里也用了 reducer：消息字段用的是 LangGraph 自带的追加合并；行程和预算这两个结果字段挂了一个自定义的合并函数，新值为空就保留旧值，避免同一步里一个工具写空、另一个写结果时报并发写入的错误，也不会把已经算好的结果冲掉。

分类器漏派了天气，或者天气查不到，怎么办？★

漏派由代码补上。目的地这一步要求必须展示天气，但分类器是模型，偶尔只派攻略，实测有一次查天津就漏了天气，前端的天气栏是空的。改提示词让模型别漏，结果永远是概率性的；而"派发列表里有没有天气"代码百分之百能判断，没有就加一个。

天气查不到就如实说。天气接口返回的格式不固定，可能是内容块列表、JSON 字符串或者字典，我先统一转成字典，再用 Pydantic 校验，缺的字段留空，不报错。早期只处理了字符串和字典，列表格式没处理，于是每次都判断成"没有天气"。查询失败时，只写一句"暂未获取到实时天气，请以当地实际天气为准"，不编造。因为这个天气会出现在给用户的行程里，编一个"晴 25 度"，用户真的会照着准备。

后来目的地这一步的天气，改成了在回合结束时由代码按整个行程的日期范围直接查询并渲染，模型自己写的天气内容会被删掉。

八、质量双防线

你是怎么评测这个 Agent 的？★★★

分两道防线，用同一套标准。

在线：每份行程清单写库之后，后台异步按三个维度打分，不达标就记一条带着裁判理由的告警日志。

离线：用 pytest 跑三组测试。第一组是路由评测，13 条用例真实调用路由，用确定性的断言判断对错。第二组是行程质量评测，6 条正反样本，按三个维度打分，正样本要求全部达标，反样本要求至少有一个维度不达标。第三组是线上数据检查，从库里取最近几份真实写入的行程逐份打分，库里没有数据就跳过。

两边用同一套标准：裁判和三个维度的定义写在业务服务里，评测目录里只是引用同一个对象，是评测依赖业务代码。如果两边各写一套，比如完整性的标准从"三个时段"改成"四个时段"，业务改了、评测没改，同一份行程线上说合格，线下说不合格。

另外还有一个冒烟脚本，只检查各个部分能不能正常组装、开关能不能切换，不调模型，也不连数据库，跑得很快，改完代码随时可以跑。

为什么用通义千问当裁判？三个维度是怎么定的？★★

DeepEval 的 GEval 默认用 gpt-4o 当裁判，我没有 OpenAI 的 key，就继承它的模型基类写了一个适配器，实现了加载模型、同步和异步生成、返回模型名这几个方法。裁判的温度设成 0，同一份行程每次打分基本一致，否则分数忽高忽低，没法用来做判断。有个坑：不能在子类里加一个只读的 model 属性，因为基类的构造函数会给 self.model 赋值，只读属性会导致赋值失败，一构造就报错。

三个维度分别针对一类真实出现过的问题。完整性：每天有没有 Day 标题，四个时段齐不齐，天数够不够，有没有预算明细，针对的是正文被挤掉、多城漏掉某个城市。需求匹配度：目的地、天数、交通、风格、预算档次和用户的需求对不对得上，针对的是用户要"文化探索"却全是游乐园、要经济型却安排五星酒店。真实性：景点和餐厅是不是真的存在，门票价格符不符合常识，针对的是编造景点和离谱的票价。

判断标准的写法要和实际产出保持一致：正文是按四个时段渲染的，标准就写四个时段，并且说明最后一天晚上只有返程一条不算缺。标准和产出对不上，裁判就会冤枉好的行程。

每次打分都新建三个 GEval 实例，因为它会把分数和理由存在对象上，重复使用会把上一条的结果带到下一条。

require_budget 这个开关是干什么的？★

预算明细只出现在流式输出的 Markdown 正文里，写进库的结构化清单只有标题和逐日行程，没有预算字段。

离线评测用的样本是 Markdown 正文，里面有预算表，"没有预算就扣分"这条标准是成立的。在线质检和线上数据检查用的是清单转出来的文本，这条标准永远满足不了，每份行程都会在完整性上被扣分，产生一大堆错误的告警。

所以给完整性的标准加了一个开关：开着就检查预算，关掉就把这一条换成"本条不适用，不能因为没有预算扣分"。另外两个维度不受影响。离线样本用默认的开，在线质检和线上数据检查传关。

为什么不让裁判自己判断有没有预算？用的是正文还是清单，代码是确定知道的，把一个确定的事情交给有随机性的模型去猜，既没必要，又会让结果不稳定。

追问：清单是怎么转成裁判能读的文字的？ 有一个函数把清单按"标题、第几天、时段：景点（简介）"的格式展开，简介截到 60 个字。要注意的是，字段名的层级写错了不会报错，它只会默默地只返回一个标题。

在线质检为什么是异步的，而且只告警不阻断？★

清单写库之后，调度函数用 create_task 起一个后台任务就返回了，回复不用等打分结束。

有三条要求。第一，出错不能影响业务：质检自己的异常全部捕获，网络问题、限流、裁判输出解析失败，都只记一条日志。第二，只做事后告警：行程已经发给用户了，质检不通过也不撤回、不重新生成。重新生成要让用户多等一轮，还可能反复重试撞上递归上限，所以质检的作用是留一条可以追查的告警记录。第三，防止任务被回收：事件循环对任务只保留弱引用，没有其他地方强引用的话，任务可能还没跑完就被垃圾回收了，所以我把任务放进一个模块级的集合里，任务结束后再用回调把它从集合里删掉。

需求用的是行程的标题，因为标题是根据需求生成的，里面有目的地、天数、出发信息。通过的时候也记录裁判的理由，截到 500 字，方便以后看分数为什么有波动。

〔选讲｜统计过才保留〕开发期的【质检总次数】次在线质检里，有【不达标次数】次不达标，主要是【不达标原因，比如：空清单、时段被截断】，修复之后连续【修复后次数】次全部达标。

路由评测为什么不用 LLM 当裁判？★★

路由的输出是固定类型的：是不是规划、预选了哪些技能，答案是唯一的，可以全部列出来，代码一比较就知道对不对。用一个有随机性的裁判去判有标准答案的题，又慢又贵，还可能判错。

我写了一个自定义的评测指标：是不是规划必须完全一致，因为它决定走哪条流程，闲聊判成规划、规划判成闲聊，后面整个流程都会走错；技能是宽松匹配，命中期望列表里的任意一个就算对，期望为空就不检查，因为一句话可能合理地对应好几个技能，要求完全一致反而会误报。路由输出不是合法的 JSON 就记 0 分，这是被测对象真实的表现。通过的阈值要在构造函数里设置，基类的默认值是 None，在外面后设置的话，断言内部调用时不一定能生效。

13 条用例分成几组，每组针对一类出过的问题：问候和闲聊必须判成不是规划；明确的规划请求；单项查询，按路由现在的实际行为，会预选技能但不进入规划；需求收集中的简短回答，带上历史，必须判成规划，这是问题最多的一组，用户只回一个"杭州"，曾经被判成闲聊；还有表单形式的完整需求。用例写的是路由现在真实的行为，不是理想中的行为。

13 条全对就说"13 条回归用例全部通过"，别说"准确率 100%"。没全对，就说通过了几条、没通过的是哪一类、你是怎么处理的。

正反样本是怎么设计的？裁判可靠吗？★★★

样本必须和线上真实的产出格式一样：有详细行程的标题、带城市名的 Day 标题、四个时段、小贴士、预算表。用"散文式的 Day 加一句话预算"这种和线上不一样的样本，测出来的只是裁判有多宽松。

一共 6 条样本：两条正样本，一条单城一条多城，内容完整、符合需求、信息真实；一条边界样本，是最简单的行程，最后一天晚上只有返程一条，也算正样本，用来防止裁判误判；三条反样本，每条针对一个维度：A 是多城只写了第一个城市、缺了后面两天，针对完整性；B 没有 Day 结构，还编了一个"紫禁城秘密花园"、门票 2000 元，针对真实性；C 结构是完整的，但用户要经济型、人均 1500 元，行程里却是五星酒店和私人直升机，人均超了十几倍，针对需求匹配度。

正样本要求三个维度都不低于 0.5，反样本要求至少一个维度低于 0.5。反样本是用来检验裁判的：只有正样本，只能说明裁判不会冤枉好行程，说明不了它能不能发现坏行程。在我的环境里，正样本【正样本达标数】/3 达标，反样本【反样本识别数】/3 被识别出来。

裁判可不可靠，我是这么看的：温度设为 0，分数基本稳定，但毕竟是模型打分，偶尔会有正好在阈值附近波动的情况。某条样本偶尔失败时，我先看裁判给的理由，再判断是样本写得不够典型，还是判断标准的表述有歧义。

〔选讲｜量过才保留〕同样的配置连续跑两次，正样本的平均分是【正样本均分】，波动在【分数波动】以内。

没做人工一致性复核，就不要说裁判和人工判断一致。

九、收尾问题

这个项目还有哪些不足？★★★

分两类。

一类是主动划定的范围：不订票、不锁票、不支付；不检查段与段之间的时间先后，留给用户在卡片里自己判断；只支持国内，城市对应机场码、对应坐标是手工维护的表，表里没有的城市就不查航班；天气只能查未来几天，更远的如实说明。

另一类是做完之后发现还没做好的，挑几条说，每一条我都知道怎么改：

  • 进程内的状态比较多。候选缓存、查询缓存、直查的多轮追问记录都存在进程内存里，部署多个实例时不共享，卡片提交如果打到另一台机器上，会找不到候选。改法是放到 Redis 里，或者让同一个会话的请求固定落到同一个实例。

  • 路由在直查规则之前调用，直查命中时这次路由是白调的。改法是把直查规则挪到路由前面。

  • RAG 没有单独做召回评测，分块大小、合并权重都是初始值；多个改写问题的结果是直接拼起来的，没有再做一次合并排序。

  • 评测集比较小。6 条行程样本、13 条路由用例，一条就占好几个百分点，只能看出大致方向；裁判也没有和人工判断做一致性比对。

  • 规则型的意图识别，比如确认语、回退、改选交通方式，是靠词表和正则做的，会有漏判和误判。

面试时挑三四条讲就够了，每条用"问题、影响、怎么改"三句话说完。做了附录里哪道扩展题，就把对应的那条不足删掉。

如果并发量上来了，或者要部署多个实例，你会怎么做？★★

先说现状：会话状态和长期记忆已经存在 PostgreSQL 里，这部分多个实例天然可以共享；问题在于进程内的缓存，也就是上一题说的候选缓存和查询缓存，要先放到 Redis，或者让同一个会话固定落到一个实例上。连接池的上限要按"数据库最大连接数除以实例数"来算，再给运维连接留一些余量。

瓶颈主要在外部调用，而不是自己的代码：模型的并发额度、12306 和各个 MCP 服务的限流、高德地点搜索的 QPS 限制。清单补坐标的时候，我已经在每次请求之间加了 0.25 秒的间隔，不然后面的请求会被直接拒掉。按成本从低到高，先减少模型调用次数，比如路由换成小模型，快速通道已经把一轮的调用压到了几次；然后把能缓存的查询结果缓存起来；最后才是加实例。

并发情况下的正确性，靠的是 ContextVar 和按会话分开存储，保证两个会话同时规划不同的城市时，不会串城市、串路段。

〔选讲｜没压测过才保留〕这些是根据原理做的判断，我没有做过正式的并发压测。

A1. RAG 的检索效果你是怎么衡量的？★★

我自己建了一套目的地问答的标注集，一共【标注题数】道，其中【无答案比例】是知识库里没有答案的题。有答案的题，是随机抽一个父块，让模型根据这个父块出题，这个父块就是标准答案，再人工去掉指代不清楚、问得太泛的题；没有答案的题是手写的，一部分完全不相关，一部分看起来相关、但知识库里确实没有，后一种更难。

指标用的是 Recall@5 和 MRR：标准答案的父块出现在前 5 条里就算找到了，MRR 看它排在第几位。检索返回的是父块，直接比较父块 id 就行。

用它回答了"重排值不值得开"这个问题：只改重排这一个开关，Recall@5 从【开重排前】变成【开重排后】，代价是 P95 多了【重排延迟增量】秒，所以重排只在目的地这一步开。

〔选讲｜遇到过才保留〕最初的题目和标准答案的文字重合度很高，召回率高得不正常，相当于把答案透露了，后来加了一步改成口语化的说法，指标才能区分出差别。

保留本题后：第 39 题删掉"没做召回评测"那条准备提示，第 52 题删掉 RAG 那条不足。

A2. 人工审批节点是怎么做的？★★

TravelState 里一开始就留了"是否等待审批"和"审批原因"两个字段，但一直没用上。我在【触发点，比如：预算汇总发现人均超预算时 / 确认行程之前】调用 LangGraph 的 interrupt，暂停图的执行，前端收到【审批帧】后展示给用户，用户的决定通过 Command(resume=...) 传回去，图从暂停的地方继续执行。暂停点由 PostgreSQL 的 Checkpointer 保存，服务重启后用同一个会话 id 还能继续审批。

有一点要注意：恢复的时候，调用 interrupt 的那个节点会从头再执行一遍，所以 interrupt 之前不能做不能重复执行的操作，有副作用的操作要放在 interrupt 之后，或者本身做成可以重复执行的。

〔选讲〕我验证过：暂停之后重启服务，再提交审批，流程能从暂停的地方继续，【验证结果】。

A3. 段与段之间的时间冲突是怎么检查的？★★

课程里是故意不检查段与段之间的时间先后的。我加了一层检查：上一段的到站时间加上【缓冲分钟】分钟的换乘时间，如果比下一段的发车时间晚，就在卡片里把这一段标成红色，提交时给出提示，但不阻止提交，因为用户可能有自己的安排，比如就在同一个车站换乘。到站时间跨天的情况要连日期一起算，不能只比较几点几分。

在【多城用例数】条多城用例里，一共发现了【冲突数】处冲突。

A7. 能力是怎么对外提供成 MCP Server 的？★

用大约【代码行数】行代码写了一个 stdio 的 MCP 服务，把"查班次、查天气、生成行程"做成工具，接入了【你用的工具，比如 Claude Code / Cursor】。工具都是只读的，内部通过 HTTP 调用平台的接口，不直接调用内部函数，这样鉴权和车票入参守卫都能复用。stdio 有个坑：日志必须写到 stderr，写到 stdout 会混进协议消息里。
