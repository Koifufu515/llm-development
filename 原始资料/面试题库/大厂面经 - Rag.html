一、RAG 基础原理

什么是 RAG？为什么要用它？⭐⭐⭐⭐

1.1 面试场景还原

面试官：先介绍一下什么是 RAG，以及为什么要用 RAG 而不是直接用 LLM？

RAG 全称 Retrieval-Augmented Generation，检索增强生成。核心思路是：在 LLM 生成答案之前，先从外部知识库检索与问题相关的内容，再把检索到的内容作为上下文一起送给 LLM，让 LLM 基于真实文档生成答案。

之所以需要 RAG，是因为直接使用 LLM 有三个根本性缺陷：

第一，知识截止问题。 LLM 的训练数据有时间截止，无法感知最新信息。RAG 通过实时检索弥补这一点。

第二，幻觉问题。 LLM 在没有依据时会"编造"看起来合理但实际错误的内容，在企业场景是不可接受的。RAG 强制 LLM 基于真实文档回答，且答案可以追溯来源，用户可以验证。

第三，私有知识问题。 企业内部的合同、产品手册、运营规范，LLM 训练时根本没见过。RAG 可以把私有文档接入知识库，让 LLM 回答企业特定的问题。

相比微调，RAG 的优势是知识更新成本极低——只需要往向量数据库里加文档，不需要重新训练模型。微调要消耗大量 GPU 资源，而且知识固化在权重里，更新很麻烦。

1.2 追问场景

追问 1：RAG 和直接用 Long Context（把文档全塞进 Prompt）有什么区别？

Long Context 把所有文档全放进 Prompt，有三个问题：一是成本极高，把百万字知识库全塞进去，每次请求的 Token 费用是天价；二是存在 "Lost in the Middle" 问题，研究表明 LLM 在处理超长 Context 时，对中间位置的信息注意力显著下降，即使把答案放进去也可能"看不见"；三是延迟高，超长 Prefill 阶段需要几秒甚至十几秒。

RAG 只检索最相关的几段（通常 3~5 段），Token 消耗少，且检索出来的内容都是高相关度的，生成质量更可控。

两者不互斥：最佳实践是 RAG 负责精准筛选，Long Context 模型负责更好地理解这几段内容做综合推理。

追问 2：RAG 和 Fine-tuning 怎么选？能不能结合？

一句话原则：知识问题用 RAG，行为问题用 Fine-tuning。

如果目标是让模型掌握新知识（最新文档、公司规章）→ 用 RAG，因为知识会变，微调后知识固化在权重里无法快速更新。如果目标是改变模型的输出风格、格式、推理方式（比如让它永远输出 JSON、学会某种专业推理范式）→ 用 Fine-tuning。

最佳实践是结合：先用 Fine-tuning 让模型学会"如何正确地利用检索到的上下文"（提升 Faithfulness），再用 RAG 提供最新知识。两者互补，不互斥。

追问 3：你们项目里为什么选择用 RAG 而不是把模型微调？

我们做的是企业内部知识库问答系统，知识库内容更新频率很高，平均每周都有新文档上传。如果用微调，每次知识更新都要重新训练，成本和时间都不允许。而且企业知识库有溯源需求——用户需要知道答案来自哪份文档的哪一段，微调做不到这点。所以我们选择了 RAG，知识更新只需要重新索引文档，几分钟内生效，同时每条答案都附带来源文档和段落，用户可以点击验证。

RAG 完整流程 ⭐⭐⭐⭐

2.1 面试场景还原

面试官：能完整描述一下 RAG 从文档入库到用户拿到答案的全流程吗？

RAG 分两条线：离线建库和在线推理，要分开说清楚。

离线建库（一次性 + 增量更新）：

  1. 文档加载：从 PDF、Word、数据库、网页等数据源把内容读进来。这里最大的坑是复杂 PDF 的解析，表格、多栏排版很容易乱，需要专门处理。

  2. 文档清洗：去掉页眉页脚、重复内容、无意义特殊字符，这步做好坏直接影响后续质量。

  3. 分块 Chunking：把长文档切成合适大小的片段，是 RAG 里最影响效果的步骤之一。

  4. 向量化 Embedding：用 Embedding 模型把每个 Chunk 转成高维向量，捕捉语义信息。

  5. 存入向量库：把向量和原文、Metadata 一起存进向量数据库，建好索引。

在线推理（每次用户提问时）：

  1. Query 处理：对用户原始问题做改写或扩展，提升检索效果（可选但推荐）。

  2. Query 向量化：把用户问题转成向量。

  3. ANN 检索：在向量数据库里找和问题向量最相近的 Top-K 个文档块。

  4. Reranker 精排（可选）：用精度更高的 Cross-Encoder 对 Top-K 结果重新打分，取前 N 个。

  5. 构建 Prompt：把用户问题 + 检索到的文档块按模板组装成 Prompt。

  6. LLM 生成：把 Prompt 送给 LLM，基于检索内容生成答案，流式返回给用户。

二、文本分块 Chunking

Chunking 策略与参数选择 ⭐⭐⭐⭐

1.1 面试场景还原

面试官：你们项目里是怎么做文本切分的？Chunk 大小怎么定的？为什么这么选？

Chunking 是 RAG 里最容易被忽视但影响最大的环节，因为它同时影响检索精度和生成质量。

Chunk 太大有两个问题：一是可能超出 Embedding 模型的 Token 上限导致向量被截断；二是大 Chunk 包含多个主题，向量被"平均"了，检索时语义会被稀释，容易匹配到不相关内容。

Chunk 太小同样有问题：单个 Chunk 缺乏上下文，比如检索到"是的，符合要求"这几个字，完全不知道说的是什么，送给 LLM 也无法生成有质量的答案。

我们项目里的实际做法是分两个阶段演进：

阶段一（快速验证期）：用 LangChain 的 RecursiveCharacterTextSplitter，chunk_size=512 tokens，chunk_overlap=50 tokens。递归切分按照"段落 → 句子 → 词"的优先级依次尝试，优先在语义自然断点切割，比固定大小切分的语义完整性好很多。

阶段二（生产优化期）：升级为父子切分（Parent-Child Chunking）策略——把文档切成小块（128 tokens）用于向量检索，检索命中后返回其对应的父块（512 tokens）送给 LLM 生成。这样做到了检索精准 + 上下文丰富的结合。

参数最终是通过实验确定的：用 RAGAS 对不同 chunk_size（256 / 512 / 1024）跑评估，看 Context Recall 和 Context Precision，选最优的参数组合。

1.3 追问场景

追问 1：Chunk Overlap 有什么用？设多大合适？

Overlap让相邻两个 Chunk共享一段重叠内容，目的是防止关键信息被切割点截断。举个例子：假设有这么一句话——"该产品的退款期限为 7 个工作日，需要提供原始购买凭证"。如果切割点刚好在"7 个工作日"之后，左边的 Chunk知道期限但不知道需要凭证，右边知道需要凭证但不知道期限，两个 Chunk都不完整。有 Overlap 后这句话会同时出现在两个 Chunk里，检索任意一个都能拿到完整信息。

设置多少：经验值是 chunk_size 的 10%20%，比如 chunk_size=512，overlap=50100。不用太大，太大会增加存储和检索时的噪声。

追问 2：文档里有大量表格，Chunking怎么处理？

表格是 RAG 里的一个典型难点，按字符切分很可能把表格切断，导致单元格和表头分离，完全不可读，向量语义也会乱。我们项目里的处理方式：第一，用文档解析工具（比如 RAGFlow 或 Azure Document Intelligence）把表格识别出来，单独转为 Markdown 格式，作为一个完整 Chunk不切割。第二，对于特别大的表格（超过 Token 限制），按行拆分，每行带上表头，保证每个 Chunk都是自解释的。第三，对于数字型表格（如财务报表），考虑用 LLM 把表格转换为自然语言描述，向量语义更好。

追问 3：父子切分里父块和子块的大小怎么定？

没有固定值，取决于文档特点和检索精度要求。经验：子块 128256 tokens（足够捕捉一个具体知识点），父块 5121024 tokens（包含完整上下文），比例大约是 1:4。如何验证：对子块做检索，看 Hit Rate；对父块做生成，看 Faithfulness 和答案完整性。如果 Hit Rate 低，子块可能太大，可以缩小；如果生成答案不完整，父块可能太小，可以加大。

三、Embedding 向量化

Embedding 原理与模型选型 ⭐⭐⭐⭐

1.1 面试场景还原

面试官：Embedding 的原理是什么？你们用的哪个模型，为什么选它？

Embedding 是把文本映射到高维连续向量空间的过程，使得语义相似的文本对应的向量在空间中距离近，语义不同的文本向量距离远。

底层原理：Embedding 模型（通常是 Transformer 架构）通过对比学习训练，给定语义相似的文本对，优化使它们的向量尽量接近；给定不相似的文本对，优化使向量尽量远离。这样训练出来的模型就能把语义关系编码进向量空间。比如"退款政策"和"如何申请退款"，字面差异很大，但 BGE 模型训练后它们的余弦相似度通常在 0.85 以上，而"退款政策"和"今天天气真好"的相似度可能只有 0.1。

模型选型上，我们用的是 Qwen-Embedding-V2，原因有三个：一是中文效果优异，在 MTEB 中文榜表现突出，实测在我们业务场景（法律合同领域）效果优于 OpenAI 的 text-embedding-ada-002，尤其对中文法律专业术语的语义捕捉更精准；二是支持本地部署和私有化部署，数据无需出公司内网，完全满足业务数据安全合规要求，适配企业级隐私保护需求；三是最大输入长度可支持 8192 tokens，远超我们的 chunk_size，不存在文本截断问题，能更好地保留长文本（如法律合同段落）的完整语义信息，减少因截断导致的语义丢失。

如果需要多语言支持或者文档有长段落（超过 512 tokens），会考虑 BGE-M3，它支持 8192 tokens 输入，多语言效果也很好。

1.3 追问场景

追问 1：为什么用余弦相似度而不是欧氏距离？

余弦相似度计算的是两个向量夹角的余弦值，范围 -1 到 1，只关注向量的方向，不关注长度（模）。用余弦而不用欧氏距离的原因：文本长短不同，向量的模会不同，但语义方向是一样的。比如"退款"和"这篇文档详细介绍了退款的相关政策和具体申请流程"，语义相近，但后者内容更多，向量模更大。欧氏距离会认为两者差很远，余弦相似度则能正确识别它们语义相近。大多数 Embedding 模型训练时用余弦相似度优化，向量库检索也默认余弦，两者要匹配。

追问 2：Embedding 模型维度高一定比维度低效果好吗？

不一定。维度高意味着更强的表达能力，但也带来：存储成本更高（1536 维 float32 = 每条向量 6KB，百万条就是 6GB）；检索计算量更大，延迟增加；如果训练数据量不够，高维反而容易过拟合。实践上要根据场景权衡：如果是对精度要求极高的场景（医疗、法律），用高维；如果是高并发、低延迟场景，用低维模型 + 量化。不要盲目追求高维度。

追问 3：领域文档（比如医疗、法律）效果差怎么办？

通用 Embedding 模型在专业领域效果确实会下降，因为训练数据里专业术语很少。解决方案：第一，领域微调：用领域内的文本对（正例：同一知识点的两段描述；负例：不同知识点的描述）对 Embedding 模型做对比学习微调，成本中等但效果提升显著。第二，混合检索兜底：加入 BM25 关键词检索，对于专业术语的精确匹配，BM25 不受 Embedding 领域偏差的影响。第三，提示工程：在 Query 前加领域前缀，比如"法律问题：XXX"，帮助模型理解查询的上下文。

四、向量数据库

向量数据库核心知识 ⭐⭐⭐⭐

1.1 面试场景还原

面试官：向量数据库和普通数据库有什么区别？你们用的哪个，为什么？

向量数据库和传统数据库的本质区别：传统数据库做精确匹配（=、>、<），向量数据库做相似度搜索——找到语义最相近的 K 条记录。

底层技术差异：向量数据库用 ANN（近似最近邻）算法加速检索。如果暴力遍历与每条向量计算相似度，百万级数据就很慢。HNSW 等 ANN 算法通过建立特殊索引结构，牺牲极少精度换来毫秒级的检索速度。

我们项目里的选型：原型阶段用 Chroma，生产阶段迁移到 Milvus。选 Chroma 做原型：轻量、本地就能跑、LangChain 原生集成、零运维成本，适合快速验证方案。选 Milvus 做生产：支持分布式部署，能扛千万级向量；支持 HNSW/IVF 多种索引；Metadata 过滤能力很强，可以在相似度搜索的同时按业务字段过滤；有完善的监控和运维工具。

1.3 追问场景

追问 1：不同用户只能访问自己的数据，向量库怎么做权限隔离？

有两种主流方案：方案一（Metadata 过滤，推荐）：每条向量记录时附带 tenant_id 作为 Metadata，检索时自动注入过滤条件。优点是所有租户共用一个 Collection，存储和维护成本低。缺点是安全性依赖应用层正确传递 tenant_id，需要在服务层做强制注入而不是由调用方传入。方案二（Collection 隔离）：每个租户独立一个 Collection，数据物理隔离，完全没有跨租户泄露风险，但当租户数量多时 Collection 管理成本很高。我们项目用的是方案一，通过统一的中间件层强制注入 tenant_id，调用方无法绕过，同时定期审计过滤日志确保没有遗漏。

追问 2：向量库数据量增大后，检索延迟变高怎么优化？

从索引和检索两个维度优化。索引层：数据量超过百万后，可以从 HNSW 切换到 IVF + PQ 的组合。IVF 把向量聚类成多个桶，检索时只搜最相近的几个桶；PQ 压缩向量表示减小内存占用。两者结合可以在亿级向量下保持较快检索速度，代价是精度略有下降（实测通常 1%3%）。检索层：适当减小 Top-K 数量；对高频查询做结果缓存（Redis）；如果有 Reranker，粗排阶段 Top-K 不需要太大，3050 就够。

五、检索策略

混合检索 Hybrid Search ⭐⭐⭐⭐

1.1 面试场景还原

面试官：你们用什么检索策略？只用向量检索吗？遇到过检索效果不好的情况吗？

我们用的是混合检索，把向量语义检索和 BM25 关键词检索结合起来，用 RRF 算法融合两路结果。

最开始只用了向量检索，上线后发现一类问题特别突出：用户输入合同编号、产品型号这类精确关键词时，检索准确率很低。根因是向量检索本质上是语义方向匹配，对精确关键词不敏感。

引入 BM25 关键词检索后（BM25 是 TF-IDF 的改进版，专门做关键词精确匹配），用 RRF（Reciprocal Rank Fusion，倒数排名融合） 合并两路结果：

RRF 分数 = Σ 1 / (k + rank_i)
k 通常取 60，防止高排名文档过度主导

两路结果里都排名靠前的文档，最终 RRF 分数最高。加入混合检索后，包含专有编号的查询 Hit Rate 从 52% 提升到 87%，整体 Context Recall 从 0.71 提升到 0.85。

1.2 追问场景

追问 1：RRF 的 k 值为什么是 60？能改吗？

k=60 是经验值，作用是平滑排名差异，防止排名第一的文档得分远高于第二名从而主导结果。如果 k 很小（比如 1），排名差距对分数影响极大；如果 k 很大（比如 1000），所有排名的分数差异变小，接近均等对待。可以调整，但通常 60 是个很好的默认值，大多数场景不需要专门调优。如果想给两路检索差异化权重（比如更信任向量检索），可以用加权融合代替 RRF，直接给两路分数乘以不同权重。

追问 2：混合检索的 BM25 部分怎么实现？

有几种方案：第一，用 Elasticsearch 或 OpenSearch，原生支持 BM25 全文检索，也支持和向量检索组合；第二，用 LangChain 或 LlamaIndex 的 BM25Retriever，基于 rank_bm25 库实现，不需要额外部署 ES，适合中小规模数据。我们项目数据量大，用的是 Elasticsearch 做关键词检索，Milvus 做向量检索，在应用层做 RRF 融合。

Query 改写与多路召回 ⭐⭐⭐

2.1 面试场景还原

面试官：用户问题表达不准确或者太简短，你们怎么优化检索效果的？

用户的原始 Query 往往口语化、信息量不足，直接向量化后检索效果差。我们用了两种优化手段：

手段一：Query 重写。用 LLM 把用户的口语化问题改写成更规范、信息更丰富的查询语句，同时去除噪声词。比如用户问"退款咋整"→ 重写为"用户如何申请订单退款，具体申请流程和所需材料是什么"。

手段二：多路召回（Multi-Query Retrieval）。用 LLM 把原始问题扩展成 3~5 个不同角度的问题，并行检索，最后去重合并，再用 Reranker 精排：

原始：  "RAG 效果不好怎么办"
扩展 1："RAG 检索召回率低的原因有哪些？"
扩展 2："如何提升 RAG 系统的检索准确率？"
扩展 3："RAG 常见的优化方案和最佳实践"
→ 三路并行检索，结果去重，Reranker 精排，取 Top-5

代价是多了 1 次 LLM 调用 + 多路并行检索的延迟（并行化后延迟增加有限）。实测多路召回让 Context Recall 提升约 12%，值得这个代价。

HyDE（假设文档嵌入）⭐⭐

3.1 面试场景还原

面试官：听说过 HyDE 吗？什么场景下有用？

HyDE（Hypothetical Document Embeddings）：不直接用用户问题做检索，而是先让 LLM 生成一篇"假设性的答案文档"，用这个假设文档的向量去检索真实文档库。

原理：用户问题是"提问语言"，文档库是"文档语言"，两者向量空间可能有偏差。假设文档也是"文档语言"，和真实文档库的向量空间更对齐，因此检索效果更好。

适用场景：用户问题很短或非常口语化，与文档库语言风格差异大。

局限：如果 LLM 生成的假设文档方向错了，会把检索带偏，在知识密集型场景需要谨慎使用。我们没有在生产环境使用 HyDE，主要用 Query 重写 + 多路召回代替，更可控。

六、Reranker 精排

Reranker 原理与必要性 ⭐⭐⭐⭐

1.1 面试场景还原

面试官：RAG 流程里为什么要加 Reranker？它和向量检索有什么区别？

Reranker 是为了解决向量检索（Bi-Encoder）精度不够的问题。

向量检索用的是 Bi-Encoder（双编码器） 架构：问题和文档分别独立编码成向量，再计算余弦相似度。优点是文档向量可以提前计算并存储，检索时只需要计算一次问题向量，速度极快（毫秒级）。缺点是：问题和文档是独立编码的，它们之间无法进行深层的语义交互，精度存在上限。

Reranker 用的是 Cross-Encoder（交叉编码器） 架构：把问题和每个候选文档拼接成一个序列一起输入模型，模型能充分建模两者之间的语义交互，输出一个精确的相关性分数。精度比 Bi-Encoder 高很多，但每次都要重新计算，不能预计算，速度慢（百毫秒级）。

所以实践中结合两者，做两阶段检索：

第一阶段：Bi-Encoder（向量检索）
→ 从百万文档里召回 Top-50，毫秒级，粗排

第二阶段：Cross-Encoder（Reranker）
→ 对 Top-50 精排，取 Top-5，百毫秒级

→ Top-5 送入 LLM 生成

我们加入 Reranker 后，Faithfulness 从 0.78 提升到 0.91，主要是因为过滤掉了更多噪声文档。

维度 Bi-Encoder Cross-Encoder（Reranker）
编码方式 问题和文档分别独立编码 问题+文档拼接后联合编码
是否可预计算 ✅ 文档向量离线预存 ❌ 每次都要重新计算
检索速度 极快（1~5ms） 慢（50~300ms / 50条）
精度 中 高
用途 向量库粗排 Top-K 精排

1.2 常用 Reranker 模型

模型 特点 推荐度
bge-reranker-v2-m3 BAAI 出品，多语言，性能强，生产推荐 ⭐⭐⭐⭐
bge-reranker-large 中文效果好，开源，轻量 ⭐⭐⭐⭐
Cohere Rerank 云服务，效果优秀，收费 ⭐⭐⭐

1.3 追问场景

追问：Reranker 会增加延迟，如何控制？

Reranker 是延迟的主要增量来源之一，有几个控制策略：第一，控制输入量：粗排取 Top-20~30 而非 Top-100，Reranker 计算量和输入量成正比。第二，批量并行：一次把所有候选文档批量送入 Reranker，而不是串行逐条处理。第三，模型量化：本地 Reranker 模型用 INT8 量化，推理速度提升 30%~50%，精度损失很小。第四，异步预热：对于实时性要求不高的场景，可以先返回向量检索的 Top-1 结果，Reranker 在后台异步精排，下次相同/相似问题命中缓存。

七、RAG 评估体系

RAGas 工具使用

如何系统评估 RAG 效果 ⭐⭐⭐⭐

1.1 面试场景还原

面试官：你们 RAG 系统上线前后怎么评估效果的？用了什么指标？

RAG 评估要分检索层和生成层分别看，否则出了问题不知道是哪里的原因，优化也无从下手。

检索层评估：Hit Rate（命中率）——在 Top-K 检索结果里，有没有包含回答问题所需的正确文档片段，是最直接的检索质量指标。MRR（Mean Reciprocal Rank）——正确文档排名越靠前 MRR 越高，衡量排序质量。Context Precision / Context Recall——精确率（检索到的内容里有多少真正有用）和召回率（需要的内容有没有被检索到）。

生成层评估（用 RAGAS 框架）：Faithfulness（忠实度）——答案里的每个陈述，是否都能在检索文档里找到依据，是核心反幻觉指标。Answer Relevancy（答案相关性）——生成的答案是否切题，没有答非所问或无关废话。

我们的评估流程：手动标注（或用 LLM 辅助生成）300 条测试集，每条包含问题、标准答案、来源文档片段。跑 RAGAS 自动评估，拿到各项指标基线。每次迭代优化后重新跑评估，对比指标变化，只保留指标提升的方案。上线后用 Langfuse 持续监控，对用户标记"答案不满意"的请求重点分析。

指标 低分说明 优化方向
Faithfulness LLM 在编造内容（幻觉） 强化 Prompt 约束；加 Reranker 过滤噪声
Answer Relevancy 答案跑题或废话过多 优化 Prompt 结构；检查 LLM 输出格式
Context Recall 检索漏掉关键信息 引入混合检索；调整 Chunking；加大 Top-K
Context Precision 检索结果噪声太多 加 Reranker；提高相似度阈值；优化 Chunk 质量

1.1 面试场景还原

面试官：如果用户反馈 RAG 系统回答质量差，你的排查思路是什么？

我的排查思路是分层诊断：先定位是检索层问题还是生成层问题，再针对性处理，而不是乱调参。

第一步：判断是检索层还是生成层。把检索到的 Top-K 文档块打印出来看：检索结果里有正确答案但 LLM 没用好 → 生成层问题；检索结果里根本没有相关内容 → 检索层问题。

九、RAG 系统设计

生产级 RAG 系统设计 ⭐⭐⭐⭐

1.1 面试场景还原

面试官：如果从零设计一个企业级 RAG 知识库问答系统，你会怎么设计？

我会分四层设计：数据层、检索层、生成层、工程层。

数据层：文档解析用 RAGFlow 或 Unstructured，支持 PDF/Word/Excel 多格式，对表格做专门处理转为 Markdown。切分用父子切分（子块 128 tokens 检索，父块 512 tokens 生成）。Embedding 用 BGE-large-zh 本地部署，数据不出内网。向量库用 Milvus，每条记录带 tenant_id、doc_id、source_file、update_time 等 Metadata。同时维护 Elasticsearch 做 BM25 索引，支持混合检索。

检索层：先做 Query 重写（LLM 规范化问题）。并行做向量检索（Top-50）和 BM25 检索（Top-50），RRF 融合。BGE-Reranker 精排取 Top-5。设置相似度阈值（余弦 < 0.6 的结果直接过滤），防止噪声送入 LLM。

生成层：Prompt 明确约束：只基于参考资料回答，无相关信息时回复"知识库中未找到相关信息"，不编造。要求 LLM 在答案中标注来源文档编号（[1][2]），支持用户溯源验证。使用流式输出降低首字延迟感知。

工程层：Redis 做语义缓存（GPTCache），对相似问题直接命中缓存，高频问题延迟降 90%+。用 Langfuse 记录每次请求的完整链路（Query → 检索结果 → Prompt → 答案），方便排查和优化。文档变更触发增量索引，不需要全量重建。Prometheus + Grafana 监控检索延迟、LLM 延迟、总 P95 延迟，设置告警阈值。

性能优化手段 ⭐⭐⭐

2.1 面试场景还原

面试官：RAG 系统延迟高，有哪些优化手段？

延迟优化要先定位瓶颈，RAG 的延迟主要来自三个地方：向量检索、Reranker、LLM 推理。每个环节都有对应的优化手段：

优化手段 效果量级 说明
Redis 语义缓存 高频问题延迟降 90%+ GPTCache，语义相似问题命中缓存
流式输出 Streaming 首字延迟感知降低 LLM 边生成边返回，不等全部完成
并行检索 节省多路召回延迟 向量检索 + BM25 用 asyncio 并行
减少 Reranker 输入 Reranker 延迟降 30%~50% 粗排取 Top-20，Reranker 输出 Top-3
Reranker 模型量化 推理加速 30%~50% INT8 量化，精度损失 <1%
Embedding 批处理 建库提速 5~10x 离线批量向量化，非逐条处理

十、前沿方向

GraphRAG ⭐⭐⭐

1.1 面试场景还原

面试官：了解 GraphRAG 吗？和普通 RAG 有什么区别？

GraphRAG 是微软 2024 年提出的方案，在传统 RAG 基础上引入了知识图谱，解决传统 RAG 无法处理多跳推理的问题。

传统 RAG 的局限：只能做"语义相似检索"，问题和答案在同一个 Chunk 里才能检索到。但有些问题需要跨文档推理，比如"张三负责的项目所在城市有哪些供应商"，需要先知道张三负责哪个项目，再知道项目在哪个城市，再知道那个城市有哪些供应商——三步推理，传统向量检索处理不了。

GraphRAG 的做法：用 LLM 从文档里自动提取实体和关系，构建知识图谱（实体是节点，关系是边）。检索时利用图的结构做多跳推理，沿关系链找到答案。额外生成社区摘要，对知识库做全局理解，能回答"这批文档的核心主题是什么"这类全局问题——这是传统 RAG 完全做不到的。

适合场景：文档之间关系复杂（人物/组织/事件交叉），需要多跳推理，需要回答全局性问题。不适合场景：知识库更新频繁（每次更新都要重新提取图，成本高）；简单问答；资源受限（GraphRAG 建库 API 消耗是传统 RAG 的数倍）。

Agentic RAG ⭐⭐⭐

2.1 面试场景还原

面试官：传统 RAG 有什么局限？Agentic RAG 解决了什么问题？

传统 RAG 是固定流程：无论什么问题，都是检索 → 生成，没有任何自适应能力。局限有三个：不知道该不该检索（问"1+1 等于几"也去检索，浪费资源）；一次检索不够时没有迭代能力；无法灵活调用多个工具。

Agentic RAG 引入了 LLM 作为推理中枢，让模型自主决策：

模式 核心思路 适用场景
ReAct 交替推理（Reasoning）和行动（Acting），一步一步调工具 通用 Agent
Self-RAG 模型自判断是否检索、检索是否有用、答案是否正确 高可靠性场景
CRAG（Corrective RAG） 评估检索质量，差则重检或联网搜索兜底 知识库覆盖不全场景

Long Context vs RAG ⭐⭐⭐

3.1 面试场景还原

面试官：现在 LLM 上下文窗口越来越长了，RAG 会不会被取代？

不会被取代，两者是互补关系。Long Context 有四个问题：第一，成本：把百万字知识库全塞进 Context，每次请求 Token 费用极高，企业无法承受。第二，"Lost in the Middle" 问题：LLM 处理超长 Context 时对中间位置的信息注意力下降，即使答案在里面也可能"看不见"，这个现象已有论文实验证实。第三，延迟：超长 Prefill 阶段耗时几秒到十几秒，实时问答场景用户体验差。第四，数据安全：把整个知识库都传给外部 LLM API，在有数据安全要求的企业（金融、医疗、政府）是不被允许的。

结论：Long Context 和 RAG 可以结合——RAG 负责精准筛选出最相关的内容，Long Context 模型负责更好地理解和综合推理这些内容，两者分工合作，效果最佳。

项目经验回答模板（STAR 法则）

面试官问：你们 RAG 项目里遇到过什么印象深刻的问题，是怎么解决的？

示例一：解决检索问题

S（情境）：我们做的是 知行旅游助手（企业合同知识库问答）系统，合同里包含大量（专有编号和法律术语）景点和美食，用户经常直接输入 目的地查询具体美食（合同编号查询具体条款）。

T（任务）：上线后发现含有 目的地美食 （合同编号）的查询命中率很低，只有 52%，用户投诉频繁。

A（行动）：第一步打印检索结果，确认正确文档根本没有被检索到，定位为检索层问题。第二步分析根因：纯向量检索对精确关键词不敏感。第三步引入 BM25 做关键词检索，加上 RRF 融合两路结果。第四步用 RAGAS 前后对比验证效果。

R（结果）：含编号查询的 Hit Rate 从 52% 提升到 87%，整体 Context Recall 从 0.71 提升到 0.85，用户投诉量下降了 80%。

示例二：解决幻觉问题

S（情境）：同一个系统，上线后发现 LLM 有时会给出文档里完全没有的条款内容。

T（任务）：需要把 Faithfulness 指标提升到 0.90 以上，同时不能牺牲答案的完整性。

A（行动）：第一，优化 Prompt：明确约束"只基于参考资料回答，资料中没有时直接说知识库中未找到相关信息，禁止补充或推断未在资料中出现的内容"。第二，引入 Reranker，过滤低相关性噪声文档，减少 LLM 被误导的机会。第三，设置相似度阈值 0.65，低于阈值的检索结果直接丢弃不送入 LLM。

R（结果）：Faithfulness 从 0.78 提升到 0.93，用 RAGAS 自动评估验证，没有出现答案完整性下降的情况。

  2. 手头有真实数字：命中率从 X% 到 X%，Faithfulness 从 0.X 到 0.X，面试有说服力

  3. 每个选型决策都能回答为什么选它而不选其他的

  4. 排查类问题用分层诊断思路，设计类问题用分层架构思路，不要乱说一通
