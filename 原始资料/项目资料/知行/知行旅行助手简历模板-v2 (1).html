  2. 每条控制在 2–3 行。 加粗前缀 4–8 个字，数字可以换个颜色或者加粗突出一些。

  3. 条数不要太多。 大概挑 4-6 条，剩下的放进面试时口头补充就行，主要还是根据自己简历模板去定。

版本 B：场景包装版

包装的边界

这个项目的价值在于架构：意图分流、状态机编排、MCP 接入、并行取数、代码兜底、质量评测。这套架构确实是通用的，换一个业务域照样成立。但"换域"不是改几个名词：

  • 可以：换业务域、换数据源、换流程步骤、换叙述重点，然后在新域上真的跑一遍，用新跑出的数字。

  • 不可以：没改代码就把旅行项目说成 Oncall 项目；编造 MTTR 下降、客诉减少、上线用户数这类业务结果。面试官问一问就穿帮，背调也可能核实。

  • 数据源可以是模拟的，但要说清楚。"本地 kind 集群 + 演示微服务 + 故障注入"和"模拟订单服务"都是正当的工程验证方式，简历里如实写"在 XX 环境上验证"。

没精力改造，就用版本 A，最好是不要硬套。

方向菜单

挑方向的两条原则：选你能搭出真实验证环境的（凭空编的数据源一问就露）；选和目标岗位 JD 关键词重合最多的。

① SRE / Oncall 排障（适合：SRE、基础架构、平台研发）

  • 流程：告警确认 → 影响面评估 → 根因排查 → 处置选择 → 执行确认 → 恢复验证 → 复盘

  • 数据源：Prometheus、Loki / ES 日志、K8s API（只读）、发布记录、服务目录（自建）、Runbook 走 RAG

  • 并行 + 卡片：受影响的上下游服务并行取证；处置方案卡片（回滚 / 扩容 / 限流）

  • 单点直查："order-service 现在错误率多少"

  • 代码接管的事实：指标数值、变更时间线、受影响服务列表

  • 怎么验证：kind 或 minikube 起集群 + 演示微服务 + 故障注入脚本

② 电商售后 / 客服工单（适合：客服技术、交易中台、AI 应用）

  • 流程：问题收集 → 订单定位 → 责任判定 → 方案选择 → 执行 → 回访记录

  • 数据源：订单、物流、库存、退款接口（自建模拟服务）、售后政策走 RAG

  • 并行 + 卡片：一单多包裹并行查物流；补偿方案卡片（退款 / 换货 / 发券）

  • 单点直查："订单 123 到哪了"

  • 代码接管的事实：退款金额、运费险、售后时效按规则计算

  • 怎么验证：用公开电商数据集造模拟订单库，简历写"模拟业务系统"

③ 企业 IT 服务台（适合：企业服务、内部平台）

  • 流程：诉求收集 → 账号 / 资产定位 → 方案匹配 → 审批路由 → 执行 → 验收

  • 数据源：OpenLDAP、资产库、工单系统、审批流（自建）、IT 制度走 RAG

  • 并行 + 卡片：多个系统的权限并行核查；权限申请卡片

  • 单点直查："我的 VPN 账号过期了没"

  • 代码接管的事实：审批人、权限范围按规则算，不让模型决定

  • 怎么验证：Docker 起 OpenLDAP + 模拟资产库

④ 数据分析问数 ChatBI（适合：数据平台、BI、大模型应用）

  • 流程：需求澄清 → 指标口径确认 → 选表 → 生成 SQL → 执行校验 → 可视化 → 结论

  • 数据源：只读 SQL 执行、元数据目录、指标定义、图表渲染

  • 并行 + 卡片：多指标多维度并行查询；口径确认卡片

  • 单点直查："昨天 GMV 多少"（命中指标库直接取数）

  • 代码接管的事实：所有数字只来自 SQL 执行结果，模型只写解读

  • 怎么验证：TPC-H 或公开电商数据集导入 PostgreSQL

⑤ 企业差旅与费控（改造量最小，适合：企业服务、SaaS）

  • 流程：原 7 步 + 差标校验 + 审批

  • 数据源：保留 12306 / 航班 / 酒店，新增自建差标服务、审批流

  • 并行 + 卡片：原样

  • 单点直查：原样，外加"我这个职级住宿标准多少"

  • 代码接管的事实：差标按职级与城市等级计算，超标自动标红

  • 怎么验证：直接在现有项目上加，工作量最小，也最不怕追问

[项目名] — 面向值班排障的多步骤 Oncall Agent

技术栈：Python、LangChain 1.x、LangGraph、MCP、FastAPI、PostgreSQL、Redis、Prometheus、Loki、Kubernetes、DeepEval、pytest

项目介绍：针对值班排障依赖个人经验、告警 / 日志 / 变更记录散落在多个系统的问题，+做的多步骤排障 Agent。意图识别区分单点查询与完整排障；状态机引导完成告警确认 → 影响面评估 → 根因排查 → 处置选择 → 执行确认 → 恢复验证 → 复盘，经 MCP 接入 [6] 个运维数据源，在本地 [kind 集群 + 演示微服务] 上用故障注入验证。

技术亮点（挑 5–6 条）：

  • 两层意图识别：规则层用服务名清单 + 意图词表组成确定性门禁，"查下 order-service 错误率"这类单点查询零 LLM 直查并支持多轮补槽；LLM 层以结构化输出区分闲聊、知识问答与完整排障，带最近 4 条历史续接短回答，回归用例 [28/30] 通过

  • 状态机驱动排障：以 current_step 驱动 7 步排障流程，中间件每步只开放该步工具（如根因步才开放日志检索）并校验前置依赖；根因被推翻时回退工具级联清空下游方案与执行记录，会话经 Checkpointer 持久化，交接班可续接

  • 数字与时间线归代码：错误率、延迟、变更时间线由代码直查并渲染，模型只提交结构化的根因假设和所引证据 ID，引用不存在的证据直接拒收，从流程上杜绝"编一个看起来合理的 P99"

  • MCP 多源接入：单例客户端按服务隔离加载 Prometheus、Loki、K8s、发布记录、服务目录等 [6] 个数据源，单源故障只降级自身；日志工具外挂守卫做参数归一、按会话回填时间窗，并把单次 [2 万行] 日志按错误签名聚合为 [15] 行

  • 多服务并行取证 + 处置卡片：受影响的上下游服务用 asyncio.gather 并行拉取指标、日志与最近变更，[5] 个服务取证 [18 s → 5 s]；回滚、扩容、限流等方案以卡片下发，值班人勾选后按 option_id 校验并幂等执行

  • 已知告警快速通道：命中 Runbook 已收录的标准告警时跳过逐步确认，并行取证 → 规则匹配处置项 → 单次 LLM 生成处置摘要，端到端 [3 分钟 → 50 秒]；变更类动作仍强制人工确认

  • 质量双防线：GEval 三维度改为步骤完整性 / 告警匹配度 / 证据真实性，标尺在线离线共用；离线回放 [20] 次故障注入（Pod OOM、慢 SQL、错误配置发布等），根因命中 [17/20]；在线质检只告警不阻断
